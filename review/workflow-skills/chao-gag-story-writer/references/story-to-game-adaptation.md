# 纯剧情到游戏流程的解构

## 使用时机

分两种粒度使用，分文件不等于思考完全串行。

## 早期玩法概念

与简洁章纲共同构思：双方在争取什么、玩家能改变什么、哪些故事结果固定、哪些方法开放、哪些分支需要用户批准。读取当前玩法总案入口，优先现有玩法族。只提前检查会推翻故事的空间、能力和资产风险，不排完整动作链、回合表、数值与镜头。

故事可以要求韩秀雅作出某个选择，但普通战斗不因此只剩按顺序点指定单位。检查同伴是否在改变战术问题，而非替玩家完成全部解题。

## 详细解构时机

纯剧情Episode Reader暂定成立后，再派生下面的详细文件。发现矛盾可以退回故事，不得在后台补动机或偷偷改故事。

## 输入

- 已通过的纯剧情Reader；
- 机体可用能力和生命周期；
- 本章玩法边界、地图现实和制作预算；
- 上一段IncidentState与本话必须输出；上一话不一定已经Clear。
- 本章已经通过的`story_play_topology`，包括稳定`story_unit_ids`、Operation边界、跨话状态、跨Operation `carry_from_state`和真正的Mission Clear位置。

不读取旧混合Reader来补答案。

## 输出结构

```markdown
# CxxExx 游戏流程解构

## 玩家体验一句话
## 游玩顺序

### 1. ADV / 自由活动
### 2. 探索或副玩法
### 3. SRPG战斗
### 4. 战中剧情与演出
### 5. 战后ADV / 关系事件
### 6. 结算与下一话交接

## 变量与分支
## 资产与演出级别
## 与纯剧情Reader的一致性
```

## 解构原则

1. 先圈出故事中的主动目标、对手反击、人物选择和结局，再决定哪些交给玩家操作。
2. 关卡目标必须是故事冲突的可操作版本，不能另加一套任务。
3. 故事里一个大动作，可以在玩法中拆成多个阶段；这些阶段不反写回剧情正文。
4. 可由画面、动画、地图变化或短通讯表达的信息，不写成长篇系统说明。
5. 游戏机制若要求人物做出违背常识或人设的行为，优先换机制。
6. 制作成本过高时，缩减交互层和资产层，不用技术解释压缩剧情。
7. Episode只是叙事切点，不自动生成一张新地图、满状态编成或Mission Clear。同一Battle Incident跨话时，必须继承敌人、伤势、装备、地图破坏、平民风险、目标和时间。
8. 一话可以含多个Encounter；同一Encounter也可以跨话。比赛分、阶段优势、撤离成功和Boss换形都可产生Checkpoint，但只有世界中的主要冲突真正结束时才触发Mission Clear。
9. 解构前先声明映射模式：`direct_play`、`supported_play`、`observe`、`expanded`、`compressed`或`optional_echo`；再声明玩家代理权是`execution_only`、`cost_or_route`或`authorized_branch`。
10. 户外战棋地图不受单屏限制。街区、道路、建筑和可破坏物属于可滚动棋盘本体；只有故事空间确实封闭时才采用固定小图。

## Operation拓扑门

正式拆分Episode游戏流程前，逐章锁定以下对象：

```text
Story beat / Scene
-> Episode
-> Battle Incident / Operation
-> Encounter / Play Segment
-> Battle Phase
-> Checkpoint / Save Resume
-> Mission Clear
```

这些对象是多对多关系。每个边界必须写明`boundary_type`和`IncidentState`输入/输出。若Episode切话后仍有敌人未退、伤员未处理、装备未归还、地图仍在崩坏或主目标未完成，只允许`episode_cut + checkpoint`，不得结算、治疗、刷新敌人或回到Hub。

## 退回条件

- 玩家为什么行动只能靠本文件解释；
- 战斗没有明确争夺对象；
- 玩法让人物作出未经授权的选择，或剧情预排动作使普通战斗只剩照稿点击；
- 需要新增装置、权限或巧合才能把故事变成关卡；
- 关卡胜利与剧情胜利不是同一件事。

命中任一项，退回故事架构或因果门，不在游戏流程里补丁。
