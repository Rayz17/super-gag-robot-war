# 超GAG写作生产

## 当前方法

2026-09-05起采用“主笔创作、按需知识、剧情与玩法共同构思、分层交付”。项目方法合同：`docs/superpowers/specs/2026-09-05-chao-gag-author-first-writing-method-v1.md`。

本入口替代旧固定配额、压力板先行和逐席补强流程。旧入口按原字节保存在`references/history/pipeline-before-2026-09-05.md`，只用于追溯，不作为新写作指令。其他未迁移的旧references只在明确追查历史流程时读取；不得把旧强制字段、固定审稿席或素材数量重新带回主笔输入。

本Skill负责文件、来源、依赖、验证与接受回写。`chao-gag-story-writer`负责人物、故事取舍、正文及体验。不能让工程检查替作者选择故事，也不能以创作自由绕过已验收事实。

## 入口与权限

1. 使用`chao-gag-canon`确认权威；运行live dashboard和当前章Story Chain查询。不要在Skill中缓存NEXT、章数、话数或特定章节剧情。
2. 读取用户最新反馈。机器READY只表示依赖通过，不覆盖用户的否决、暂停或缩小范围。
3. 区分本轮是`creative_candidate`还是`formal_integration`，在工作计划中明示。不默认开展整章、下一话、Canon迁移或游戏实现。

`creative_candidate`是正式生产之前的探索，可以写提案、关键场面、纯剧情样稿和玩法概念，不需要先填完旧链所有生产板。全部放独立Candidate目录，不覆盖manifest所指的封存文件，不提供自动PASS/验收资格。

`formal_integration`才修改正式章节产物。先按最早受影响阶段合法invalidate，再顺序重建和封存。不能把新的探索顺序理解成篡改旧manifest阶段顺序；更不能刷新SHA伪装复核。探索稿被选中后可以作为已声明来源支持重建，但不能冒充已验收Reader或免除独立审查。

## 四种输入

| 类别 | 内容 | 用法 |
| --- | --- | --- |
| `fact` | 已验收前情、有效身份、能力和世界限制 | 不可静默改动；保留完整限制与来源 |
| `future_obligation` | 当前章职责、下章接口、未来保留 | 保留目的；实现可提新案，重大结果变更需裁决 |
| `creative_material` | IP精神、名场面、生活、喜剧、历史高光 | 可全部不用；不按引用数量验收 |
| `presentation_option` | 候选空间、战斗编排、画面与承载 | 未批准前可重构；已封存事实仍走迁移 |

上层文档的Working身份不代表每句未来安排已经发生。源有冲突先裁清本次要用的事实，不以“较新文件”自动覆盖正式接受记录。History保留可追溯性，不进入普通写作宽查询。

## 创作顺序与正式回填

```text
有效前情、世界限制、人物模型、当前职责
-> 主笔作故事取舍
-> 简洁章级故事梗概 <-> 玩法概念与尺度可行性
-> 最不确定的完整场面试写
-> 单一主笔顺序完成纯剧情Reader
-> 体验首读与独立事实/因果审查
-> 独立详细游戏解构、按需公开情报
-> 三层一致性、用户验收、确认事实回写
```

这是创作探索顺序，不是越过现有正式Story Chain的命令。正式链尚要求三板/拓扑先于总纲、L4.5先于Reader时，将它们用于核验选定故事的可制作性，不用它们从零编故事。只派发当前合法阶段；重大分歧先决定故事，再一次性重建受影响依赖。

章纲写人物选择、连续情势、关键转折、高潮和去向，不写第一遍详细Reader。正文不再通过给动作表加对白来生成。物理可行性只提前核对会推翻故事的尺度、控制、时间和简单替代，不在探索阶段穷举每个关节、设备与镜头。

选案数量按问题决定：方向明确时可一个主案加反例检查；有真正分歧时给2-3案。用户明确要比较或实验时照其范围执行。不是每话重新三选一。

## Runtime与单次交互

使用`references/story-runtime-v3.md`和当前请求模板。新创作使用`context_policy=author_first_v1`；旧自动装载只以`legacy_inspection`复现历史结果，不得喂给新主笔。

Runtime按问题检索，主笔可在提案、场面、正文和复核时多次查询。选中人物复用稳定模型，但模型不规定标准台词或最终选择。查询只能回答事实与可用素材，不能自动生成完整高潮动作链。

硬事实、未来限制和选中人物不得静默截断。超预算缩小问题或拆成完整场面，不减少硬限制；可选素材只能整条省略，并列出可再查询的ID。来源和工具版本参与指纹；本地缓存与模型计费分别记录，未知成本不填0。

同一主笔可以连续规划与创作。模式是职责隔离，不是每个模式必须新开一次Agent。只有体验冷读需要不知道作者答案的隔离上下文；若工具不可用或未授权，明确自审，不能声称独立评审。

不把模型输出容量当目标字数。长话按完整戏剧场拆分，每段继承必要状态和前文尾部；不要固定切碎每个场面、不断重启作者。未获用户确认的局部出口只是本次Candidate状态，不回流Current知识。

## 玩法共同构思与分层交付

章纲阶段读取当前玩法权威入口，提出敌方目标、玩家可改变的局面、固定故事结果与可选方法。优先已有玩法族，不因换章节就发明系统。

纯剧情只写世界内的行动、人物和胜负转折，不写UI、回合、条件变量、资产或程序。详细游戏解构在故事暂定成立后另写；允许反向提出问题，不允许偷偷补人物动机或改故事结果。公开情报可选，不是理解正文的前提。

Operation/Encounter/Phase/Episode是多对多，不按每话结算。正式解构保留`story_unit_ids`、`carry_from_state`、IncidentState及玩家代理权。只有世界内主要冲突结束才Mission Clear；切话不能清伤、复活敌人或重置地图。户外地图可滚动，建筑属于棋盘本体。

剧情动作的触发事实和结果归故事/规则所有；演出只负责呈现。正式平台、美术、BOM、性能与运行验证另行授权，不能阻塞不依赖它们的纯剧情探索，也不能被纸面合同冒充已完成。

## 审查与成本

默认只区分两类问题，不默认17席或逐项素材审计：

- 体验首读：必要已知前情+正文，先复述、再判断是否想读、何处动人/无聊/不可信。不给作者意图、工程板和内部PASS。
- 事实/因果及必要玩法复核：有效来源+正文，检查身份、尺度、控制、时序、知识、跨章继承与可玩性。不能推翻首读没读懂的事实。

同一上下文不能伪称多个独立席。局部错修局部；发动机或人物选择不成立，回提案，不加技术解释。一次结构性重写仍不能解决就停并报根因，不自动多轮补强。

交稿前由主笔在当前单话源完成一次称谓与时间指代复读，沿用story-writer的`references/drafting-reader.md`，不另开Agent门。检查既有名字、实物状态、版本与历史是否说准；不把“旧”等字的计数当质量分，也不把自动替换结果当审稿通过。修词后机械重建合章，保留既有事件和正式名称。

没有每话新机、燃泪Gag、感情硬动作、敌方必获益或固定债务数配额。既有明确用户事实仍有效；去配额不等于取消机战主体、玩梗、群像、资源连续性或全剧成长。生活可以只增加熟悉感，获胜可以是真正获胜。

首轮新方法与同模型、同事实和近似预算的最简直接主笔比较。实际用量、耗时、返修和用户阅读负担一起记账。不以更多步骤、字数或机器PASS判胜。具体实验范围由写作计划约定，不在每章重复整套实验。

## 正式生产治理

- 写正式文件前运行对应`--before-stage`，修改passed上游前执行`--invalidate-stage`；不手改passed/hash。既存Accepted故事须有明确范围授权才能替换。
- 章节Reader只按manifest中的Episode路径、顺序和SHA机械合成，不glob目录，不手改合章。
- 前章Reader/状态账/用户接受回执变动，需要正式兼容审查与合法重绑定或失效；不能用内部PASS替换用户接受。
- 话数变更使用`resize_v35_story_chain.py`及迁移依据，总上界从registry读取，不写死。
- 校验正式适用的packet、topology、人物状态与Canon；旧ELO配额检查只适用于历史复现，不作为新方法创作门。
- user_acceptance只记录用户真实批准及精确产物；不得代签、推断沉默、复用旧SHA接受或自动解锁下一章。
- 未完成的事实冲突、制作债、体验问题分别记录。技术测试通过不清除体验阻断。
- Canon、图谱、生产回写只更新受影响项，不批量美化历史，也不清理并行改动。
