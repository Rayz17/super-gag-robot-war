# Story Runtime v3：分阶段知识与人物建模

## 目标

Runtime是可查询的知识底座，不是代替编剧的剧情编译器。它应当：

- 让主笔在需要时找到正确设定、人物、机体、前情和素材；
- 防止人物提前登场、忽然到场、获得不属于自己的能力或机体；
- 保证L1至L3的作品目标与全剧波形不在细写时失踪；
- 给作家真正的否决、选择和迁移权；
- 只把用户确认的新事实回写知识底座。

Runtime不应当：

- 在选案前预写高潮、动作链、人物出站状态或正确答案；
- 为了「完整」把Canon、素材库、旧Reader和全员档案全部塞给主笔；
- 把旧Working章节或旧高光当成不可否决的标准答案；
- 用更多技术名词修复普通常识即可解决的因果问题。

每个阶段包会生成`06-writer-view.md`。主笔默认只读这一份决策视图；其他完整切片、TSV、trace和冲突表是审计与定向二次查询工具，不得全量塞入Prompt。

## L1至L6的使用时机

| 层 | 在Runtime中的作用 | 何时读 | 不能做什么 |
|---|---|---|---|
| L1体验宪章 | 判断本章是否仍在给玩家机战、GAG、关系、情绪与玩家意志 | `ideation`、`design review` | 不得变成每话配额；冷读不看 |
| L2总发动机 | 确认万机馆为何移动、长期对手在做什么、胜利如何推动下一局 | `ideation`、`design review` | 不得要求本话解释全部宇宙设定；冷读不看 |
| L3结构母盘 | 给出本章能量位置、上下章因果、机体/人物生命周期和未来保留 | `ideation`、`scene_plan` | 不得把候选章号当成永久结构 |
| H0/Canon | 给出世界机制、当前位置、控制权、所有权、知识和物理状态 | `entity_model`、`scene_plan`、`review` | 不得默认把所有条目发给作家 |
| L4章级总纲 | 提供可迁移章引擎、主要变化与出口 | 选案后的`entity_model`、`scene_plan`、`design review` | `ideation`只看章位，不读旧答案；必须按ID准入 |
| L4.5演出承载 | 规定玩家怎样看见、操作或听见关键因果 | 选案后的`scene_plan`、`design review` | 不得用制作表代替故事；正文只拿已选载体 |
| L5 Reader | 是写作产物、冷读对象或揭盲基准 | `cold_reader`、`benchmark`、`writeback` | 旧同章Reader不得进入重构输入 |
| L6台本/演出/关卡 | 在L5通过后落实制作 | L6专用流程；当前为空 | 不得反向篡改未迁移的上游故事，也不得假定已有资产 |

## 七个阶段

### 1. `ideation`

只给：L1/L2/L3摘要、上章出口、本章职责、合法人物索引、机体/对手索引和未来保留。

产物：三种白话成立、结构不同的剧情方案。它们可以使用不同的主角欲望、对手手段、机体奇观、战斗目标和关系反转。

### 2. `research`

方案选定后，用它的具体问题检索IP、名场面、名台词、机体、模玩生态、喜剧、关系和What-if材料。主笔选用，Runtime不自动准入。

### 3. `entity_model`

只对已选人物、机体、对手、地点、关键物件进行稳定建模。每个重要人物模型保留：

Runtime同时显示本章已登记的L4/L4.5来源索引；只将主笔点名的`admitted_layer_source_ids`作为迁移参照调入。目录里“看起来像最新版”的文件没有自动资格。

- 形成史、欲望、恐惧、核心矛盾；
- 压力行为、亲密行为、声线与禁止扁平化；
- 能力边界、知识边界、机体/道具/权限归属；
- 关系边和当前弧线状态；
- 首次登场、当前地点、本场存在方式和出场生命周期；
- 每一条信息的来源与Hard/Working/Candidate层。

可用存在方式包括`physical`、`remote_live`、`recording`、`work_trace`、`linked_machine_soul`、`not_present`。「在章里有用」不等于「肉身在场」。

### 4. `scene_plan`

导演板和因果预演必须确认：

- 谁在哪里，怎样到达，能看见和听见什么；
- 机体尺寸、移动、控制者、受损和可用动作；
- 双方目标为何不兼容，为何不能用更简单办法；
- 每场结束后哪些人、机体、地点、资源、知识和关系发生变化；
- 玩家如何看到关键信息：ADV、地图事件、短动画、战中通讯、探索、玩法结果还是环境证据；
- 删掉梳理旁白后，普通玩家是否仍能理解。

### 5. `draft`

作家只读选定方案、精简因果骨架、本场活跃人物切片、准入素材和上一场出口。先写一个完整场做熔断，通过后再继续。

### 6. `review`

- `review_scope=cold_reader`：只读玩家已知前情和正文，先复述自己读到的因果，不得读导演板、设定答案、旧同章Reader或作者意图。
- `review_scope=design`：逻辑、机战和制作席另读独立事实切片及显式准入的L4/L4.5，验证位置、控制、知识、尺寸、生命周期和演出承载。
- `review_scope=benchmark`：冷读结果封存后才揭盲旧同章Reader，用于比较增量与成本，不能修改第一次阅读判断。

### 7. `writeback`

只在用户确认后生成：人物状态差量、关系边变化、机体生命周期、位置/控制/伤势/资源变化、新悬念、已回收信息和Canon迁移候选。

## 人物与实体门

进入`scene_plan`前必须通过：

1. 每个重要人物有稳定模型或明确的建模缺口。
2. 远程、录像、作品痕迹、机魂联系和肉身出场不得混用。
3. 人物未首次正式登场前，不得承担现场职能。
4. 人物、机体、道具、权限和知识的归属不得因剧情方便静默改变。
5. 新具名人物必须解释既有人物为何不能承担、本章功能、资产成本、章末去向和未来复用。
6. 编剧可以改变Working设定，但要显式提交迁移；默默遗忘、改名或绕过属于失败。

## 反过度工程化规则

- Runtime包不得用字段齐全证明故事成立。
- 审查发现动机、常识、空间或台词问题时，先给最简单修法，不允许新造名词修复。
- 稳定人物模型只提供反应范围，不提供本场标准台词。
- 作家可以为了更好的戏拒绝检索素材、旧高光和Working章引擎。
- v2.2的交互级缓存和事务拆分只用于已通过选案、建模和场面规划的超长单话，不再从零生成剧情。
