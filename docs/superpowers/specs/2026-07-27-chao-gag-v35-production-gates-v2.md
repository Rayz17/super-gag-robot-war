# V35章节生产门禁v2

> Status: `working_writing_workflow_migration / non_canon`
>
> 日期：2026-07-27
>
> 目的：让章节生产既能追溯因果，又不会把机器PASS误当成“故事已经好看”。

## 一、修正的五个根因

1. **工程通过不等于创作通过。** 哈希、依赖、Canon与字段检查只证明过程一致，不能判断燃点、可读性、关系吸引力和继续游玩的欲望。
2. **因果盲审发生太晚。** 过去往往到Reader或连续阅读时才发现人物为何行动、空间怎样连接、谁控制机体等根因。
3. **话数迁移会分裂。** 章节Registry、L3上界、manifest、Canon场景和看板曾需要分别修改，容易出现不同版本的容量事实。
4. **所有章节同一成本。** 舰内关系章与多尺度巨构大战都跑重量流程，造成文档负担和上下文衰减。
5. **去AI味被误当作正则任务。** 确定性lint能抓句式，抓不到人物替作者讲结论、人人同声和关系表演失真。

## 二、新的唯一顺序

```text
全剧看板选中当前章
-> 选择 light / standard / heavy 档位
-> 章级对齐与最小上下文
-> 档位化预生产
-> 导演板 / 战斗预案 / 必要物理板
-> 完整剧情总纲
-> 独立首读因果盲审
-> 逐话结构 / 状态 / 四视角 / 累计连续性
-> L4.5演出承载
-> 一次一话Episode Reader
-> 机械合成章节Reader
-> Reader时间空间与物理因果盲审
-> 人类声线语义审查
-> 确定性lint与章节总审
-> 用户创作验收
-> 下一章
```

`chapter_review`只表示内部生产完成。`user_acceptance`才表示用户愿意让当前故事成为下一章的上游。

### 已有章节的批次返修

线性新写仍必须等待前章`user_acceptance`。但用户明确要求对一组已经存在的章节做连续返修时，可以建立一份限域的“批次返修授权”：

- 文件必须列出`Authorized-Chapters`，并明确`Does-Not-Grant-User-Acceptance: true`；
- 前章必须已有当前哈希的`chapter_reader + state_ledger + chapter_review`；
- 后章`series_alignment`绑定上述三项及返修授权文件的联合指纹；
- 返修授权只允许内部回迁、重封和跨章复核，不得把`user_acceptance`写成`passed`，也不得解锁授权范围以外的新章；
- Story Chain首次重封`series_alignment`时显式传入`--repair-batch-authority <path>`，其后从清单notes自动复核授权路径和哈希。

该通道解决“用户要求整批修旧稿，却被逐章验收门卡死”的维护场景，不改变正常创作顺序。

## 三、三种生产档位

| 档位 | 适用范围 | 必要证据 |
| --- | --- | --- |
| `light` | 既有人物、空间、能力、控制链与战斗语法的关系章或短过渡章 | 标准工件可以简写和引用；物理板可选 |
| `standard` | 新增一项重要场所、能力、敌方规则或控制链 | 完整预生产模型；有歧义时补物理板 |
| `heavy` | 新巨构、多尺度、变形、机魂/现实交叉、新能力首用、三方混战或地形决胜 | 物理板必需；补尺度、控制、地图灰盒和关键奇观预演 |

档位不删除首读因果盲审、声线语义审查、用户验收或标准目录。

## 四、首读因果盲审

盲审只读取完整总纲、上一章精简退出状态、本章一句话发动机与预定退出状态。不得读取导演板、物理辩护、术语词典和作者预设答案。

分发盲审前必须先过“输入来源门”：从当前章节Registry与前章manifest编译精简退出状态，核对章名、前后继、话数、当前Reader与状态账哈希。任何标记为`history`、`superseded`、`retired`或位于`_history`的继承包，都不得作为当前因果审查输入；若旧继承包与当前Registry冲突，应先修正文档生命周期或重新生成当前继承包，不能要求现行剧情倒回旧稿。盲审回执必须列出实际读取的上游文件及状态，来源不明时返回`INPUT_BLOCKED`，不得给剧情下PASS/FAIL。

读者必须能复述：

- 谁想得到什么，冲突为何现在发生；
- 各方为何行动，为什么不用更简单的方法；
- 人物与机体在决定性场面的地点和控制权；
- 胜负如何由前文动作产生；
- 章末发生了什么不可逆变化；
- 下一章为何自然被发动。

失败时由单一主笔回到最早责任层修改，审稿者不向正文追加解释。

### 4.1 冲突不可并行门

任何足以发动Boss战、阵营决裂或重大事故的冲突，在首读因果盲审中必须单独回答：

1. 双方能否同时做各自想做的事，例如一边准备发射一边交付物件；
2. 能否交给中立保管者、暂时停机、卸武装、切远控、换驾驶员、绕路、等待或撤退；
3. 仍在现场且上一场可用的人、载具、吊机、通道和权限，能否直接解决；
4. 若存在和平解，为什么人物没有提出或采用；
5. 战斗结束后究竟改变了哪项条件，才让停火、放行或合作成为新的合理选择。

“时间很紧”“双方顺序不同”“某人挡在路上”不能单独通过此门。若两个目标可以并行，正文必须采用和平解，或在前台建立至少一项真正不可兼容的对象状态、控制权、主体存续风险或物理限制。该判断必须写入物理因果板与首读回执，不另建新表。

### 4.2 线索揭示生命周期

跨话线索必须在导演板的信息揭示表中使用以下阶段之一：

`发出 -> 观察 -> 分离/定位 -> 解读 -> 验证 -> 修正`

同一证物、信号、记忆或异常不能在两话中重复宣称“第一次发现、终于还原、正式确认”。后一次出现必须增加新信息或推翻旧判断。Episode Reader若需要改变阶段，先回写导演板；不能靠换一个近义词重复制造悬念。

## 五、人类声线语义审查

语义审查在章节Reader合成后、确定性lint之前完成。它检查有限认知、具体听众、动作压力、角色差异、沉默空间、关系欲望和作者借嘴。零条正则命中不能替代该审查。

高风险场景至少做隐名、互换、听众、关声和朗读测试。发现“漂亮但不像人话”时，优先改人物行动、信息来源和场面压力，不做同义词替换。

## 六、Reader物理因果盲审

这一门位于机械合成章节Reader之后、声线审查之前。它与第四层的`first_read_causal_audit`不是同一件事：

- `first_read_causal_audit`检查完整总纲的发动机是否成立，防止错误进入逐话生产；
- `reader_causal_audit`检查逐话表演和正文是否重新制造了时间、空间、受力、站位、证据或安全常识错误。

审稿者只允许读取当前章节Reader、上一章结尾和必要的前章Reader，不得读取导演板、物理板、设定词典、资料卡或作者解释。至少回答：

1. 天色、日期、航程、维修和通信时间是否连续；
2. 人、机体、展舰、建筑和敌人的位置、尺寸、移动路径及可达范围是否成立；
3. 谁在驾驶、远控、接入、失去控制，身体和意识各在哪里；
4. 角色怎样获得证据，证据是否真的在此前出现；
5. 事故是否有可见的失效链，正常安全装置为何没能阻止；
6. 有能力的人为何没有采用更直接、更安全、更便宜的办法；
7. “首次出击、首次母舰战”等说法是世界内首次还是玩法解锁首次。

其中第6项必须执行4.1的“冲突不可并行门”，不能只检查单一工具是否还能使用。

任何答案只能靠后台板补全时，Reader仍判失败。审稿人只定位最早责任层，不向正文临时发明解释。修订必须回到L4、L4.5或单话源，随后重新合成Reader并复审。

另外增加三条通用硬问：

8. 若安全规则、远程命令或紧急覆盖制造危机，正文是否明确显示签发者、推送席、作用对象、正常权限和被越过的边界；
9. 若事故或救援依赖某人位于驾驶舱、操作艇、舰内或设施中，正文是否完整显示其最后一次离开、返回、入席与锁止，而不是让状态表代替人物移动；
10. 若地面牵引、舰载短滑、主推进等不同系统由不同角色控制，是否使用不同的玩家可见称呼和动作，责任链能否一眼区分。
11. 任何舰艇、操作舱、滑架或巨体发生关键位移时，正文是否明确当前动力或承载来源、操作者、控制席、独立移动能力与停机方式；“已经移到”不能替代动力链。
12. “接住”是否只是救援中段；合并载荷如何止坠、返回稳定地面或回收范围、卸力并固定人员，是否形成一条完整受力闭环。
13. 破拆、开盖、切舱或夺取设备以后，压力边界与适航状态是否仍成立；若保留飞行，正文必须让玩家看见被打开的是外置非增压舱还是主压力壳。
14. 若一条物理链只有后台物理板讲得通，而Reader把推进、受力或恢复动作省略为结果句，该Reader仍判失败。
15. 上一场结束时仍供能、连接、可达且胜任的载具、吊机、绞盘、通道、武器、操作者和控制席，是否继续被视为下一场的可用方案；若改用更危险、更昂贵的办法，正文是否明确显示这些简单方案为何被摧毁、断电、脱钩、阻挡、调走、来不及重接或超出能力范围。
16. 关键物件使用“送回、重新装上、再次出现”等回归动词时，前文是否真实发生过离开；救援装置是否沿用已经建模的同一对象，还是临时换名制造了不存在的新资产。
17. 本章预告某支援机、人物或物件“下一站到场”时，后续章的真实出发地、目的地与抵达方式是否一致。
18. 无名群体获得姓名后，集合代词、席位呼号和性别指代是否重新检查；承担情绪后果的人是否在高潮或回收处再次被叫到名字。
19. 单话开放资料是否保留在Episode Reader，而跨章连续阅读稿是否默认折叠，避免每话结算反复打断连读。

### 6.1 声线与去AI味的语义硬问

声线审查除隐名、互换、听众、知识、动作、沉默和朗读测试外，必须逐项回答：

1. 正文是否反复用“不是、没有、不等于、不替谁”替读者排除误解，而没有给出正面的载体、位置、动作和后果；
2. 冲突双方是否都像作者一样完整陈述立场，句长、礼貌程度、沉默、打断和身体任务是否真正不同；
3. 关系状态是否由旁白宣布“和好/没有和好、靠近/疏远”，而不是由触碰、躲避、误会、照料、离开和选择让玩家感到；
4. 战斗是否被模块、例外和微动作写成操作手册；玩家当下真正需要理解的目标、反转、大动作和人物选择是否清楚；
5. 资料卡和开放情报能承担的完整排除项，是否被错误塞回戏剧正文。

这些问题不能由正则脚本自动判定。任何一项为“是”且影响关键场面时，`human_voice_review`不得封存。

### 6.2 可测试的最小硬门

这些门只验证“产物是否属于本轮且审查范围完整”，不替代人的剧情判断。

1. **章节Reader精确合成。** `assemble_v35_chapter_reader.py`只读取manifest中的`episode_eNN`路径，按`stage_order`合成，并把每个源文件名与SHA写入Reader头部。目录中存在的旧稿、备份稿和额外文件不会被glob进来；Episode编号不连续、路径越出本章Episode目录或源文件缺失时立即阻塞。
2. **Packet不得空过。** `check_v35_chapter_packet_consistency.py`在没有任何`passed/generated`产物时必须失败。`--allow-noncurrent`只允许检查失效文件的库存形状，输出明确标为`inventory-only`，不能作为封存证据。
3. **前章联合指纹。** C02以后封存`series_alignment`时，Story Chain自动把前章`chapter_reader + state_ledger + user_acceptance`的联合SHA写入现有`notes`字段：`predecessor_fingerprint=<sha256>`。三者任一内容或封存哈希变化，后章对齐卡即判陈旧，必须使其失效并重新对齐；不新增表格。
4. **跨章风险候选扫描。** `check_v35_reader_continuity.py`扫描当前Reader及此前已验收Reader，输出稳定的风险ID、文件、行号、摘录和原因：
   - `FIRST_SCOPE`：第一次、首次、从未等作用域声明；
   - `RELATIVE_TIME`：昨天、今晚、次日、破晓等相对时间；
   - `ORPHAN_EVIDENCE`：没有可见产生或取得过程的残骸、残片、样本、证物；
   - `OBJECT_RETURN`：损坏、移走或离场对象的恢复与返回；
   - `SPACE_TRANSITION`：抵达、返回、登舰、离舰、停靠、起飞等空间变化。

   扫描结果是审计候选，不是禁词表。出现候选不会自动判错；审稿人必须结合前文确认、豁免或返修。
5. **Reader因果回执绑定。** `reader_causal_audit`必须在正文头部记录：

```text
Audit-Scope: reader_causal_full
Reader-SHA256: <当前章节Reader>
Prefix-SHA256: <C01至当前章Reader序列>
Risk-Scan-SHA256: <本次风险扫描>
Result: PASS
Open-P0: 0
Open-Blocking-P1: 0
```

Reader、前缀或扫描任一变化，旧回执立即失效；部分抽查、开放P0或阻塞P1不能封存。

回执H1必须同时包含当前章号与Registry中的当前章名；正文必须声明只读Reader边界，并逐项覆盖时间/航程、人物和机体位置、尺度受力、驾驶与远控、证据来源、安全失效与更简单方案、跨章首次/返回口径。只写“物理审查通过”或借后台板补答案的文件，不得封存。

预审命令：

```bash
python3 scripts/check_v35_story_chain.py \
  --manifest docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/Cxx-story-chain.tsv \
  --before-stage reader_causal_audit
```

该命令会输出风险候选和本轮必须使用的回执头。完成审稿后，再用常规`--record-stage reader_causal_audit --record-status passed`封存；封存时重新计算并核对全部SHA。

## 七、容量事务

当前话数上界只存在于`V35-upper-layer-registry.tsv`的L3行。Skill、提示词和脚本不得写死数字。

调整话数前：

1. 登记一份说明真实场面容量、拆并理由、上下游影响的迁移文档；
2. 若`first_read_causal_audit`或其下游已封存，先使该阶段失效；
3. 运行`resize_v35_story_chain.py`，同时传入章节、新话数、迁移文档和理由；
4. 若新总量突破上界，同一命令传入`--new-ceiling`；
5. 脚本一次提交上位Registry、章节Registry、manifest与看板，任一步失败则全部回滚。

Canon出现`V35L4-CxxExx`场景时，也必须先与新话数对齐，否则事务拒绝提交。

## 八、用户验收门

用户明确认可当前故事文件后，才能运行：

```bash
python3 scripts/record_v35_user_acceptance.py \
  --chapter Cxx \
  --evidence '<用户明确决定>' \
  --scope '<被认可的文件与边界>'
```

通用`--record-stage`、内部审稿、批次运行、用户沉默、旧版本认可都不能生成验收回执。后续章初始化会检查此前所有已建立manifest的章节，不只检查相邻上一章。

- 合同迁移器只在新阶段第一次加入manifest时补录回溯证据；阶段一旦存在，就保留其当前`passed / invalidated / missing`状态。旧回执不能让已经失效的新稿重新获得验收。
