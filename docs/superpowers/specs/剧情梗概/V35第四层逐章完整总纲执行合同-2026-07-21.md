## 一、这一层解决什么

第三层回答“全剧为何这样发生”；第四层回答“每一章具体怎样成为一段完整、可玩、可读、可继续的机器人大战故事”。

本层不写完整台本，也不直接生产Episode Reader。它需要把母盘中每章三至五段的结构说明，发展为足以指导后续逐话写作、关卡设计、角色演出和资产准备的完整章级总纲。

## 二、每章必须完成的创作工作

1. **章级对齐与Canon收敛。** 读取上一章实际输出、全剧长线、当章机体/IP候选和后续保留峰值，说明本章为什么必须发生在此时此地；随后比较Current Canon与L1-L3、本章对齐卡、上一章真实输出。稳定事实继续保留，只靠旧Reader、Runtime或资产合同自我引用的角色、机制和未来回收义务必须先迁入Candidate/History并完成Canon校验，不能带入预生产。
2. **戏剧发动机。** 锁定谁最想得到什么、谁主动阻止、为什么不能和平解决、人物与机体分别会失去什么，以及章末不可逆变化。
3. **章级档位与预生产模型。** 初始化manifest前，先在`V35-chapter-registry.tsv`将本章定为`light`、`standard`或`heavy`。轻量章复用既有人物、空间、能力和控制关系，预生产可压缩但不能省阶段；标准章允许引入一项重要新场所、能力、敌方规则或控制链；重量章涉及新巨构、多尺寸机体、变形、机魂空间交叉、新能力首用、三方混战或地形决胜，必须补尺度轮廓、战场灰盒、控制链和四至八格奇观草图。随后把本章会使用的人物、主体、机体、敌人、关键机制、物件、空间、可见大动作和预演资产编译成一份可删除的章级模型。每项必须有来源、控制者、位置/尺度、允许与禁止动作、玩家可见证据、章末状态和复用价值。章纲原则上不得临时新增承担因果、胜负、身份或长期伏笔的专名；确需新增时，先提交短变更票并更新模型。具体方法读取`2026-07-23-chao-gag-chapter-preproduction-model-v1.md`。
4. **章节导演板。** 使用已经通过的预生产模型锁定代表路线的场景链、人物欲望、误解与破裂、高光的前因后果、信息由谁在何时得知、场景数量与普通观众第一次观看时的理解顺序。每个关键场面必须标注`玩家可见证据`、`暂定演出载体`、`当场必须理解/允许疑问/作者后台真相`、`最低资产需求`和所引用的预生产项，并通过旁白删除测试。导演板同时按话建立`本次开放资料`揭示矩阵，区分玩家必须理解、可以怀疑、必须隐藏、资料状态、可见来源、当前可信度与未来修订窗口；资料页只能整理已演出的知识，不能替故事补因果。导演板必须把高光留给人物完成，不能让日志、权限、倒计时或装置替人物作出决定。具体门槛读取`V35游戏叙事演出语法基线-2026-07-22.md`与`2026-07-26-chao-gag-current-open-information-system-v1.md`。
5. **战斗与玩法预案。** 在完整总纲前为每话写清ADV、探索、SRPG、战中演出、舰内生活与结算的先后；每场主要战斗只锁定一句人话目标、地图轮廓、一个主要可见规则、两至三个大画面、改变结果的人物选择和不可逆输出。机体、空间和大动作必须引用预生产模型，不能在预案里另造。此阶段不写回合数、数值和全机逐步走位。不能从战棋俯视、明确UI或短过场中看懂的关键动作，必须简化、移到ADV或删除。
6. **场面与能量波形。** 设计章内开场抓力、升级、转折、大败或大胜、情绪释放、生活呼吸和结尾发动；不以平均字段代替故事。若一话同时要求玩家追踪多层地形、人类与巨机实时动作、多个控制系统和大段前情说明，应拆话或减少事件，而不是补更多术语。
7. **逐话切分与容量裁决。** 每话拥有自己的目标、冲突、战斗或主要玩法、角色动作、机体动作、关系变化和下一话钩子。话数由容量决定，可以调整第三层候选数，并记录对全剧预算的影响。高密度章还必须在章级对齐卡或导演板中明确每话的主要高潮、独立反转、关系转折、世界揭示和战后余波；若同一话包含两个各自拥有铺垫、选择、胜负和不可逆结果的高潮，默认拆话，除非它们在同一玩家目标中连续完成且中间没有自然存档点。不得为了守住旧话数，把战争胜负、人格诞生、关系决裂和下一章发动压成同一段结算。
8. **机器人大战兑现。** 明确主力机、驾驶员、首登/首控/加入/升级/离队、宿敌、名场面与台词锚、具体机械动作、玩家永久获得和敌方学习。主要战斗优先保留能在地图、Cut-in或PV中一眼看懂的大动作；微小错位、微妙开缝和厘米级工程操作不能承担高潮。
9. **人物与关系。** 纪存、七海、白鸢及群像必须做大决定并承受可见后果；成人关系通过欲望、身体距离、嫉妒、误解、照料、争吵、互救和共同生活推进，不靠权限小动作代替感情。Reader不得用“算我的”“我替你背”“你可以X但别替我Y”“今天先X但别Y”制造强硬或深沉；先写人物抢下的动作、身体反应和具体听众，再决定他当场会说哪半句。任何“道歉、修复、原谅、仍然留下”都必须能追溯到前文已经发生的伤害或误解。
10. **玩法与制作。** 区分ADV、探索/多玩法、SRPG、战中剧情、舰内生活和结算；检查地图、Rig、场景和UI复用是否真实可做。人物尺度与巨机尺度可以交叉剪辑，但不得要求玩家在同一战棋阶段同时操作普通人、巨机和多层移动建筑来理解主冲突。
11. **常识语言与术语预算。** 每个新机制先用两句日常语言解释；若仍说不清，就回到机制重构。完整总纲只保留确有辨识度的地点与装置名，普通停机坪、运输机、服务器、实体密钥和生产线不得为了显得硬核另造“廊、槽、架、根、锚、语法”。内部技术名可留在制作附录，不得成为读懂剧情的前置课。
12. **分支与连续性。** 写清主路线、即时差分、未选路线执行者、长期结果、下一章输入和未来不得提前消费的内容。
13. **尺度与称谓。** 任何巨体交战、母舰泊位、运输和巨构动作都必须读取`v35_major_body_scale_interaction_baseline_v1.tsv`，写清三轴尺寸、质量级、支点与反力；地外敌人首登及后续称呼必须读取`v35_external_threat_designation_protocol_v1.tsv`，区分未知接触、正式编号、作战呼号、地方俗称和自称。两张表当前是Candidate创作基线，不得在单章内临时改尺寸或凭空赐予神话真名。
14. **游戏可见性阻断。** 若删去梗概旁白后，玩家无法从操作、画面、机体动作、人物反应和最低UI复述当前因果，该场面不得进入完整总纲。第四层只锁承载形式与信息边界，不写具体机位、秒数、完整台词或数值；总纲通过后另做章级演出承载规划。
15. **首读因果盲审。** 完整总纲写成后，先只把总纲、上一章精简退出状态、本章一句话发动机和预定退出状态交给独立读者；不得同时附送导演板、物理辩护、机制词典或作者解释。盲审必须复述人物欲望、冲突起点、行动理由、站位与控制权、胜负因果、不可逆结果和下一章发动。任何一项只能靠作者补充说明才能成立，必须回到最早责任层修改并重审；盲审通过前不得拆逐话表、做L4.5或写Reader。

## 三、每章交付物

1. `Cxx-章级对齐卡.md`：上游输入、当章职责、未来保留、退出状态。
2. `Cxx-章级预生产模型.md`与`Cxx-预生产实体动作表.tsv`：一份可读灰盒加一张机器表，合并人物、机体、敌人、机制、空间、动作和预演资产，禁止拆成多套重复清单。
3. `Cxx-章节导演板.md`：代表路线场景链、信息揭示、人物高光链、关系破裂与回收条件、场景预算、通俗用语表，以及关键场面的玩家可见证据、暂定载体、信息边界、最低资产、预生产项引用与旁白删除测试；同一文件内包含逐话`本次开放资料`揭示矩阵。导演板必须先于总纲通过。
4. `Cxx-战斗与玩法预案.md`：逐话制作层顺序、战斗人话目标、地图轮廓、可见规则、大画面、角色选择、不可逆输出与资产复用。预案必须先于总纲通过。
5. `Cxx-物理因果与人物站位板.md`：只在manifest标记为必需，或章节涉及巨构、多驾驶、多身体、变形与跨尺度动作时建立；用于否决矛盾和删减动作，不得生成Reader术语或首次创造装置。
6. `Cxx-完整剧情总纲.md`：可连续阅读的章级故事，不写成字段报告，也不依赖上述作者板才能看懂。
7. `Cxx-首读因果盲审.md`：只读故事层后复述欲望、行动、空间、控制、胜负、结果与下一章发动；记录阻断、根因、回迁层和复审结论。
8. `Cxx-逐话结构表.tsv`：逐话目标、类型、战斗/玩法、机体/IP、人物关系、分支、永久结果和钩子。
9. `Cxx-机体人物分支状态账.tsv`：当章前后位置、损伤、拥有、关系、敌方收益和未回收线索。
10. `Cxx-四视角章审与问题账.md`：制作、剧作、机器人文化和目标玩家四席只举证问题，由单一主笔统一修改。四席必须分别回答第一次观看是否看懂、游戏是否能演出、高光是否有前因、专有名词是否压过人物。
11. `C01-Cxx累计连续性回执.md`：每章完成后连读到当前章，检查因果、重复解法、人物波形、机体/IP生涯和高潮透支。
12. `Cxx-章级演出承载规划.md`：完整剧情总纲获准后、Episode Reader开始前制作，排定玩家实际经历顺序、制作层切换、动画峰值、战中通讯、地图事件、可选生活场和资产复用。
13. `V35.9/rebuild/reviews/Cxx/Cxx-人类声线语义审查-v1.md`：章节Reader合成后，对活人语气、有限认知、听众、动作、关系表演和作者借嘴作独立语义检查；确定性lint不能替代它。
14. `V35.9/rebuild/reviews/Cxx/Cxx-用户创作验收回执.md`：仅在用户明确认可当前故事版本后，由专用命令生成并封存；内部PASS、批次完成、用户沉默和旧版本认可都不能替代。
15. `V35.9/rebuild/manifests/Cxx-story-chain.tsv`：机器生产状态与内容哈希。文件存在不等于通过；只有`passed`与`generated`能解锁下游。上游改动、缺项或哈希失配时，演出承载、Reader、章节合成、用户验收与下一章必须自动阻断。

上述文件是当前Story Chain的标准职责模板。已经进入V35机器生产链的章节不得自行合并、改名或省略manifest中的阶段；轻量章通过缩短正文和引用唯一事实所有者降低成本，而不是另造一种目录结构。章级临时研究、双盲试写、旧高光提炼和回滚证据只能进入本章`support/`或`_history/`，不得与标准工件并列在当前阶段目录。标准工件之间只引用，不复制同一事实的整段解释。

## 三点五、五章一致性门

Story Chain只证明顺序、依赖和哈希，不能证明五章真的按同一种创作方法完成。每次封存L4、L4.5、章节Reader或章审前，必须再运行章节包一致性检查：

```bash
python3 scripts/check_v35_chapter_packet_consistency.py \
  --chapter Cxx \
  --strict
```

检查至少覆盖：

- Registry、manifest、标准工件与Reader使用同一章名和话数；
- 对齐卡包含章发动机、能量波形、未来保留与章末输出；
- 预生产包含人物、机体/敌人、能力/控制、空间/尺度、大动作和资产复用；
- 导演板包含观众承诺、场面链、人物关系、玩家可见证据和人类声线门；
- 战斗预案包含人话目标、地图、可操作单位、阶段变化、大画面与不可逆结果；
- 物理板包含时间、站位、尺度、控制权、因果与章末物理状态；
- 演出规划包含实际游玩顺序、承载形式、前台信息预算、逐话安排、开放资料与Reader门；
- 章审明确检查连续阅读、人物表演、人类声线、游戏可玩性与前后连续性；
- 当前阶段目录不存在未登记的“第二套正文”或游离过程稿。

一致性检查只验证职责覆盖，不给剧情质量颁发PASS。高密度、人物欲望、机战爽点和关系波形仍由人工审稿负责。

## 四、执行顺序

1. C01-C03保留已经成立的Working故事事实，但不享有流程例外。它们和后续章节一样，必须依次建立章级对齐、预生产、导演/战斗/物理板、完整剧情总纲、演出承载与逐话Reader；旧Reader只能作为重建输入，不能反向替代缺失的上游。
2. C04作为重量章反向编译样本，先补章级预生产模型并关闭其中的实体、控制权和动作阻断；不以事后物理板替现稿辩护。
3. C04经回归确认后再用同一方法回放C05；此后仍一章一闭环，不批量生成全剧。
4. 每章必须依次通过`章级对齐卡 -> 按档位完成章级预生产模型 -> 必要的角色沙盘 -> 章节导演板（含游戏可见性门） -> 战斗与玩法预案 -> 档位要求的物理因果板 -> 完整总纲 -> 首读因果盲审 -> 逐话结构/状态/四视角/累计连续性闭合`。导演板、预案与物理板只能调用或否决预生产项，不能首次创造关键实体、权限、空间或动作。
5. 首读因果盲审通过后，才完成`章级演出承载规划`，再拆成下一层Episode Reader；逐话Reader仍按一次一话执行。
6. Episode Reader与台本阶段按`表演与对白简报 -> 单一主笔初稿 -> 角色声线分离 -> 单话连续性 -> 章节Reader合成 -> 人类声线语义审查 -> 确定性lint -> 章节总审`执行。去AI味不能只靠正则，也不能用语气词、方言、错字或括注掩盖上游问题；具体读取`2026-07-23-chao-gag-human-voice-dialogue-gate-v1.md`。
7. `chapter_review`只表示内部生产审查完成，不表示用户喜欢，也不能解锁下一章。只有用户明确认可当前版本后，才可运行`python3 scripts/record_v35_user_acceptance.py --chapter Cxx --evidence \"用户原话或可核验摘要\" --scope \"获准范围\"`；此前所有已经建立manifest的章节中，只要有一章尚未验收，后续章节初始化即保持冻结。
8. 每次开始写总纲、演出承载、单话Reader、章节合成或下一章前，必须先运行对应`story-chain`目标门。每项通过后用当前文件哈希封存；不得手填`passed`，不得用“事实早已Working”“旧稿用户认可”或“已有下游文件”跳过。
9. 话数不得写死在Skill、提示词或检查器里。当前上界只读取`V35-upper-layer-registry.tsv`的L3行。调整本章话数时，先废止`first_read_causal_audit`及其下游，再以已登记的迁移文档和理由运行`resize_v35_story_chain.py`；若总量突破当前上界，同一事务必须显式传入新的L3上界。禁止分别手改Registry、manifest、Canon和Reader文件。
10. 外部模型或人工审稿进入返修前，先做事实分诊。每项意见必须指出当前文件、当前章节/话次和正文证据，并分为`valid`、`valid_but_wrong_layer`、`already_present`、`stale_source`、`mislocated`或`invalid_test`。章节号错误、建议内容已存在、把自己的改写当成原文、角色性别/控制权与Current资料冲突的意见，不得直接进入修改清单；有价值的审美判断可以另行吸收，但不能借错误事实证明。

## 五、验收标准

一章通过，不是因为字段齐全，而是因为玩家能清楚回答：这一章我为什么继续玩、我驾驶了什么、谁做了令人记住的选择、哪段关系真的变了、哪一个机器人动画式画面能进入PV、我永久获得了什么、敌人又学会了什么，以及下一章为什么已经不可避免。

提交前必须先做三道观众与制作阻断：不了解作者板的普通读者能否只读总纲复述主因果；删掉梗概旁白后，玩家能否从操作、画面、人物反应与最低UI理解关键转折；关卡、美术与演出能否用既定制作层表达关键动作。若答案是否，不能把解释移进对白，也不能增加装置名，必须回到导演板或战斗预案删减、拆话或改场景。

最后再做三项机械复核：人类声线确定性lint与真实坏句fixture；巨体三轴尺寸、质量与反力检查；敌方编号、呼号与命名来源检查。机器无命中不等于台词自然，核心关系场仍须通过隐名、互换、听众、关声和朗读测试。命中问题时不能只换同义词或改一个数字，必须回到人物动作、场面因果和信息揭示重写。

高密度章另做一次“容量而非字数”复核：按场面列出玩家目标、独立高潮、不可逆决定、关系质变、主要新机制和自然存档点。一个段落写得长不等于容量足够，一个话次写得短也不等于负担轻。若主要高潮互相争夺余波时间，先拆话或移位，不用资料卡和章末结算替它们收尾。
