# Cxx 第四层章包与演出门模板

> Status: `working_production_template / non_canon`
>
> 用途：后续每一章从第三层结构母盘进入第四层完整总纲时使用。模板负责阻断“梗概作者能解释、玩家却看不见”的场面，不替代创作，也不要求每章平均填满相同篇幅。

## 零、机器状态先于写作

先运行`python3 scripts/report_v35_layered_pipeline.py`，确认本章是全剧看板列出的当前唯一活动点。若前章尚未通过`advance`，不得初始化或推进本章。

开始本章前，先复制并填写：

```text
docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/Cxx-story-chain.tsv
```

它是本章唯一生产状态，不得由README、进度说明、文件是否存在或作者口头判断替代。每个上游产物完成审查后，用命令封存当前文件哈希：

```bash
python3 scripts/check_v35_story_chain.py \
  --manifest docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/Cxx-story-chain.tsv \
  --record-stage <stage_id> \
  --record-status passed
```

自动生成物使用`generated`。不得手填`passed/generated`，不得先写下游再补上游。上游文件封存后发生改动，哈希失配即视为整条下游失效；下游文件可以保留为重建输入，但必须标为`invalidated`。

五个生产入口必须分别通过：

```bash
# 开始完整剧情总纲前
python3 scripts/check_v35_story_chain.py --manifest <manifest> --target write-outline

# 开始章级演出承载规划前
python3 scripts/check_v35_story_chain.py --manifest <manifest> --target write-performance

# 开始每一话Episode Reader前
python3 scripts/check_v35_story_chain.py --manifest <manifest> --target write-episode

# 合成章节Reader前
python3 scripts/check_v35_story_chain.py --manifest <manifest> --target assemble

# 进入下一章前
python3 scripts/check_v35_story_chain.py --manifest <manifest> --target advance
```

任何命令失败，立即回到它报告的最早缺失或失效阶段。既有Reader、已经成立的Working故事事实、用户曾认可过的旧稿，以及C01-C03的历史状态均不构成例外。

## 一、生产顺序

```text
本章story-chain manifest
-> 全剧结构母盘切片与上一章真实输出
-> 章级对齐卡
-> 章级预生产模型
-> 必要的角色有限认知沙盘
-> 章节导演板
-> 战斗与玩法预案
-> 必要时的物理因果与人物站位板
-> 完整剧情总纲
-> 逐话结构表 / 状态账 / 四视角章审 / 累计连续性复读
-> 用户或生产门审定
-> 章级演出承载规划
-> 逐话 Episode Reader
-> 关键场表演与对白简报
-> 台本初稿
-> 声线分离 / 人类声线与去AI味门
-> 分镜 / 地图事件 / 战斗设计 / 资产任务
```

缺少任一上游门时，停在当前层修正。不得把总纲解释句拆成人物对白、终端百科或战中通讯，冒充已经完成演出设计。

## 二、章级对齐卡

只提取本章真正需要的全剧切片：

- 上一章交来的事件、欲望、伤势、关系、机体、资源、阵营行动与分支状态；
- 本章必须兑现、可以推进、只能预显影、必须留给未来的内容；
- 本章表层发动机、深层压力和章末不可逆结果；
- 主要机体/IP生命周期、玩法升级与永久奖励；
- 本章结束为何必然发动下一章；
- 若突破旧总纲，迁移哪些后续章节、峰值、Roster或谜团阶梯。

对齐卡不是旧大纲摘抄，也不是六层机制配额表。

## 三、章级预生产模型

章引擎通过后，先建立一份`Cxx-章级预生产模型.md`与一张`Cxx-预生产实体动作表.tsv`。两者只回答本章有什么、能做什么、在哪里以及是否值得做资产，不提前写场面正文。

机器表用同一个`item_type`字段容纳：

- `character / subject`：本章欲望、有限认知、权限、禁区、主动动作和退出状态；
- `mecha / enemy`：驾驶、机魂、AI、导航、武装控制、尺度、标志动作、限制和敌方观察方式；
- `mechanism / object`：输入、处理、输出、验证、接受者、执行者、可见结果、位置与代价；
- `space`：普通名称、连接关系、尺度、可进入者、移动时间、支点与SRPG阶段；
- `action`：一眼可懂的大动作、真实执行者、前提、反制、结果与禁止替代；
- `previs_asset`：只为验证尺度、空间、控制权和大轮廓而制作的低精度预演。

### 生成前七门

1. 具名关键实体已登记。
2. 每个动作能指出提案、验证、接受、操作和执行身体。
3. 新能力已固定输入、输出、限制和代价。
4. 巨体移动、变形、坠落和跨场能落在灰盒上。
5. 每场高潮至少有一个远景可读的整机动作。
6. 一次性新专名证明了画面、玩法、情绪或后续复用价值。
7. 同一战斗阶段只有一个主要目标和一个核心可见规则。

### 视觉预演触发

- 轻量章：既有地图引用、人物站位和场面顺序即可。
- 中量章：追加俯视灰盒、尺度轮廓、三至四格动作草图和最低资产。
- 重量章：出现新巨构、多尺寸机体、母舰/机体变形、驾驶舱/机魂/现实战场交叉、新能力首用、三方以上混战、地形决胜或高成本Boss时，必须先完成尺度板、俯视与剖面灰盒、控制链、四至八格奇观板和SRPG阶段切换图。

预演是逻辑与轮廓草图，不是正式美术生产。它的任务是尽早否决“文字能讲、画面站不住”的设计。

### 写作中的新增项

完整总纲原则上只能调用已登记项。若写作时出现会改变因果、胜负、能力、控制权、空间或资产的新灵感，先暂停并提交：

```text
新增项：
现有元素为何做不到：
玩家能看到什么不同：
改变哪条因果：
后续是否复用：
资产增量：
裁决：采用 / 合并 / 普通名词 / 拒绝
```

裁决采用后先更新预生产模型，再继续写纲。生活细节、表演和不改变规则的笑点不需登记。

## 四、章节导演板

导演板先回答观众怎样经历故事，再考虑术语和装置。每个关键场面填写：

| 字段 | 必须回答 |
| --- | --- |
| 场面与观众目标 | 玩家进入此场想完成什么、担心什么或想知道什么 |
| 人物欲望与阻力 | 谁主动要什么，谁为何阻止，不能和平解决的原因 |
| 玩家可见证据 | 屏幕上具体看见、听见、操作或比较到什么 |
| 暂定演出载体 | 舰内自由活动、ADV、探索、地图事件、SRPG、战中通讯、Cut-in、短动画、UI、经营/小游戏或结算 |
| 当场必须理解 | 不懂便无法继续当前剧情或玩法的信息 |
| 允许留下疑问 | 此刻只需觉得异常、危险、可疑或有情感意味的部分 |
| 作者后台真相 | 角色与玩家尚不能知道、不得泄漏进对白的答案 |
| 最低资产需求 | 人物、机体、背景、状态差分、UI及必要的一次性资产 |
| 前因与后果 | 高光此前由什么铺垫，之后改变谁的选择、关系或局势 |
| 旁白删除测试 | 删掉作者解释后，玩家能否复述原因、行动和结果 |

必须过门的场面包括：章级发动机首现、新机制/能力首次生效、主要敌人改变战场、关系破裂或修复资格、分支选择、主要机体首登/首控/升级/离队、章级高潮和下一章发动器。

若纸张、模型、分镜、名字、合同或数据越过工程验证与执行身体直接改变现实，退回机制重构。若关系只能由旁白宣布，退回人物场面。若第一次观看需要先学一组新造名词，退回通俗表达。

导演板中的关键场面必须引用预生产项。若导演板第一次介绍一台机体尺寸、一种权限或一个决定胜负的装置，退回预生产层。

## 五、战斗与玩法预案

每场主要战斗只先固定能被游戏表达的骨架：

| 项目 | 必须回答 |
| --- | --- |
| 一句人话目标 | 谁为了什么，在什么空间里，必须阻止谁完成什么 |
| 玩家实际操作 | 本场是SRPG、探索、追逐、调律、经营还是复合玩法 |
| 地图轮廓 | 俯视图能一眼辨认的主方向、关键地形和尺度 |
| 可操作单位与操作者 | 驾驶、导航、武装、自主行动和支援分别归谁 |
| 主要可见规则 | 一个能由单位、地形、目标或少量UI直接表现的核心规则 |
| 阶段变化 | 什么人物决定或敌方行动改变目标、敌我、地形或胜负逻辑 |
| 大画面 | 两至三个可进入PV、漫画跨页或关键Cut-in的整机动作 |
| 不可逆输出 | 人物、关系、机体、地图、资源、分支或敌方获得什么状态 |
| 制作边界 | 复用资产、新增资产、需转短动画的动作与应删除的复杂度 |

此阶段不写精确回合数、数值和全机逐步走位。厘米级开缝、复杂受力链、多层同步微操和必须连续近景才能理解的动作不得承担SRPG高潮。

战斗预案中的单位、空间和标志动作必须来自预生产模型。预案负责组合玩法，不负责临场扩建世界。

## 六、物理因果与人物站位板

本板在导演板和战斗预案之后建立，只验证已经选定的大动作：

| 场面 | 时间窗口 | 人物/机体位置 | 谁控制什么 | 尺度、伤势与负荷 | 信息来源 | 为什么不能用更简单办法 |
| --- | --- | --- | --- | --- | --- | --- |

它可以否决动作、要求拆场或简化机制，不能反向发明新装置、新地点、新权限或新剧情。若确实发现缺项，退回预生产模型走新增票。正文若必须搬运本板术语才能看懂，说明场面仍未完成第四层。

## 七、完整总纲与章审

完整总纲必须能独立连读，不依赖上述作者板。完成后同步：

- `Cxx-逐话结构表.tsv`；
- `Cxx-机体人物分支状态账.tsv`；
- `Cxx-四视角章审与问题账.md`；
- `C01-Cxx累计连续性回执.md`。

四视角分别检查：

- 编剧：因果、人物欲望、关系波形、高光前因与章间发动；
- 机器人文化：机体生命、IP情绪与名场面语法、机战爽点；
- 游戏制作：操作目标、地图可读性、载体切换、资产复用与成本；
- 目标玩家：第一次观看是否看懂、是否好玩好磕、是否想继续。

四席只提交症状、证据、根因和需重写的场面，由单一主笔整合。

## 八、章级演出承载规划

完整总纲通过后，另建`Cxx-章级演出承载规划.md`，按一次真实游玩顺序排列：

```text
舰内自由活动 / 可选事件
-> ADV
-> 探索或副玩法
-> 地图事件
-> SRPG阶段
-> 战中通讯 / Cut-in / 短动画
-> 战后ADV
-> 结算与状态变化
```

规划必须标明每段的玩家目标、信息证据、载体切换、可跳过性、动画峰值、ADV长度级别、地图复用、最低资产和下游交接。此层仍不写完整台词、逐镜机位、镜头秒数、敌军数值或最终资产技术规格。

没有通过的演出承载规划，不得启动本章Episode Loop或逐话Reader。

## 九、人类声线与台词门

第四层不写完整台词，但总纲中的对白样句、Episode Reader和后续台本都必须读取`2026-07-23-chao-gag-human-voice-dialogue-gate-v1.md`：

1. 上游因果、欲望和执行链先通过，不能用口语化掩盖设定错误。
2. 关键场先做表演与对白简报，再由单一主笔写初稿。
3. 按角色逐人做声线分离，再做整场人类声线审查。
4. 运行隐名、互换、听众、关声和朗读测试。
5. 机器扫描责任结算腔、否定式作者辩护、技术Cookbook和退化，只作工程证据。

命中问题时不靠增加`啊、呢、吧`、省略号、方言、错字或“若有所思”括注修复。

## 十、第四层完成判据

机器判据优先：

1. `write-performance`门通过后，才可认为完整剧情总纲的全部上游已封存；
2. 完整剧情总纲封存为`passed`且`write-episode`门通过后，才可启动Episode Reader；
3. 所有单话Reader封存后，必须由带`--manifest`参数的章节合成器生成章节Reader；
4. 章节审定封存后，`advance`门通过，才可宣布本章闭章并进入下一章。

机器门只证明顺序和产物未被静默改写，不代替内容验收。内容还必须满足以下两组判据。

普通玩家只读完整总纲，能够回答：

1. 这一章谁想得到什么，为什么非战不可；
2. 玩家主要操作了什么，每场玩法为什么改变剧情；
3. 哪台机体做了什么一眼能懂的大动作；
4. 谁作出不可撤销的选择，哪段关系真的改变；
5. 章末永久获得和永久失去分别是什么；
6. 敌人或世界学会了什么；
7. 下一章为什么已经不可避免。

制作人员只读预生产模型、导演板、战斗预案和演出承载规划，能够判断需要哪些地图、角色、机体、状态差分、UI、短动画和Cut-in。任一方仍需作者口头解释，章包退回相应上游层。
