# V35章节生产操作手册

> Status: `working_production_interface / non_canon`
>
> 用途：规定从第三层结构母盘进入第四层、演出承载与Episode Reader的唯一操作入口。创作者不需要凭记忆判断下一步，只执行本章manifest报告的下一合法阶段。

## 一、默认推进单位

默认一次只推进一个机器阶段。用户明确要求“完成本章第四层”时，可以连续完成第四层内部阶段，但必须在`write-performance`门通过后停止，不自动进入演出承载或Reader。

```text
第四层：
章级对齐
-> 章级预生产模型与实体动作表
-> 导演板（含“本次开放资料”揭示矩阵）/ 战斗预案 / 必要物理板
-> 完整剧情总纲
-> 首读因果盲审
-> 逐话结构表
-> 机体人物分支状态账
-> 四视角章审
-> C01至本章累计连续性回执

第四层通过后：
章级演出承载规划
-> 单话Episode Reader
-> 机械合成章节Reader
-> Reader时间空间与物理因果盲审
-> 人类声线语义审查
-> 章节Reader审定
-> 用户创作验收
-> 下一章
```

章节初始化时同时选择生产档位：`light`复用既有实体与规则，`standard`引入一项重要新场所、能力、敌方规则或控制链，`heavy`涉及多尺度、变形、机魂/现实交叉、三方混战或地形决胜。档位只改变预制和审查深度，不改变标准阶段、首读盲审、声线审查或用户验收。

## 二、每章开始时的输入

### 固定权威输入

1. `V35六层创作生产看板.md`：全剧当前层、活动章、缺口和下一门。
2. `V35-PRODUCTION-STATUS.md`：生产口径迁移、用户裁决和历史状态日志。
3. 本章`Cxx-story-chain.tsv`：本章唯一机器生产状态。
4. `authority_manifest.tsv`及本章涉及人物、机体、地点、机制的精确Canon查询。
5. 《V35主题玩家幻想与作品体验宪章》。
6. 《V35故事定位世界冲突与全剧总发动机》。
7. 《V35世界机制与创作接口设定基线》。
8. 《V35全剧结构母盘》内本章切片与章间因果。

### 章节继承输入

1. 上一章已经封存的完整总纲、状态账和累计连续性回执。
2. 上一章章末真实人物位置、机体状态、关系结果、资源、分支和敌方所得。
3. 本章必须兑现、允许调整、只能预显影和必须保留到未来的内容。
4. 经过用户确认的旧高光或Working故事事实。

### 章首Canon收敛

完成`series_alignment`后、开始`preproduction_model`前，必须把本章涉及的Current Canon与L1-L3、本章对齐卡和上一章真实输出逐项比较：

1. 区分稳定身份/空间/世界机制、已确认故事事实、候选实现和纯历史素材；
2. 发现只靠旧Reader、Runtime或资产合同自我引用的角色、装置、未来回收义务时，先暂停预生产；
3. 能保留功能而不保留旧机制的，写进对齐卡的高光继承；没有上层职责和当前生命周期的，迁入History；
4. 更新源TSV、authority override、继承包、资产锁、图谱与生产状态后，运行完整Canon校验；
5. Canon收敛导致预生产内容变化时，必须使`preproduction_model`及下游失效并重新封存。

这一步不是要求L1-L3枚举全部细节，而是禁止下层旧实现反向创造新的上层义务。C01首批实例见《V35 L1-L3到Current Canon收敛迁移》。

### 只能作为素材的输入

- 旧Reader、旧章稿、V16/V22.10等历史高光；
- IP名场面、台词、What-if、机体候选、模型生态和成人关系素材；
- Candidate Canon与历史版本。

这些材料必须在章级对齐卡中写明“保留其什么功能”，不能凭旧文件存在直接继承整段剧情。

## 三、初始化后续章节

新章没有manifest时先运行：

```bash
python3 scripts/init_v35_story_chain.py \
  --chapter C06 \
  --episodes 4 \
  --physical-board required \
  --profile heavy \
  --chapter-title '章节暂名'
```

`--episodes`采用第三层当前候选话数，只是生产规划，不是创作配额。多尺寸机体、变形、复杂控制权、巨构空间或地形决胜章节使用`required`；普通关系或轻量过渡章才可使用`optional`。

若第四层在逐话结构表封存前决定改话数，运行：

```bash
python3 scripts/resize_v35_story_chain.py \
  --chapter Cxx \
  --episodes <新话数> \
  --migration-doc docs/superpowers/specs/<已登记迁移文档>.md \
  --reason '<为什么真实场面容量需要变化>'
```

命令会以一次事务同步L3上界、章节registry、manifest与全局看板，任一步失败便回滚。当前上界只从`V35-upper-layer-registry.tsv`读取，不得写死在Skill或脚本。若新总量超过当前上界，在同一命令加入`--new-ceiling <新上界>`。若首读盲审或更下游已经封存，先从`first_read_causal_audit`执行`--invalidate-stage`，不得在Reader阶段临时增减。C05由五话改六话的迁移依据见`V35第三层-C05高潮拆分与87话容量迁移-2026-07-27.md`。

初始化命令拒绝覆盖已有manifest。已有章节永远先读取现有状态，不重复初始化。

## 四、唯一日常入口

每次开始工作先查看全剧六层状态：

```bash
python3 scripts/report_v35_layered_pipeline.py
```

只允许推进看板列出的“当前唯一活动点”。随后运行：

```bash
python3 scripts/check_v35_story_chain.py \
  --manifest docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/Cxx-story-chain.tsv \
  --next
```

命令会输出：

- `NEXT`：唯一应处理的阶段；
- `PATH`：应创建或修订的文件；
- `READY`：是否允许开始；
- `PREFLIGHT`：动笔前命令；
- `SEAL`：审查通过后的封存命令。

动笔前执行它给出的`PREFLIGHT`。完成内容和对应审查后，才执行`SEAL`。封存保存当前SHA-256；之后静默改稿会自动使下游失效。

上游确实需要修改时，不手工改状态，执行：

```bash
python3 scripts/check_v35_story_chain.py \
  --manifest docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/Cxx-story-chain.tsv \
  --invalidate-stage <stage_id>
```

该阶段及所有依赖它的下游会一起失效，然后从`--next`重新推进。

## 五、当前批次怎样续接

C01-C03已获得用户明确认可，并有专用验收回执。C04-C05内部L4、L4.5、L5、声线语义审查与章审已经封存，但仍在等待用户创作验收；这两个内部PASS不代表用户已经认可。

当前唯一活动点由生成看板给出。C04尚未验收时，C05和C06都会显示等待C04；C04验收后，门会自动移动到C05。只有C01-C05全部取得用户回执后，C06才可选择档位并初始化。不要依据本手册里的示例章号推断当前状态。

## 六、第四层通过后怎样写Reader

用户确认第四层方向后：

1. `--next`应返回`performance_plan`。
2. 完成章级演出承载规划，封存后确认`write-episode`通过。
3. `--next`只会依次返回`episode_e01、episode_e02……`。
4. 每次只写一话；必须读取此前所有已封存单话和当前状态账。
5. 每话完成独立审查后封存，才能开始下一话。
6. 全部单话封存后，使用合成器：

```bash
python3 scripts/assemble_v35_chapter_reader.py \
  --chapter C01 \
  --title '闭馆以后，万机出击' \
  --episode-dir docs/superpowers/specs/剧情梗概/V35.9/rebuild/reader/episodes/C01 \
  --output docs/superpowers/specs/剧情梗概/V35.9/rebuild/reader/C01-闭馆以后万机出击.md \
  --manifest docs/superpowers/specs/剧情梗概/V35.9/rebuild/manifests/C01-story-chain.tsv
```

7. 对机械合成稿完成独立`reader_causal_audit`。审稿者只读章节Reader与上一章结尾，不读物理板、导演板或资料卡，检查时间、空间、尺度、站位、控制权、证据来源、安全失效链及“为何不用更简单办法”。失败项回到最早责任层修订，随后重新合成；不得修改生成Reader。
8. 物理因果盲审通过后，完成独立`human_voice_review`：逐场检查有限认知、听众、动作、角色差异和作者借嘴，再运行确定性lint。
9. 完成并封存章节Reader审定回执。
10. 把当前故事入口交给用户阅读。只有用户明确认可后，运行：

```bash
python3 scripts/record_v35_user_acceptance.py \
  --chapter Cxx \
  --evidence '用户原话或忠实短引' \
  --scope '用户认可的当前故事文件与边界'
```

11. `--target advance`通过后，才可初始化或推进下一章。批量任务、内部PASS、旧版本认可和用户沉默都不能生成该回执；任一更早章节未通过用户验收，后续章也保持冻结。

## 七、给Codex的推荐命令

### 只做C01第四层

```text
执行V35 C01第四层补全。先读取生产状态、C01 story-chain、Current Canon、
第一至第三层权威输入和C01旧稿素材。每次运行--next与--before-stage，
只处理当前合法阶段，审查通过后封存。连续推进到write-performance门通过，
然后停止，不写演出承载和Reader。保留已成立高光，但不得让旧Reader反向决定因果。
```

### 继续某章的下一合法阶段

```text
继续V35 Cxx。读取全局看板、本章story-chain和production_profile并运行--next，只完成它报告的一个阶段；
先过--before-stage，完成后做对应内容审查并seal。seal会自动更新六层看板；
只有产生新的设定事实、依赖或迁移时才更新Canon与图谱。遇到user_acceptance时停止，
等待用户明确认可，不得自动越过。
```

### 第四层已审定后写一话

```text
执行V35 CxxExx单话Episode Reader。先确认本章write-episode门和该episode阶段前置通过；
读取完整章节总纲、演出承载、状态账以及此前所有已封存单话。只写这一话，
完成表演、人类声线、机体/IP、玩法、关系和连续性审查后seal，不自动写下一话。
```

自然语言命令只是任务目标。实际是否允许执行，始终由本章manifest和机器门决定。
