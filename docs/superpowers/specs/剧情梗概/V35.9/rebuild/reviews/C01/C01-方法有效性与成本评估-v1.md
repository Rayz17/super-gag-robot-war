# C01 Story-First方法有效性与成本评估 v1

## 结论

**方法有效，但当前重型执行方式不值得原样继续。**

Story-First确实解决了旧稿最关键的问题：四话有连续因果，玩家知道在玩什么；机体通过身体动作推动剧情；纪存、七海、兜灯、唐胶和陆衡会犯错、选择并改变局面；E03断臂与E04起身具有过程、反应和余波；人口、损伤、能源、载荷与敌方学习能跨话守恒。这个收益是真实的，不能退回旧的行政摘要式写法。

但C01累计形成约83份单话/章级审稿文件，四话Episode正文约173.7KB；第一版Reader又达到76.7KB，最后必须再压缩67.7%才能恢复可读性。用户观察到本轮消耗约一半Pro周限额。以这种成本跑完C01-C12，性价比不可接受。

## 真正有效的部分

1. 先写代表周目因果脊柱，再回填合同，显著改善连续性。
2. 一话一文件与唯一原子快照，真正消除了人口、机体伤痕和分支前态漂移。
3. 玩法、关系、机体、Canon五个独立审面能抓到单一上下文容易漏掉的反例；E04双臂预算就是有效例证。
4. 章末连续Reader复读能发现单话PASS掩盖的工程化、重复句法和关系温度不足。
5. 局部补丁而非整话重写，保住了主动侧倒、撤令、断臂成桥和巨构起身等高光。

## 成本失控的原因

1. 普通Episode也反复使用接近严格章门的审稿席位，没有遵守Pipeline自身的轻量分级。
2. 同一阻断在正文、Runtime、Graybox、资产、迁移、图谱和多份审稿中重复展开，复核输入过长。
3. Reader v1直接拼接工程合同，先制造了一个14倍膨胀的中间产物，再付费做减法。
4. 每次补丁后重开过多审面；实际上只需原发现席做窄复核，其他已通过面保持锁定。
5. 检查器初版只验证字段存在，未验证最短路线与资源预算，导致人工审稿后才发现反例。

## 后续建议流程

普通一话采用：

1. 一次Story-First写作，正文先达到可读与可玩。
2. 一套本地结构/状态/预算检查器。
3. 按风险调用1至3个针对性独立审稿席，不默认全席。
4. 每个阻断只允许一次局部补丁和原发现席复核；第二次仍失败才进入问题账本。
5. 每章完成后才运行五席章门和C01至当前章连续复读。
6. Reader直接按当前v2密度生成，不再先合成工程版长Reader。

严格五席只保留给：章节闭环、关键Boss/关系破裂、巨构变形、路线大分叉和连续两轮不过的Episode。按Pipeline既有估算，这应比本轮减少约50%至75%的子Agent调用与复读上下文。

## 继续/停止判断

- **保留**：Story-First创作顺序、一话一文件、唯一快照、章末连续复读、风险定向独立审稿。
- **删除**：普通一话全席反复审、工程版超长Reader、所有补丁触发全量重验、字段存在即算预算验证。
- **当前决定**：C01完成后暂停，先由用户审读Reader v2与本评估；C02不自动启动。
