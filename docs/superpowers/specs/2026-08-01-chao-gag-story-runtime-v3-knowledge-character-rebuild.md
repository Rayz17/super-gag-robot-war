# Story Runtime v3：知识底座、人物模型与分阶段查询改造

> 状态：Production Interface Working
> 日期：2026-08-01
> 作用：改造写作知识工程，不改变任何未经迁移的剧情结论。

## 一、这次改造解决什么

此前 Runtime 把“知道得更多”误解成“在写作前编译一份更大的合同”。结果有三种失真：

1. 同一个人物被实体表、小传、声线表、全剧弧线和章末状态分别描述，作家每次只拿到其中一小块，又临时重建人物。
2. L1-L6、Canon、候选素材和旧稿被一次性压进上下文；权威等级不同的信息在摘要中失去边界。
3. Runtime 预先决定高潮、动作链和全员出站状态，主笔只剩修辞自由；审稿席又因为看过设计答案而替正文补足意义。

v3 的目标不是让知识工程替作家写故事，而是让作家在不同创作阶段，能反复查询同一个可信底座，并只得到当前决定真正需要的切片。

## 二、L1-L6如何进入创作

| 层 | 稳定职责 | 主要使用阶段 | 不应直接做什么 |
|---|---|---|---|
| L1 体验宪章 | 作品承诺、玩家幻想、气质边界 | 选案、终审 | 不规定本话动作和台词 |
| L2 总发动机 | 世界冲突、全剧目标、长期敌我关系 | 选案、章级对齐 | 不代写局部冲突 |
| H0 世界机制 | G.A.G.、机魂、白框、索引、模型与实机等事实 | 因果预演、设定核查 | 不以百科段落进入正文 |
| L3 结构母盘 | 本章位置、未来峰值、机体/IP生命周期、不可提前消费项 | 选案、章间交接 | 不把候选未来当已发生事实 |
| L4 章级总纲 | 已审定的章发动机、人物欲望、章末不可逆结果 | 场面规划 | 不替场面作者决定每个动作 |
| L4.5 演出承载 | 玩家如何看见、操作和理解关键事件 | 场面规划、制作审查 | 不提前写完整镜头和台词 |
| L5 已确认Reader | 已经发生的动作、关系和状态 | 连续性、写后复核 | 不作为通用文风范本，不继承未确认稿 |
| L6 台本/演出/关卡 | 制作层细节 | 后续生产 | 当前没有，不反向假定其存在 |

这些层不是严格串行且只读取一次。选案、实体建模、场面规划、正文写作和冷读审查都可以重新查询，但每个阶段拥有不同可见范围。

逐章L4、L4.5和L5来源由`story-runtime/production/chapter_layer_source_registry_v3.tsv`登记。Runtime不靠目录名猜“最新版”：选案阶段不读取旧章纲答案；选案后只显示可查询源索引，主笔或导演以`admitted_layer_source_ids`逐项准入。C02旧Reader只可在完成冷读后揭盲比较，不能进入重构输入。L6目前无有效输入，保持显式空置。

## 三、人物模型不是另一套Canon

人物模型是一个带来源的组合视图，由以下部分构成：

1. **稳定身份**：姓名、国籍、年龄呈现、正式登场、角色身份、不能越过的能力边界。来自Current Canon和有效美术锁。
2. **戏剧内核**：欲望、恐惧、矛盾、压力反应、亲密行为、最容易被写扁的版本。来自人物小传和声线资料。
3. **全剧弧线**：长期胜利、破裂、分舰、终局候选。明确标成Candidate Support，不能冒充已经发生。
4. **关系边**：吸引、误读、身体亲密、破裂和修复候选。按关系边单独标权威。
5. **当前状态**：只从用户已接受的Reader、章末状态账和最新合法继承包读取。
6. **场景切片**：本场位置、存在方式、知道什么、能控制什么、想得到什么、离场状态。

模型中的每个分面保留来源和权威，不把候选弧线抄进Canon实体行。作家看到的是活动切片，审稿人可以追溯到底层来源。

### 人物建模等级

- `A_SERIES_CORE`：全剧主角和长期关系核心，必须拥有完整模型。
- `B_RECURRING`：反复登场的驾驶员、机魂、阵营人物，首次承担章级功能前必须完成中等模型。
- `C_CHAPTER`：本章重要人物，在选案通过后、场面规划前建模。
- `D_LOCAL`：单场NPC只需场景卡；若第二次承担实质动作或产生长期后果，必须晋级C/B。

模型定义人物会如何抵抗剧情，而不是储存可复用金句。任何模型都不能禁止主笔提出Working迁移；迁移必须显式记录，不能在正文里静默改设定。

## 四、逐场实体存在表

`scene_entity_presence.tsv`只记录非默认或生命周期关键状态：

- `physical`：本人/本体在场。
- `remote_live`：实时远程通讯。
- `recording`：录音、录像或历史影像。
- `work_trace`：作品、签名、程序、维修痕迹等在场，本人不在场。
- `mentioned`：仅被谈及。
- `system_effect`：主体不在场，但其已部署系统产生效果。
- `not_present`：明确禁止误写为在场。

场景表仍负责“本场需要哪些实体”，存在表负责“它以什么方式存在”。没有覆盖行时，required/optional角色默认解释为`physical`；因此所有远程、录音、作品先行和禁止提前登场都必须显式登记。

## 五、Runtime v3的阶段查询

```mermaid
flowchart LR
  A["选案：L1/L2/L3 + 合法人物索引"] --> B["定向检索：H0 + 机体/IP/生态素材"]
  B --> C["实体建模门：活动人物/机体/敌人/地点"]
  C --> D["场面规划：L4/L4.5 + 当前状态 + 逐场存在"]
  D --> E["因果预演：位置/知识/控制权/简单解"]
  E --> F["正文作家：场面链 + 活动人物包 + 少量事实"]
  F --> G["冷读：只读前情和正文"]
  G --> H["确认后回写：状态差量/新关系/登场变化"]
  H --> A
```

### 各阶段输出

- `ideation`：作品承诺、章职责、合法可用人物索引、当前局势；不交付预写高潮。
- `entity_model`：活动人物与实体的完整来源视图、冲突和缺口；允许作家提出新增或迁移。
- `scene_plan`：逐场位置、存在方式、知识、控制权、进入/离开状态；不写修辞。
- `draft`：只给已选场面链、必要事实、活动人物包、正向声线样本和上一场出口状态。
- `review`：默认`cold_reader`，只读玩家前情和成稿；`design`才读取L4/L4.5做逻辑与制作复核；`benchmark`只在冷读完成后揭盲旧稿。三种视野不能合并。
- `writeback`：仅在用户确认后生成候选差量；不得自动提升Canon。

同一创作任务可以多次调用这些阶段。上下文按活动实体裁剪，而不是把完整Canon反复塞给每个智能体。

## 六、门禁与作者自由

人物与实体建模门只拦截四类硬错误：

1. 正式登场前把作品痕迹写成本人到场。
2. 不在场的人直接看见、触摸、驾驶或控制现场实体。
3. 角色获得模型中没有的知识、权限或能力，却没有建立过程。
4. 新具名人物承担现有角色本可承担的功能，且没有后续价值或退场闭环。

门禁不规定谁必须说哪句话，也不规定高潮必须使用哪个素材。若旧Working事实妨碍更好的故事，主笔可以提交迁移说明；在迁移批准前，测试稿必须标为Candidate。
