# 《超GAG机器人大战》逐话循环编剧工作流 v2.8

> 状态：工作流规格，不是剧情正文。  
> 目标：建立可直接用于逐章/逐话厚版梗概编写的循环式写作机制，防止 V24 式“字段齐全但读感变薄”。  
> 核心原则：每一话从上一话的结果长出来；每一话都调用写作 pipeline；每一话都留下状态账本，供下一话继续。
> v0.2 迁移：V24 暴露出 ELO 可以通过最低字段门禁却仍然低于 V22.10 厚度，因此新增“输出类别”“V22.10 厚度基准”“场面链门禁”和“章节厚写模式”。
> v0.3 迁移：V26.2暴露出“先写整章再打补丁”会反复漏机体、关系、名场面和meta边界，因此规定核心 writing pipeline 单次只写一话；ELO 是连续调用 pipeline 的外层调度器。
> v0.4 迁移：每完成第N章后，必须连读第1章到第N章做前缀回归总审；若问题根源在第K章，回到K章修正并重放K+1..N。同一根因最多阻塞3轮，仍不过则登记未解决问题账本，选择最优版本继续推进。
> v0.5 迁移：新增“主角熔炉门禁”。纪存、七海、白鸢不能只做符合人设的小判断；关键话和每章连读必须出现欲望、隐忍/准备、误判/诱惑、外部打击、崩溃或危险觉醒、不可逆选择、代价、升级/新限制和后续债务。秒数、半格、贴标签、存档、回合数等微指标只能作为表层表现，不能冒充主角级戏剧。
> v0.6 迁移：新增“情绪关系事件门禁”。主角团互相吸引不能靠规矩小动作、权限债务和共犯标签堆出来；成人/成年感关系必须有误会、体谅、理解、牺牲、吃醋、失去、回归、战场救援、选择某人而放弃正确计划等能被玩家记住的情绪事件。必要的狗血允许进入，但必须改变战斗、关系或后续状态；儿童线继续完全隔离成人向。

## 0. 为什么要加这一层

之前的大纲写作反复出现几个问题：

- 一次性写长文，越到后面越薄。
- 人物关系、分支、敌方收益、机体曝光和名场面梗点容易断线。
- 写完一话后，没有明确“下一话必须偿还什么债”。
- 资料很多，但每话写作时不稳定调用，导致素材库、50问题方案、canon、机体名单和玩法字段时常掉线。

这个工作流在 `chao-gag-writing-pipeline` 外面再加一层调度器：

```text
全剧六层生产看板
-> 当前唯一活动章
-> 本章story-chain NEXT与上游门
-> Story Runtime本地多路检索与四合同编译
-> 稳定章级前缀
-> 上一话状态差量与审稿
-> 下一话推进判断
-> 当前单话卡组装
-> 规划场面事务依赖图
-> 逐场组装内容寻址的交互上下文
-> 同一主笔写一场
-> 局部因果审查与出口状态提交
-> 顺序生成下一场
-> 机械合成整话并做接缝审查
-> 状态账本更新
-> 自动生成下一话 brief
-> 循环
```

它不是替代写作 pipeline，而是让 pipeline 可以逐话递归运行。

v0.3后必须区分两层责任：

- `chao-gag-writing-pipeline`：一次只进入一话；短话可以一次成文，长话必须由同一主笔顺序生产、审稿和提交场面事务。
- `Story Runtime Interaction Loop`：负责一话内部的场面规划、上下文组装、状态继承、局部审查、后代失效和整话合成。
- `Episode Loop Orchestrator`：负责连续多话/整章/全剧，把上一话账本变成下一话brief，逐话调用pipeline，全部通过后再组装章节。

如果某一章需要系统性补丁，不应把“补丁救稿”视为正常流程，而应退回到对应话的Pressure Board或Episode Card重做。

v2.1后还必须区分三种编号：

- `chapter_id`：由当前逐章总纲形成的章节编号，不预设总数。
- `slot_id`：旧V35.4/V35.7作者槽或迁移后的新槽编号，负责追踪分支、玩法、机体和状态来源；它不能反向生成章节。
- `episode_id`：最终单话编号；一个作者槽可以拆成多话，但必须写入`slot_episode_mapping.tsv`。

V35逐话写作不得从V35.2章段直接平均切话，也不得默认旧槽永远等于一话。先有新章级故事，再建立迁移映射。

v0.8后还必须区分“真实运行”和“叙述性运行”：

- 真实运行：存在逐话 packet 文件、独立审稿记录、prefix review、ticket/replay log、ledgers，并通过脚本检查。
- 叙述性运行：只在回答或一个大文档里描述自己跑过流程；这种不能算 ELO。

V27.0 暴露的问题就是叙述性运行：把多章合并成大稿、事后自检标通过、没有真实回滚迭代。因此 V28 开始必须以 packet-first 作为硬门槛。

v2.6后，“真实运行”先要求`report_v35_layered_pipeline.py --check`通过，再要求本章对应的`story-chain`阶段门实际返回成功。未运行命令、命令失败、manifest缺失或推进了看板未解锁的章节时，即便下游文件已经写出来，也只算越级草稿，必须标为`invalidated_downstream_artifact`。

v0.9后还必须区分“可推进 warn”和“坏通过 warn”：

- 可推进 warn：已经说明为什么不是阻塞项，写清分类、必要动作、回收窗口，并落到对应账本。
- 坏通过 warn：只在复审里写“关系还弱、机体后续要加强、宏观线以后补”，但没有 ticket、没有 replay、没有 ledger。这种不得进入下一章。

v1.0后还必须区分“结构完整”和“真的好看”：

- 结构完整：有机体、玩法、关系、敌方收益、状态变量和账本。
- 真的好看：玩家能复述本话发生了什么；能记住一张机体画面；能开始关心某段关系；能感觉更大的G.A.G./索引/远星阴影；能期待下一话。

如果前三章的评价是“设定挺聪明，但不像机器人大战开局”“故事能理解，但不想立刻打C04”“关系有设计但没感觉”，这不是普通 future watchpoint，而是开局试玩审查的回归问题。

v0.4后，ELO还承担一层“前缀回归总审”：

- 写完第N章后，不只审第N章，而是连读第1章到第N章。
- 如果第N章暴露的问题根源在第K章，就生成Regression Ticket并回到第K章。
- 第K章自检通过后，从K+1顺序重放到N；不受影响的章保留，局部受影响的章patch，结构受影响的章重跑ELO。
- 重放到N后，再次连读第1章到第N章。
- 同一根因最多阻塞3轮；3轮仍不过，就写入未解决问题账本，选择当前最优版本继续第N+1章。

v0.5后，ELO还承担“主角熔炉审稿”：

- 纪存、七海、白鸢必须有长期弧线账本。不是每话都要三人同场升级，但每章连读必须能看见他们至少一人的重大转折，并且另外两人的压力不能失踪。
- 主角成长不是“更会说主题”，而是状态改变：权限、支援、路线、机体解锁、公开身份、法律责任、关系位置、敌方样本或下一目标发生变化。
- 微动作必须挂到大后果。比如“七海延迟40秒”只有在导致她被处分、暴露改革派身份、改变白名单法律结构或触发纪存/白鸢关系裂缝时才是戏；否则只是细节。
- 纪存的戏不能默认靠“他又做错了”增强。他要有能力、审美、隐忍、危险权限、公开承担和自我限权；他的成长应像主角升级，而不是反复补锅。

v0.6后，ELO还承担“情绪关系事件审稿”：

- “债务、共犯、权限、白名单、支援变化”只是账本语言，不能替代玩家能感受到的关系场面。
- 成人/成年感关系要能出现危险吸引、误会、吃醋、体谅、理解、牺牲、短暂失去、不可思议的回归、狗血反转和战斗支援变化。
- 如果角色死亡、失踪、被封存或被索引替换，后续可以通过 G.A.G. 残响、机魂、版本层、万机馆证词或机体载体回归，但回归不能抹掉牺牲的代价。
- 儿童角色只承担托付、童年、观众和家感，不参与成人卖相和狗血暧昧。

v0.7后，ELO还承担两层新审稿：

- 情绪积累语法：关系爆发前后都要有积累。可参考桂正和作品处理情绪的方法：错过、尴尬近距离、欲言又止、视线停留、吃醋后自责、重复物件、日常照顾、替对方忍住、笨拙但真诚的欲望。只取方法，不照搬剧情、人物设定或台词。
- 纪存机魂记忆层：纪存不是普通档案员，而是逐渐苏醒的机魂实体。每次记忆苏醒都要有触发物、身体/权限/情绪代价，并推动谜团、保护行动、地图层、战斗规则或 G.A.G./万机馆/远星真相，不能只当设定说明。

v1.0后，ELO还承担“体验承诺审稿”：

- 读者/玩家钩子：本话最后必须留下一个具体继续动机，不能只说“主题推进”。
- PV级机体画面：开局、高潮和篇章启动话必须有能剪进预告的机器动作、出击、变形、防御、失败、觉醒或地图尺度变化。
- 全剧机体/IP来源：写每话前先查 `2026-07-04-chao-gag-full-series-roster-ip-material-pool-v0-2.md`、`v29_roster_bible_reserve_backfill_pool_v0_1.tsv`、`v29_roster_ip_first_appearance_candidate_pool_v0_1.tsv`、`v26_roster_ip_remount_matrix_v0_1.tsv` 和 `v26_episode_slot_remount_v0_1.tsv`；C01-C03开局钩子池只补关系、PV镜头、异常阴影和锚件。
- 首登选择：候选池不排定话号；每话在Context Pack里按本话场面需要选择实际首登机体，并在State Deltas写入 `roster_first_appearance_ledger`。除过场/纯经营轻话外，本话新增里至少1台优先来自参战Bible/Reserve回填池；旧机复出不得冒充新增。
- 关系情绪事件：成人/成年感关系不能只靠权限、债务、白名单、水印和共同责任推进；必须有被看见的误会、吸引、羞耻、吃醋、体谅、牺牲、救场或伤害。
- 宏大阴影：G.A.G.、索引、远星、旧灾变和万机馆隐藏尺度必须以UI伤口、信号、地图异常、敌方抽取、记忆症状或物件反常出现，而不是后期再解释。
- 议题转戏剧：授权、证词、标签、价格、公共信托、未完成等议题必须落成人、机体、地图、损失、救援、公开羞辱、胜利或敌方收益。
- 真实证词边界：若本话使用真实爱好者案例，必须说明case_id、来源、direct/inspired/fictionalized用法、具体情绪物件、敏感边界和发布前复核；真实证词只能加深生活厚度，不能变成催泪按钮、现实人物战斗单位或机战承重替代品。
- 机器人文化价值轴：写顶层命题、远星、索引、开馆权战争、真实证词、终局或体验承诺板时，先查 `robot_culture_value_axes_v0_1.tsv`。本话可选用一条或明确跳过；选用后必须落成场面、玩法、角色选择、机体动作、敌方误用和后续债务。价值轴不是每话机械KPI，但关键话不能只喊口号。

## 0.0 高密度剧情章节模式

当一章的局部场面无法脱离全章波形判断，或多条人物、IP、机体、分支和玩法线争夺同一个高潮时，ELO先读取[高密度剧情章节模式 v1](2026-07-18-chao-gag-high-density-dramatic-chapter-mode-v1.md)。这项模式治理戏剧耦合，不等同于V35“高密度机体manifest”，也不因资料行或机体数量多而自动启用。

启用后，ELO先从生产状态、体验宪章、总发动机、世界机制基线、六层融合逐章前提和Current Canon提取一页“全剧脊柱对齐卡”，明确本章必须兑现、可以推进、只能预显影、必须留给未来以及必须交给下一章的状态；随后编译最小Context Pack与章级实体、空间、能力、动作和资产预制包，再依次完成章节导演板、战斗与玩法预案、只负责校验的物理因果与人物站位板，以及完整章纲。预制包与三张板共同执行玩家可见性门，不能让只能靠作者解释的场面通过。

被用户确认或已经升为Working的章节仍接受同一套独立审查。确认状态只要求保护已经成立的场面功能、提高整章推倒的证据门槛，不允许跳过控制权、空间、玩法、机器人文化、关系表演和人类声线检查。

完整章纲获得用户或生产门审定并以当前哈希封存后，ELO先通过`write-performance`门，再制作章级演出承载规划。规划把全章按一次真实游玩的顺序排成舰内自由活动、ADV、探索、地图事件、SRPG、战中通讯、短动画、Cut-in、结算与可选事件，并检查动画峰值、ADV长度、地图复用和资产成本。规划审定并封存后还必须通过`write-episode`门，才允许Pipeline进入一话。随后先判断该话是否能在一次稳定交互中闭合；不能时必须建立场面事务依赖图，由同一主笔逐场生成、局部审查、提交状态和机械合成。后话读取本章已完成Reader的真实结果，不允许先批量填满空白话卡；同一话的后场也必须读取前场已提交的真实状态，不允许并行填场或把章纲解释句直接拆成角色对白。

Reader正文由一个主笔职责持续持有。审稿席在Reader成形后独立指出症状、证据、根因和需要重写的场面，不直接往正文中追加各自的解释。动机、因果、控制权、关系转折、IP情绪前提、战斗目的或分支结果发生变化时，必须整场重写并顺序复读后话；局部补丁只处理真正局部的问题。

HDCM通过标准是全章戏剧是否成立，不是模板字段是否填满。章级工件是所有单话调用的共同母板，但不能膨胀成另一套设定百科。

全剧对齐也不是旧纲否决新戏。若本章产生更好的结构性方案，必须先提出总纲迁移，列出被替代内容及对后续人物、关系、机体、敌方、谜团和分支的影响；迁移通过后再进入Reader。不能让旧纲和新正文同时声称不同的未来仍然有效。

章级预制、故障路由与声线门的当前入口为：

- `docs/superpowers/specs/research/2026-07-23-chao-gag-chapter-preproduction-model-v1.md`
- `docs/superpowers/specs/research/2026-07-23-chao-gag-human-voice-dialogue-gate-v1.md`

常规章最多新增“一份可读预制模型、一张可选机器表、一份审查结果”；轻量章直接并入导演板。新大型场景、多尺度巨体、变形、新能力首用、三方混战或胜负依赖空间结构时，才强制制作俯视灰盒、尺度/控制关系与关键奇观预演。

## 0.1 输出类别先行

ELO 每次运行前必须先判断目标产物，不允许混用：

| 类别 | 用途 | 可接受密度 | 禁止误用 |
| --- | --- | --- | --- |
| 路线图 | 全剧导航、章节顺序、话题覆盖 | 每话可短，但必须标注为蓝图 | 不能当成厚版梗概或台本 |
| 话卡 | 单话设计输入 | 字段完整即可 | 不能替代剧情流程正文 |
| 厚版章节梗概 | 可读剧情底稿、后续拆关卡和资产 | 以 V22.10 为当前厚度与内容类别参考 | 不能压成两段摘要，也不能把参考稿当正确性金标准 |
| 章级演出承载规划 | 把通过的章纲排成玩家实际经历顺序 | 标明载体切换、信息证据、动画峰值、地图复用和资产等级 | 不写完整台词、逐镜分镜、秒数或敌军数值 |
| 台本 | 对白、动作、演出 | 逐场逐句 | 不能直接照抄梗概说明句 |
| 资产 brief | 美术/关卡/机体拆分 | 明确层级和边界 | 不能把临时支援都当完整参战 |
| Reader Synopsis | 判断故事是否好看、给用户连读 | 连续剧情、少字段、重场面和情绪 | 不能替代packet账本，也不能塞满变量名 |

只要用户提到“完整”“厚度”“别偷懒”“保持 V22.10 强度”“读起来要有戏”，默认目标就是 **厚版章节梗概**。

## 0.2 V22.10 厚度基准

当前厚版章节梗概的厚度与内容类别参考是：

`docs/superpowers/specs/剧情梗概/V22-A5厚度修复整合稿-星火战队与万机同心-v22.10.md`

这个参考不证明其结构、因果、声线或Canon天然正确，也不是要求机械凑字数；它只要求每话拥有完整场面链：

1. 开场图像：玩家能看见地点、机体、物件和气氛。
2. 压力到场：敌方、制度、索引、灾害或关系矛盾切入。
3. 可玩问题：玩家这一话到底做什么，地图/胜败条件是什么。
4. 中段变化：战斗或探索中出现反转、误读、抢夺、支援失效或新机制。
5. 人物选择：至少一个角色用行动承担代价，而不是只说主题。
6. 机体动作：机体/模块/残响改变战局，不只列名字。
7. 敌方抽取：敌方学走、抢走、误读或复制某个样本。
8. 余波债务：下一话必须回应本话结算。

厚版章节梗概每话通常应接近 V22.10 的信息密度。若每话只有几百字，即使字段齐全，也只能视为路线图或话卡。

## 0.3 Fable固定二审位置

v1.7 后，Fable 不再作为“什么时候想起来就用”的可选外挂，也不作为主稿生成器。它的位置固定在：

```text
本地单话packet完成
-> 本地Writer Room Review / 标准门禁通过
-> 生成Fable Review Pack
-> Fable只做读感、台词、关系、燃泪梗、无聊/看不懂处诊断
-> Codex本地采纳、改写、拒绝或延期
-> Patch Merge
-> Gate Result / State Deltas / 账本
```

Fable Review Pack 必须限制输入和任务：

- 输入：Reader Synopsis、关键关系场、角色声音笔记、机体/玩法摘要、禁止改动项、本地已通过门禁。
- 输出：可读性/连续感诊断、台词/人物声音诊断、关系张力/成人边界诊断、燃点/泪点/梗点诊断、无聊/注水/看不懂处、局部改写建议表、不应改动项确认。
- 禁止：新增 canon、改机体名单、发明分支变量、改战斗规则、写 TSV、替 Codex 决定主线。

每话必须写入 Fable 状态：

- `fable_review_done`：Fable 诊断完成，输出已捕获，Codex 已本地合并或拒绝建议。
- `fable_failed_technical`：GUI、页面 chip、模型选择、提交、输出捕获或页面验证失败；必须追加本地台词/关系/读感替代复审。
- `fable_rejected_overdrift`：Fable 输出越界，改 canon/机体/玩法/分支或味道不对，整体拒绝。
- `fable_skipped_user_approved`：用户明确批准跳过。

不能出现两种坏状态：一是 Fable 失败但口头说“也算二审了”；二是 Fable 没跑、没入账，却在最终稿里声称已通过 Fable。

启用 Fable 模式的运行，最终 validator 应额外带：

```bash
--require-fable-review
```

如果本轮明确不启用 Fable，不能使用这个开关，也不能在完成说明里声称 Fable 二审已完成。

## 1. 工作流名称

建议名称：

**Episode Loop Orchestrator / 逐话循环编剧调度器**

简称：**ELO**。

它负责：

- 判断下一话该做什么。
- 给 pipeline 组织上下文。
- 检查 pipeline 产物是否合格。
- 更新状态账本。
- 生成下一话输入。

## 1.2 子agent编剧室

厚版运行默认采用子agent编剧室。若工具不可用或用户未授权，则必须在 packet 中写：

```text
Reviewer Mode: single-context fallback
Fallback reason:
```

不能把 single-context fallback 称为“子agent审稿”。

子agent分两层：

- **常驻顾问**：canon/素材提取、机体/IP挂载、主角/关系线顾问。它们适合做章节资料包、侧评和跨话一致性提醒，但不能算逐话过稿。
- **逐话席位**：每一话都必须重新审当前 packet。正式厚版重写默认采用这层作为通过线。

普通授权使用子agent时，每话至少有六个独立审稿面：

| role_id | 职能 | 阻塞点 |
| --- | --- | --- |
| showrunner | 剧情监督 | 戏剧无转折、高潮不成立、因果断线 |
| mecha_ip | 机器人文化专家 | 机体只是名单、IP/名场面不可识别、机战爽点不足 |
| gameplay | 游戏制作人 | 玩家不知道玩什么、地图机制空泛、战斗中段无变化 |
| relationship | 感情戏顾问 | 纪存/七海/白鸢关系账本化、无误会/吸引/牺牲/积累 |
| protagonist | 主角熔炉编辑 | 主角只做小指标选择，没有打击、代价、升级 |
| canon_asset | Canon/资产监督 | 设定冲突、资产层级不明、图谱索引缺失 |

主控 Orchestrator 只能整合和判定，不能本地伪造子agent结果。若某角色审稿给 fail，必须补丁、重建 episode card，或把本话标为 failed/warn。

每个 episode packet 必须有独立审稿记录。不能把同一组子agent ID 或同一轮子agent结论复制给多话使用；否则只能算章节级侧评，不能算逐话 writer-room review。

所有剧情工作流文档、复审、票据和说明默认中文书写。为了脚本稳定，字段名如 `Episode ID`、`Gate decision` 可以保留英文，但字段内容和判断说明必须中文。

正式厚版重写、V30+开局修复、全剧重写或用户明确担心“偷懒/衰减/漏关系/漏机体/IP”时，启用 **理想编剧室**。理想编剧室每话十七席：

| role_id | 职能 | 退稿权 |
| --- | --- | --- |
| showrunner | 剧情监督 | 戏剧无转折、因果断线、高潮不成立 |
| 50_issue | 50问题审计 | 旧问题只贴标签、没有场面化解决 |
| mecha_ip | 机器人文化专家 | 参战机体少、IP投射弱、名场面不可识别 |
| gameplay | 游戏制作人 | 玩家不知道玩什么、地图/胜败条件/中段变化不清 |
| character_dialogue | 人物与对白编辑 | 人物同声、金句化、台词没有听众和动作 |
| relationship | 感情戏/成人卖相顾问 | 关系无吸引、误会、牺牲、狗血事件或战斗后果 |
| protagonist | 主角熔炉编辑 | 主角只有小指标动作，没有打击、代价、升级或新限制 |
| jicun_memory | 纪存机魂记忆编辑 | 机魂记忆只讲设定，不破局、不保护、不付代价 |
| quote_scene | 名台词/名场面连续性编辑 | 直接引用复用、错用，或梗点没有进入剧情动作 |
| spectacle_emotion | 燃泪梗编辑 | 无燃点、泪点、梗点，或都是小口径设计 |
| robot_anime_pv | 机器人动画/PV导演 | 没有可剪预告的巨大机器画面和动画时机 |
| commercial_opening | 商业开局制作人 | 玩家没有继续动机、奖励期待或试玩吸引力 |
| macro_mystery | 宏观谜团监督 | G.A.G./索引/远星/旧灾变没有事件化阴影 |
| player_interest | 玩家兴趣代表 | 读完无法复述“发生了什么值得说” |
| wanji_culture | 万机馆文化容量编辑 | 万机馆/开馆/馆藏规模和谱系不够“万机” |
| thickness | 厚度编辑 | 退化成话卡、设计备忘录或两段摘要 |
| canon_asset | Canon/资产监督 | canon冲突、资产层级不清、图谱/索引遗漏 |

理想编剧室运行必须满足：

- 每话每席都有独立 `pass/warn/fail`、证据、补丁动作和账本风险。
- 同一个 reviewer_id 不得跨角色或跨话复用；不能用三位常驻顾问覆盖十七席。
- 任何席位 `fail` 都必须补丁、重建 episode card，或把本话标为 failed/warn。
- 运行完成态必须带 `--strict-writer-room` 通过脚本检查。
- 若工具/上下文无法支撑十七席，就降级为 `shared advisory only` 或 `single-context fallback`，并在最终说明中承认它不是理想编剧室产物。

## 3. 每轮循环

### 3.1 上一话结果审稿

先不写下一话，先审上一话。审稿不是评价文笔，而是提取状态：

| 审稿项 | 必须回答 |
| --- | --- |
| Clear State | 本话结束时世界、万机馆、人物、敌方和机体状态变成了什么 |
| Debt | 哪些关系、分支、物件、敌方收益必须在后文偿还 |
| Escalation | 本话把哪条线推高了，下一话不能平行重复 |
| Mecha Exposure | 本话新增了哪些机体/单位/模块，是否满足密度 |
| Quote/Scene Use | 本话用了哪些名场面/台词锚点，是否只是引用还是已原创化 |
| Gameplay Change | 本话给玩家玩了什么，是否改变地图、胜败条件或支援 |
| Character Turn | 谁做了不可逆动作，谁被误解，谁靠近或破裂 |
| Protagonist Crucible | 哪个主角进入熔炉：欲望、隐忍/准备、误判/诱惑、外部打击、崩溃/觉醒、不可逆选择、代价、升级/新限制分别是什么 |
| Emotional Relationship Event | 哪条关系出现可记忆情绪事件：误会、伤害、体谅、牺牲、吃醋、失去、回归、战场救援或狗血反转 |
| Emotional Accumulation | 哪些错过、近距离、欲言又止、重复物件、日常照顾或笨拙真心让羁绊成立 |
| Jicun Memory | 纪存苏醒了哪段机魂记忆，付出什么代价，解开了什么谜团/死局 |
| Enemy Gain | 敌方学走、抢走、误读或复制了什么 |
| Slot/Route State | 上一话完成了哪个作者槽，当前路线选中/跳过哪些槽，下一话是否合法 |
| Unit Availability/Fleet | 哪些机体已可控、离队、转敌、跨舰或改变政治归属 |
| Decision Propagation | 哪些V35.4命运线程已经改变，下一话必须继续读取什么 |

如果上一话没有明确状态变化，下一话不能直接写，必须先补上一话结算。

V35运行中，如果上一话没有更新`slot_episode_mapping.tsv`、`route_state.tsv`、`unit_availability.tsv`和相关`decision_propagation.tsv`，下一话也不能直接写。

### 3.1A V35.4槽位预解析

V35正式运行在“判断下一话推进方式”之前先完成：

1. 确认`Author Slot ID`和槽到Episode映射。
2. 确认当前route window、selected slots与skipped slots。
3. 为跳过槽生成world continuation，不允许只写未选择。
4. 根据72机生命周期生成`Available Fleet`；C12后读取舰群。
5. 根据50节点表生成`Incoming Decision Threads`与本话必须输出的delta。
6. 选择`New Unit Gate Mode`：`first_appearance`、`lifecycle_delta`或`bridge_exception`。

任一项不明确时，只能停在Pressure Board，不能开始Draft Synopsis。

v0.3附加审稿：如果上一话没有机体动作、玩法钩子、关系硬动作、名场面/台词使用层级、敌方收益、情绪物件或世界内meta边界，也不能直接推进下一话。

### 3.2 判断下一话推进方式

下一话不能只是“发生下一件事”。调度器必须给它选一个推进类型：

| 类型 | 用途 |
| --- | --- |
| 埋种 | 放入后续大爆点的物件、台词、敌方样本或关系误会 |
| 推进 | 让上一话债务产生直接后果 |
| 反转 | 证明上一话看似胜利其实被敌方利用 |
| 破裂 | 让人物关系、队伍信任或合体条件出现裂缝 |
| 爆发 | 大战、灾害、公开听证、发布会、暴走或名场面高潮 |
| 冷却 | 用生活场、维修场、开馆场让人物消化代价 |
| 回收 | 回收旧物件、旧台词、旧选择、旧机体或旧分支 |

每一话至少要有一个主推进类型，重点话可以有两个，例如“反转 + 爆发”。

### 3.2.1 体验承诺板

### 3.4 调用写作 pipeline

每话都按 `chao-gag-writing-pipeline` 的内部轮次运行。核心pipeline一次只允许进入一话，但不再假定整话只需一次模型交互：

1. Task Brief
2. Context Pack
3. Pressure Board
4. Episode Card
5. Scene Transaction Plan
6. Sequential Scene Draft / Local Review / State Commit
7. Episode Mechanical Assembly / Seam Review
8. Writer Room Review
9. Patch Merge
10. Structure Normalization
11. Canon/Graph Backfill 判断

外层 ELO 不跳过这些步骤。它只把每一轮输入组织好，并在输出后做额外门禁。若用户要求连续写完整章，ELO负责循环调用pipeline，不得把多话塞进一次pipeline调用。

### 3.4.1 单话场面事务循环

Episode Card完成后，先判断本话能否在当前模型的稳定创作容量内一次闭合。判断依据是场面数量、地点和视点切换、活跃人物/机体、战斗阶段、控制权变化、新机制、关系转折和信息揭示，不以总纲字数平均切段。

需要多次交互时：

1. 建立`单话场面事务计划`，每场声明依赖、入口事实、局部目标、阻力、转向和出口事实；
2. 编译字节稳定的单话前缀；
3. 每次只装配一个场面事务，读取前置出口状态、必要旧场回执、上一场少量原文尾段和本场检索摘要；
4. 同一主笔完成正文和出口状态回执；
5. 独立局部审查检查入口/出口因果、知识来源、物理控制、人物动机、最简单可靠方案、未来边界和转场；
6. 通过后提交场面；未通过则整场重写；
7. 前场提交内容改变时，后续场面与整话合成自动失效并从最早受影响处顺推；
8. 全场提交后机械合成完整单话，再做接缝和全话因果审查。

禁止按固定字数截断正在进行的争吵、选择、攻击、合体、救援或关系爆发。禁止多名写作Agent各写一场后直接拼接成主笔正文。

### 3.4.2 厚写顺序

厚版章节不能先写字段再往里塞剧情，而要按以下顺序：

```text
发动机句
-> 场面链
-> 战斗/玩法规则
-> 机体动作
-> 人物关系和情绪物件
-> 敌方收益和结算
-> 字段归整
```

如果先得到的是短话卡，必须先升级为场面链，再进入正文；不能把短话卡直接合并成章节稿。

### 3.5 门禁审查

每话写完必须过门禁。

最低门禁：

- 输出类别门禁：厚版章节不能低于 V22.10 场面链密度。
- 场面链门禁：开场图像、压力到场、可玩问题、中段变化、人物选择、敌方抽取、余波债务必须可见。
- 至少 2 台新机体/机体单位曝光。
- 至少 1 台机体进入战斗规则或玩法机制。
- 至少 1 个读者/玩家钩子。它必须是具体问题、危险、机体、关系、谜团或奖励，不能只写“主题推进”。
- 开局、高潮和篇章启动话必须有至少 1 个PV级机体/战场画面。锚件、展签、变量表和术语不算，除非它们让机器移动、变形、防御、失败、觉醒或改变地图。
- 至少 1-2 个名场面/名台词/文化梗进入场面，并声明三档用法：直接短引、错引/误记、原创变奏。直接短引必须短、贴场面、不可代替原创戏剧。
- 至少 1 个可玩的战斗/探索/开馆/深潜/修复/听证机制。
- 至少 1 个敌方收益或敌方误读。
- 真实爱好者证词若进入本话，必须有case_id、来源、使用模式、具体情绪物件、敏感边界和发布前授权/署名复核；不满足时只能写成虚构化现实母题或不使用。
- 至少 1 个关系硬动作：权限、误会、靠近、破裂、吃醋、背锅、公开选择、共犯、支援状态变化或成年关系卖相。
- 承担本话戏剧重量的关系必须有情绪事件；“债务/共犯/权限/流程缝隙”不能单独通过。情绪事件可以是误会、伤害、体谅、牺牲、失去、回归、战场救援、狗血反转或选择某人而放弃正确计划。
- 关系大事件需要足够情绪积累才成立；如果是突然冲击，后续必须把“没来得及理解/告白/解释”处理成伤口。
- 关键话必须有主角熔炉；每章必须有可见主角弧线增量。合格的增量包括隐忍/准备、重大失败、公开背锅、崩溃、禁忌能力、暴走代价、修炼/重建、权限升降、路线承诺、关系破裂/重建、机体/支援升级或主动接受新限制。
- 若纪存是本话主承重，他的机魂实体身份或苏醒记忆必须影响谜团、保护、战斗规则、地图层或主线死局，不能只是站在终端前解释。
- 开局和篇章启动话必须有至少 1 个宏大阴影信号：G.A.G.异常、索引优化、远星错序/误译、旧灾变残痕、万机馆隐藏尺度或敌方抽取样本。它必须是可见事件，不是背景说明。
- 如果本话承载授权、证词、标签、价格、公共信托、未完成等抽象议题，必须把议题转成玩家能操作、看见、失去或赢回的东西：人、机体、地图、公开羞辱、救援、胜利或敌方收益。
- 至少 1 个情绪物件或可回收证物。
- 至少 1 个下一话债务。
- 人类角色不得说“章节、玩家、剧情、路线”等世界外meta。半透meta只能由G.A.G.、索引、终端UI、小查错版、残响版本层等世界内载体承担。

失败处理：

```text
门禁失败
-> 回到 Writer Room Review
-> 生成补丁计划
-> Patch Merge
-> 再审门禁
```

不能用“后面会补”通过本话门禁。

若失败是系统性缺项，例如整话没有机体玩法、关系硬动作、敌方收益或名场面层级，则不是普通补丁，而是回到3.3资料包或3.4 Pressure Board/Episode Card重做。

厚度门禁失败的典型症状：

- 剧情流程只有两段概述，没有场面推进。
- 战斗与玩法只有类型，没有地图、胜败条件、中段变化。
- 机体出场只是名单，没有具体动作或资产层级。
- 读者钩子只是“下一话继续调查”，没有具体机体、关系、谜团、奖励或危险。
- PV画面其实是展签、变量、锚件或说明句，没有任何机器动作或战场尺度。
- 关系线只有“推进/靠近/误会”标签，没有动作、权限、身体距离、共犯或代价。
- 关系吸引只有规矩小动作、债务和共犯，没有误会、体谅、牺牲、失去、回归或狗血情绪事件。
- 关系大爆发前没有错过、近距离、重复物件、欲言又止或日常照顾等积累，导致牺牲/告白/吃醋不成立。
- 主角成长只有“存档/贴标签/40秒/半格/一回合”等小动作，没有大打击、大选择、大代价或状态升级。
- 纪存作为主角时只整理资料，不通过机魂记忆、保护和智慧破局。
- G.A.G./索引/远星只作为后期名词，没有前三章可见阴影。
- 授权、证词、标签等议题只在对话里讨论，没有变成战斗目标、机体状态、人物损失或敌方收益。
- 梗点只写来源感觉，没有原创化成关卡、台词压力、机体动作或玩家选择。
- 名台词被强行改到看不出来源，或直接短引用成彩蛋清单，没有改变场面。
- 普通人类角色说出世界外meta。
- 通关结算只说“进入下一话”，没有敌方收益、分支疤痕或可回收物件。

## 3.8 前缀回归总审

每完成第N章后，ELO必须执行前缀回归总审：

```text
完成第N章
-> 连读第1章到第N章
-> 专业编剧/机器人文化专家/游戏制作人三视角审稿
-> 判断是否存在连读问题
-> 若有，定位最早根因章节K
-> 生成Regression Ticket
-> 回第K章修正
-> 从K+1顺序重放到N
-> 再次连读第1章到第N章
-> 通过后进入第N+1章
```

### 3.8.1 总审视角

| 视角 | 检查内容 |
| --- | --- |
| 专业编剧 | 戏剧推进、起承转合、人物动机、关系质变、情绪爆点、前后因果 |
| 机器人文化专家 | 参战机体规模、机体谱系代表性、IP名场面可识别度、模玩/动画/特摄/游戏文化是否用活 |
| 游戏制作人 | 每章玩法差异、战斗目标、地图机制、奖励/解锁、资产成本、玩家是否持续有欲望 |
| 宫本式体验检查 | 玩家是否一眼知道怎么玩，规则是否简单但有惊喜，机体玩法是否像玩具一样好玩 |
| 小岛式叙事检查 | 主题余味、影像感、仪式感、meta边界、角色关系的危险吸引力 |
| 主角熔炉检查 | 纪存、七海、白鸢是否经历了隐忍、误判、打击、崩溃、觉醒、选择、代价和新状态；是否摆脱小指标式成长 |
| 情绪关系检查 | 主角团关系是否有误会、体谅、理解、牺牲、失去、回归、狗血反转和战斗后果；是否摆脱债务/共犯账本感 |
| 情绪积累检查 | 关系是否通过错过、尴尬近距离、重复物件、日常照顾、笨拙真心和欲言又止建立羁绊，而不是直接跳爆点 |
| 纪存记忆检查 | 纪存机魂记忆是否逐步苏醒、付出代价，并用保护和智慧解开谜团/死局 |
| 开局体验检查 | 当前章节是否让玩家想继续、是否像机器人大战、是否有PV级画面、是否有人物关系钩子和宏大阴影 |

### 3.8.1.1 C01-C03 开局试玩审查

完成第三章后，必须额外写一次开局试玩审查。它可以独立成 `reviews/C01-C03-opening-arc-review.md`，也可以作为 C03 prefix review 的单独章节，但必须包含以下判断：

| 项 | 必须回答 |
| --- | --- |
| Trial Hook | 如果试玩到C03结束，玩家为什么会想继续C04？ |
| Robot-war Promise | 前三章是否证明这是机器人战棋/机战游戏，而不只是文化策展故事？ |
| PV Images | 前三章至少三张可剪PV的机器人画面是什么？ |
| Relationship Hook | 哪段成年/主角团关系已经让玩家想继续看？ |
| Macro Shadow | G.A.G./索引/远星/旧灾变有没有形成更大阴影？ |
| Reader Synopsis | 有没有可连续阅读的故事稿，还是只能看packet字段？ |

如果答案是“设定不错但不够抓人”，不得直接推进C04。必须开回归票据或做C01-C03趣味性增强补丁；只有用户明确接受这种开局气质时，才能作为 `user_review` 带出。

### 3.8.2 Regression Ticket

每个回溯问题必须具体化成票据：

```markdown
Regression Ticket

发现时间：完成第N章后
问题症状：连读1..N时暴露了什么
最早根因章节：第K章
根因判断：为什么不是第N章局部问题
影响账本：关系/机体/IP名场面/玩法/敌方收益/G.A.G./远星/分支
必须保留：已经成立的好场面、机体动作、关系动作、玩法机制
修改目标：第K章必须补出什么
重放范围：K+1..N
通过条件：1..N连读不再暴露该问题
根因轮次：1/3、2/3或3/3
```

### 3.8.2.1 Warn 分类断路器

Prefix Review 的 `Overall result: warn` 必须继续填写：

```markdown
Warn classification:
Blocking issue:
Required action:
Unresolved issue carried:
Ledger rows written:
```

分类只能是以下几种：

| 分类 | 含义 | 是否可推进 |
| --- | --- | --- |
| `local_fix` | 问题在当前章局部可修 | 修完并重验后才可推进 |
| `regression` | 根因在更早章节K | 开Regression Ticket并重放K+1..N后才可推进 |
| `future_watchpoint` | 刻意留给后续章节爆发/回收 | 必须入账，写明回收窗口后可推进 |
| `implementation_debt` | 数值、UI、资产成本等实现期问题 | 必须入账，不影响剧情逻辑时可推进 |
| `user_review` | 涉及主轴、路线、关系或风格取舍 | 停下给用户看，不自动推进 |

严禁：

- `Overall result: warn` 但不写分类。
- 写了“Unresolved issue carried”但 `unresolved_issues.tsv` 为空。
- 写了“关系偏弱、机体后续加强”却只当普通 watchpoint，不入账。
- 子agent警告没有补丁动作，却把 `Gate decision` 写成 pass。

### 3.8.3 重放规则

第K章修正通过后，不能直接进入第N+1章。必须从K+1顺序重放到N：

| 后续章节状态 | 处理 |
| --- | --- |
| 不受影响 | 保留原章，只更新ledger |
| 局部受影响 | 局部patch并重新过本章门禁 |
| 结构受影响 | 该章重跑ELO |

### 3.8.4 Deadloop Breaker

同一个根因最多阻塞3轮。

| 轮次 | 处理 |
| --- | --- |
| 第1轮 | 回根因章节K修正，重放K+1..N |
| 第2轮 | 若仍暴露同根因，允许再次修正和重放 |
| 第3轮 | 最后一次阻塞性修正，选择三轮中最优版本 |
| 3轮后仍不过 | 不再阻塞；写入未解决问题账本，记录原因、判断、已尝试方案、选择版本和后续观察点，然后继续第N+1章 |

只有当问题需要用户做高层取舍时才停止推进，例如：改变主轴、删除锁定角色/机体、改变用户确认的关系线、接受明显不同的作品气质。

下一轮从这个 brief 开始。

## 4. 全剧运行模式

用户要求“不用试跑，直接干出全部”时，启用 **Full Run Mode**。

Full Run Mode 的意思不是一口气输出 60 话薄文，而是：

- 按循环连续推进全剧。
- 每次核心pipeline只写一话。
- 默认不在每话后停下来问用户。
- 每 3-5 话做一次内部连续性审查。
- 每篇结尾做一次篇章审查。
- 如果遇到硬 canon 冲突、重大用户取舍、角色入队硬锁或超出尺度边界，才停下来报告。
- 如果目标是厚版章节梗概，每次最多交付 1 篇或 1 个重场面微批；全剧只能先做路线图，再逐篇厚写，不能一次性声称 60 话全都达到 V22.10。

### 4.1 批次节奏

建议：

| 批次 | 内容 |
| --- | --- |
| 微批 | 1 话重话，或 2 话轻话 |
| 小批 | 3-5 话，做一次连续性审查 |
| 篇章批 | 1 篇完成后，做篇章状态审查 |
| 全剧批 | 全部完成后，做全局密度/关系/敌方/分支审查 |

### 4.2 不允许的全剧写法

- 不允许先填 60 个两段摘要，再回头补机体。
- 不允许把路线图标成厚版梗概。
- 不允许把机体、名场面、关系、玩法写成四张单独清单，而不进入剧情。
- 不允许后半段比前半段明显变短。
- 不允许“本话暂略，后续补充”。
- 不允许只用旧 canon 限制新素材。

## 5.1 厚度校验脚本

写厚版章节时，至少运行：

```bash
python3 /Users/rayz/.codex/skills/chao-gag-writing-pipeline/scripts/check_story_doc.py \
  docs/superpowers/specs/剧情梗概/<目标稿>.md \
  --episode-regex '^## A\\d{2}-\\d+ ' \
  --heading '### 本话功能' \
  --heading '### 剧情流程' \
  --heading '### 战斗与玩法' \
  --heading '### 机体出场' \
  --heading '### 燃点 / 爽点 / 梗点' \
  --heading '### 泪点' \
  --heading '### 感情线' \
  --heading '### 通关结算' \
  --min-block-chars 1800 \
  --max-min-ratio 2.6 \
  --report-lengths
```

`--min-block-chars` 只是警报线，不是文学质量；若某话低于警报线，必须由 Thickness Editor 判断是轻话合理，还是确实退化成话卡。V24 那类每话几百字的产物不能通过厚版章节验收。

## 5.2 ELO运行结构校验脚本

V28 及之后，在声称 ELO 运行完成前，至少运行：

```bash
python3 /Users/rayz/.codex/skills/chao-gag-writing-pipeline/scripts/check_episode_loop_run.py \
  docs/superpowers/specs/剧情梗概/V28 \
  --require-subagents \
  --require-chapter-reviews \
  --require-run-validation-log \
  --strict-prefix-warn-policy \
  --strict-creative-gates \
  --strict-writer-room \
  --min-story-chars 1200
```

如果某次运行没有授权子agent，只能去掉 `--require-subagents`，并且最终说明必须写明“single-context fallback”。这类运行可作为草稿，但不能作为子agent编剧室产物。

如果某次运行只使用三位共享顾问或复用同一批子agent ID，只能标记为 `shared advisory only`。它可以作为资料包或试跑，但不能通过 `--strict-writer-room`，也不能称为理想编剧室运行。

首次检查时可先不带 `--require-run-validation-log`；通过后把实际命令和结果写入 `ledgers/run_validation.tsv`，再带该参数复跑。未记录 run_validation 的产物不能声称“已完成ELO运行”。

## 7. 与 canon 的关系

这个工作流允许“先放开创作，再回填 canon”：

1. 写作时先判断什么最有戏。
2. 若需要新机体、角色、章节顺序或设定迁移，先标为 candidate。
3. 每篇完成后统一判断哪些 candidate 应迁移进 canon。
4. 不要让旧 canon 把新剧情压小。
5. 但已确认硬锁、儿童线边界、版权避险和用户明确决定仍然必须遵守。

## 8. 成功标准

全剧梗概完成后，应能回答：

- 每话发生了什么，为什么必须在上一话之后发生。
- 每话至少有哪些新机体/单位。
- 每话映射了哪些名场面、台词或文化梗。
- 每话玩家玩了什么。
- 每话敌方得到了什么。
- 每话人物关系怎样变化。
- 哪些真实爱好者证词或现实共鸣母题被使用、跳过或延期；直接使用的公开案例是否有来源、边界和发布前复核状态。
- 每章主角团怎样被打击、怎样选择、付出什么代价、获得什么新能力/新限制。
- 每章主角团互相吸引、误会、理解、牺牲和羁绊如何被共同事件塑造，而不是只靠小动作累积。
- 每章关系羁绊如何被日常积累支撑；每次狗血/牺牲/回归前后是否有情绪余温。
- 纪存的机魂记忆如何逐步苏醒，如何让他通过努力、保护和智慧解开谜团与死局。
- 每话留下什么债。
- 每篇为什么存在。
- 全剧如何从机器人文化热爱走向“会开馆的方舟”和共同语言。
- 这份产物到底是路线图、话卡、厚版梗概、台本还是资产 brief。
- 如果称为厚版梗概，它与 V22.10 的差距在哪里，是否已经由厚度审稿补齐。

如果这些答案要靠补充说明才能成立，说明循环没有真正运行。
