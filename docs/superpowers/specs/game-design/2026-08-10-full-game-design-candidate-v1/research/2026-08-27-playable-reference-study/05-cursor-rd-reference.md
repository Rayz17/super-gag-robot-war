## 2. 当前研发假设必须使用的Candidate基线

以下是非穷尽摘要，不是冻结的Build规格，也没有覆盖`00c`全部规则。默认以`00c`作为Candidate基线；若原型要故意比较另一答案，必须把差异登记为对照试验并得到授权，不能静默改写总案：

1. 战术规划默认不限现实时间；世界截止用战术周期、班次或长期时间格；
2. 玩家逐台编辑3—5台常规机体后整队一次提交；
3. 提交前草案免费修改，提交后不免费倒带；
4. 敌方真实计划本轮开始冻结，不能读取玩家未提交草稿；
5. 普通敌人意图诚实；特殊佯动只能按已登记规则隐藏／伪装一个字段；
6. 执行中不弹后见之明改令窗口；预备、主动中止和备用方案事前公开；
7. 身体损伤关闭或改变具体动词，不只扣总HP；
8. 普通移动、攻击和惯用动作不经过角色／权限／机魂审批链；
9. 人物牌战前至多5张，每轮至多用2张；同机战前改动作至多1项；
10. 每场一个主战斗家族，至多一个局部次压力；
11. 基础战不运行气势与请战；焦点／高潮战才使用额外的机会、请战、让台／拆台等机制。它们与玩家选择完整／精简／跳过的观看长度是两条独立轴；
12. 一项任务一个主目标、至多两个次目标，另有身体／撤离账；
13. 城市巡访、残响深潜、返馆之夜和关系时刻是正式产品层，不得因战棋原型而删除；
14. 角色与机体的主线、关键关系和结局离线完整；LLM可关且不裁判硬后果；
15. 外部样本、Fable母型和本目录都只是Candidate研究，不是Canon事实。

## 3. 正确的引用方式

### 3.1 每个建议必须回答五项

```text
reference_id: BV-ITB-01 / BV-PB-20-01 / H-TAC-02 ...
observed_fact: 录像或官方来源实际证明什么
project_hypothesis: 为什么可能适合本项目
guardrail: 哪一点绝不能照搬
validation: 用什么玩家行为或可见证据判通过／失败
```

正确示例：

```text
reference_id: BV-ITB-01 + H-TAC-02
observed_fact: 录像在05:05用编号显示本回合攻击顺序。
project_hypothesis: 提交摘要突出困难冲突，同时让全部行动顺序与同刻组可追溯；编号只是待比较的表达之一。
guardrail: 本项目仍保留估计／未知、身体朝向、承力和共同执行。
validation: 首次玩家能复述困难冲突的先后和原因，并能查到其他结果相关动作怎样进入结算。
```

错误示例：

```text
“照《陷阵之志》做敌方意图。”
“做成《幻影旅团》时间轴。”
“参考机战加精神指令。”
```

这些话没有说明版本、观察点、不可照搬项和失败条件，不能进入任务单。

### 3.2 证据标签

| 标签 | 用法 |
| --- | --- |
| `O1` | 官方平台、正式功能或开发者说明 |
| `V1` | 本轮有时间点的实际视频流观察 |
| `V2/V3` | 教学或长流程，可用于结构但需防剪辑与版本差 |
| `V0-discovered` | 只发现候选录像，尚不能当操作事实 |
| `E1` | 模拟器官方／兼容数据库路径 |
| `M-A/M-B/M-C` | 视频中的模拟器／真实PS2采集证据；只说明该录像链条，不自动等于本机`L1` |
| `L1` | 这台Mac启动指定标题并完成指定观察；当前标题级仍为空，PCSX2主界面启动不算游戏`L1` |
| `H-*` | 本项目待验证假设，不是外部事实 |

不要把`V0`写成“我们看见”；不要把`E1`写成“本机跑通”；不要把`H-*`写成已接受规则。

## 4. C01E02可用的研究映射

本轮研究建议C01E02用隔离灰盒比较以下最小交互骨架；它不是未经试玩即可写死的UI规格：

```text
选机体
→ 画短路线
→ 定终点朝向
→ 选一个主要动作或预备
→ 查看敌方场上意图
→ 查看全部行动先后、同刻组与结果相关事件
→ 优先检查其中2—3个困难冲突
→ 整队提交
→ 共同执行
→ 轮末读取身体、目标和环境变化
```

事件编号、分组行动表与连续时间线是三种待比较的呈现；单轮Replay是可选解释工具。`00c`已经要求完整日志、减速／逐步查看和不同观看长度同结果，但没有把Replay规定为首个原型必做。

来源不是单一竞品：

| 层 | 主要参考 | 仅借用 | 必须保留的本项目差异 |
| --- | --- | --- | --- |
| 敌方意图 | `BV-ITB-01` | 场上箭头、顺序编号 | 来源、时效、估计／未知、冻结计划 |
| 全队规划 | `BV-PB-EA-01`、`BV-PB-20-01` | 残影、共同执行；Replay仅作候选 | 不拖现实秒数；短路线＋动作／预备；全部先后与同刻组可追溯 |
| 动词与预演 | `BV-TBW-01` | 少动词、悬停结果、快速试推 | 提交后不使用无代价Rewind |
| 身体 | `BV-BT-01`、`BV-FM5-01`、`XV-FM4/5` | 轮廓、渐进披露、部位事件 | 先翻译成动词关闭／改变 |
| 焦点接触与尺度 | `XV-ROR`、`XV-RAD` | 战略命令兑现为短具身接触；人类视点与城市后果 | 不增加执行中实时微操，不让笨重操作冒充重量 |
| 人物与高潮 | `BV-SRWOG-01`、`XV-OGS` | 头像、组合能力、台词、音乐、演出分档 | 不使用必中／增伤替代角色打法；高光由搭台产生 |
| 关系与出击 | `XV-SWV` | 城市生活—回应—角色打法—战后余韵 | 不使用默认限时回应、查表好感或战力服从 |
| 机体生活 | `XV-SC` | 旅行、维修、工作、竞技和关系读取同一机体 | 不复制开放世界杂项和维护劳动 |

这不等于立即重写C01E02。若制作人授权进入Demo调整，先用一个隔离切片验证`H-TAC-01—04`。这条战棋切片不应同时塞进人物牌、名场面、Hub和Meta；但任务型探索与独立返馆／关系应开自己的早期切片并行取证，而不是等战棋全部完成。

## 5. 推荐拆成的研发包

这些包是隔离试验，不是必须按字母串行的产品开发顺序。A建立共同状态后，C和D应尽早与战棋线并行，防止探索、返馆和关系再次被推迟成“以后补”。

### `RD-PACK-A` 可读共同轮

**输入：**固定灰盒地图、三台我方、两种敌方意图、一个主目标和两个次目标。

**只做：**

- 场上意图；
- 短路线、终点朝向、主要动作／预备；
- 一种完整顺序／同刻组摘要；
- 视觉上优先突出2—3个困难冲突；
- 整队提交；
- 无弹窗执行。

**不做：**人物牌、气势、长动画、Hub、成长、LLM。

**可选对照：**事件编号／分组行动表／连续时间线三选二做A/B；Replay只有在现有日志和逐步查看不足时另开`H-TAC-05`。

**验收证据：**首次玩家从开局到完成两轮的完整录屏；操作步数；误解点；能否口述困难冲突并追查其他结果相关事件；不是自动测试绿灯。

### `RD-PACK-B` 动词身体

**输入：**A包同一地图，增加两种明确伤损。

**只做：**

- 身体轮廓；
- 四类功能；
- 动词关闭／变化；
- 短句反馈；
- 下一轮方案因此变化。

**验收证据：**同一玩家在伤损前后选择不同路线／任务；能说出变化来自哪个身体功能。

### `RD-PACK-C` 任务型探索接口

**前置：**共同状态与少量操作语法已有纸面定义，不要求A、B全部完成。

**只做：**一个城市巡访节点＋一个残响深潜节点；共用“观察—形成理解—重访／试作—明确提交”的语法与状态卡，但使用不同空间呈现。

**验收证据：**玩家能把操作经验迁移到第二个节点，又能说出两种空间幻想不同；至少一个结果被关系、档案、机体理解或以后一句回声读取，不强制变成战斗Buff。

### `RD-PACK-D` 独立返馆与关系生活

**前置：**一份最小万机馆空间状态；不要求已有完整战后系统。

**只做：**一次共同活动或主动邀请、一次可拒绝／退出的关系选择、一次未出席战斗者仍在生活的可见状态；再让一项机体伤损／修复／生活用途在空间中被人物真实读取，但不要求玩家清维修清单；不以好感值或战力奖励收口。

**验收证据：**玩家能说出人物为何这样回应；关系不是“战后点红点”，拒绝不会被系统判失败，多角关系也不自动收束成后宫。

### `RD-PACK-E` 两套人物牌换题

**前置：**A、B已经能单独玩懂。

**只做：**两套战前编组、每套2—3张可用牌；同一关产生两条不同战法。

**验收证据：**玩家不看设计稿也能描述“这套人为什么这样打”；不是伤害更高的同解。

### `RD-PACK-F` 基础爽与焦点高光

**前置：**无气势版本已经有人愿意重玩。

**只做：**一个基础战漂亮解＋一个焦点机机会；明确比较机制差异，并让每个结果都有完整／精简／跳过三种观看长度。

**验收证据：**玩家能指出自己怎样促成高光；跳过演出仍理解规则；完整演出明显加强情绪。

### `RD-PACK-G` 战后回写

**前置：**一场任务已有部分完成与身体伤损。

**只做：**事实账、发布选择、最多4张后果卡、1—2个由本次结果触发的关系／生活余韵和下一任务读取。它不能替代D包中不依附战果的共同生活。

**验收证据：**玩家在下一屏看到自己刚才的具体选择；没有全清待办冲动。

### `RD-PACK-H` 焦点接触与巨物尺度

**前置：**A、B已经让玩家仅看棋盘就能理解接触的规则结果。

**只做：**同一次已确定的身体接触做三种观看表达：普通精简结算、5—12秒焦点具身兑现、一次从地面人物／城市设施旁观看的特殊镜头。三者输入和规则结果完全一致；执行中不增加前进、瞄准、四肢或临时闪避操作。

**来源：**`XV-ROR`只借“宏观命令进入局部身体段再返回”，`XV-RAD`只借“人类与建筑让巨机重新巨大”。

**验收证据：**玩家能复述接触为何这样结算，并认为焦点版更有重量／责任；选择精简版不丢信息；一轮总等待没有因重复焦点镜头显著增加。

**停止条件：**具身段变成第二套动作玩法；普通接触也被迫长演；镜头只炫技却看不出承力、位移、保护对象或城市后果。

## 6. UI实现的渐进披露建议

主屏只常驻：

- 地图与身体占格／朝向；
- 敌方当前意图和作用方向；
- 主目标＋至多两个次目标；
- 当前选中机体的动作与四类功能；
- 唯一主提交键。

选中单位后展开：

- 短路线、终点朝向；
- 一个动作／预备；
- 能影响它的角色牌；
- 该动作相关的来源与误差。

提交摘要展开：

- 显示全部行动先后与同刻组，并突出接触、争格、承力、触发或备用切换等困难冲突；
- 折叠不重要的路径采样点，但保留所有会改变接触时刻、预备、撤离与目标结果的事件；
- 人物牌消耗；
- 未知区间；
- 环境／目标轮末推进。

详细层可以展开：

- 更细的连续时间线或逐步日志；
- 具体部件与阈值；
- 伤损履历；
- 详细计算与来源链。

禁止把“专家层可查”误做成“新手看不到为什么”。主屏仍须用人话说明动词结果。

## 7. 自动化与真人证据分工

### 自动化适合证明

- 同一输入得到确定结果；
- 敌方不能读取草案；
- 接触组不受选择顺序影响；
- 预备每轮最多触发一次，反应链能终止；
- 完整／精简／跳过演出同结果；
- 伤损状态跨屏传递；
- 信息来源与敌方学习不会无中生有。

### 自动化不能证明

- 玩家一眼看懂；
- 一轮只有2—3个真正困难判断；
- 时间线不像办公软件；
- 身体有重量；
- 人物牌换了打法；
- 名场面是玩家搭出来的；
- 返馆让人想回家而非清待办；
- 燃、爽、笑、爱、色、痛、惊、感动真正成立。

这些必须有真实玩家路径、实际帧、操作录屏和制作人判断。机器PASS与玩家／视觉PASS必须分开记录。

## 8. 竞品资产边界

不得：

- 复制竞品UI布局、图标、字体、地图、角色、台词、音效、音乐或动画；
- 把B站视频帧、整段录像、ROM、ISO、BIOS或游戏文件提交到仓库；
- 用竞品截图训练／临摹成项目成品资产；
- 把社区补丁、兼容层结果或视频作者的观点冒充官方事实；
- 把某个竞品的内部术语直接变成本项目玩家术语。

可以：

- 保存文字化的操作链、信息层次、因果结构和失败倾向；
- 设计原创的灰盒比较；
- 现代原生游戏只使用官方购买版本；模拟器测试只使用用户自己主机导出的固件／BIOS和自己介质转储，并记录必要的小段自有证据；购买记录本身不作为网络镜像授权；
- 把“哪类信息应常驻、哪类应悬停、什么时刻应反馈”转成原创界面需求。

## 9. Cursor每次交付应附的回执

```markdown
## 研究引用
- reference_id:
- observed_fact:
- project_hypothesis:
- guardrail:

## 本次只改变什么
- interaction_or_rule:
- files:
- non_goals:

## 保持的核心不变量
- ...

## 验证
- deterministic_checks:
- rendered_or_playable_evidence:
- human_test_required:

## 结果
- pass / revise / reject / insufficient_evidence
- what_failed:
- next_smallest_test:
```

没有`observed_fact`和`guardrail`的竞品引用，视为灵感闲谈，不得成为实现依据。没有真人证据的交互原型，最多标`machine_checked`，不得标“好玩已验证”。
