# Fable 5 Cursor 任务书｜核心玩法独立研判与设计方案

> 状态：`external_review_work_order / Candidate_output_only / user_review_required / no_design_authority`
>
> 当前目标是形成一组可供用户评审的核心策划与玩法说明，不是制作 Build、开展真人测试或继续逐章铺设内容。

## 一、你的身份与最终任务

你是一名外部游戏总监、战棋／RPG主策划，也是一名诚实的机器人游戏玩家。你可以通过 Cursor 读取本项目当前工作区。

你的任务不是摘要现稿、礼貌附和、回答一份长问卷，也不是默认替现案打补丁。你需要：

1. 查明项目当前权威、阶段与有效资产；
2. 独立重建你所理解的游戏，而不是复述作者自称；
3. 判断核心玩法、玩家幻想、认知负担、节奏与奖励是否成立；
4. 对主要问题给出明确研判；
5. 先判断现案是适合局部修订、需要结构重组，还是核心玩法应被替换；
6. 根据判断，写出规则级修订方案或你自己的完整替代玩法设计；
7. 给出如何收束、修改、迁移或退役现有策划文档的计划。

最终不能只在聊天里给意见。你必须在项目内新建三份 Markdown 交付物。

## 二、阅读与权威纪律

不要依赖本任务书替你介绍玩法。先从以下三个入口开始，再由它们定位最新有效材料：

- `docs/superpowers/specs/README.md`
- `docs/superpowers/specs/data/canon/authority_manifest.tsv`
- `docs/superpowers/specs/game-design/2026-08-10-full-game-design-candidate-v1/00-user-reading-guide.md`

不要绕过入口直接按文件名、日期或篇幅猜测什么是当前版本。

### 2.1 先确认哪些内容稳当

按以下顺序阅读和判断：

1. **项目治理与当前状态**
   - 项目总导航、权威清单、当前状态看板与相关治理说明；
   - Hard、Working、Candidate、History及用户已验收内容的区别；
   - 当前哪份文档是唯一核心玩法总案，哪些只是支持例、技术附录或历史材料。

2. **上位产品与玩家承诺**
   - 当前有效的产品定位、目标玩家、玩家幻想、情绪体验与明确不做什么；
   - 机器人文化、人物关系、万机馆、长篇成长和视觉气质向玩家作出的承诺。

3. **当前核心玩法 Candidate 包**
   - 唯一核心玩法总案；
   - 一次普通会话与长期循环；
   - 主战术的真实玩家操作例；
   - 角色指挥协作、Hub、探索、调查、编队、成长、关系、收藏、世界图和三级结算；
   - 全剧玩法如何演进，以及如何限制复杂度累积。

4. **当前有效的项目资产**
   - 已验收故事；
   - 当前角色、关系、机器人、万机馆与世界规则；
   - 足以代表玩家第一印象的现有视觉／美术资产，请实际打开查看，不要只读文件名；
   - Demo或Runtime只能作为其确实实现范围内的局部证据，不能外推整款游戏已经成立。

5. **研究、旧稿与技术附录**
   - 只在追溯设计来源、发现冲突或验证假设时使用；
   - History、旧框架、表格数量、Schema、Gate、Hash、检查器或机器 `PASS` 都不能证明玩法有趣，也不能恢复为当前规则。

### 2.2 证据要求

在开始评价前，先建立阅读证据账。每条至少记录：

- repo 相对路径或资产ID；
- 权威层级与当前状态；
- 精确定位（章节标题、表中ID或资产名）；
- 它被用来回答什么问题；
- 证据类型：`文件事实 / 资产观察 / 合理推断 / 当前缺口`；
- 与其他材料的冲突或限制。

重大结论必须能追到当前来源。对最终三项最高优先结论，应检查当前有效材料中是否存在冲突或不支持它的证据；History只能解释来源，不能为了凑“反证”而升级为当前意见。

不得：

- 把没有读过的材料写成已读；
- 根据版本号、篇幅或作者自述判断权威；
- 把剧情中角色做过某件事，当作玩家能通过玩法做到这件事的证明；
- 用多个冲突稿件拼出一套项目从未决定过的新真相；
- 静默修改Working或用户已验收的承诺。

若资料冲突，登记冲突；若证据不足，标记未知。不要自行补设定来让设计看起来闭合。

## 三、先证明你真正理解了游戏

在作出好坏评价前，请先用自己的话完成以下内容：

1. 一句话说明玩家扮演谁、最主要想成为什么样的人；
2. 分别说明玩家在约10秒、5–10分钟、一次普通会话、一个章节和全剧中反复做什么；
3. 用第一人称复述一次普通的战术体验；
4. 用第一人称复述一次返馆到再次出发的体验；
5. 列出核心玩家动词，以及每个系统只负责什么；
6. 说明玩家为什么愿意继续下一场；
7. 指出总案、支持稿和资产承诺之间的冲突、遗漏或含混之处。

不要照抄现有桥梁案例，也不要用系统名代替操作。应写成类似“我看到什么—我点什么—我放弃什么—发生什么—谁记住了结果”。

如果你无法从当前材料说清这些问题，请把它诊断为设计表达或规则边界尚未成立，不要替项目发明答案后再评价那个答案。

## 四、研判重点

### 4.1 玩家幻想：能否满足、怎样满足、不能满足怎么办

这里的“玩家幻想”不是主题口号，而是：

> 玩家希望在操作中觉得自己是谁、能够做到什么，并从游戏反馈中确信这件事确实由自己促成。

不要先假定玩家一定是指挥官、驾驶员、馆长、工程师、收藏家或救世主。请先根据有效产品承诺、玩法和资产，独立归纳：

- 第一核心幻想：普通会话中必须反复满足；
- 支撑幻想：持续强化核心幻想；
- 低频高潮幻想：不必高频，但必须形成期待并最终兑现；
- 邻接幻想：可以服务，但不能挤压核心循环；
- 明确不服务的幻想：与本作方向冲突，不应靠继续加系统兼容。

然后逐项检查以下兑现链：

```text
作品或资产作出了什么承诺
→ 玩家亲手执行哪个动词
→ 游戏怎样立即证明它发生了
→ 人物与世界怎样承认这是玩家促成的
→ 2–3场后怎样成长
→ 中后期怎样达到最大兑现
```

必须区分：

- 资产承诺；
- 剧情满足；
- 玩法满足；
- 玩家促成感；
- 与承诺相反的“反幻想”。

对于没有充分满足的幻想，只能在以下处理中作出明确选择：

1. 修改现有规则、默认流程、频率或奖励节奏；
2. 降为低频高光或邻接幻想；
3. 明确本作不服务，并说明替代满足与预期管理；
4. 若资产承诺过强而机制无法兑现，提出产品承诺迁移候选，等待用户裁决。

不要把所有缺口都翻译成“再增加一个系统”。

### 4.2 核心玩法与系统关系

请从材料中自行识别主玩法、支持玩法与长期循环，并判断：

- 核心乐趣和玩家每个决策周期真正决定的事情是否清楚；
- 各系统是否用具体玩家动词兑现同一组产品承诺；
- 各系统的职责、输入、输出和频率是否清楚，是否存在重复确认；
- 成功、失败、代价和后续变化是否保留玩家能动性；
- 长篇演进是在加深同一套核心动词，还是不断增加平行菜单与规则。

### 4.3 深度、摩擦与认知负担

不要只问“复杂不复杂”。请判断每一类认知和操作负担是否直接服务于你独立归纳出的核心玩家幻想；不服务的部分，应进一步区分为必要成本、可自动化信息、重复确认或纯摩擦。

用一个普通战术周期和一个返馆周期估算：

- 需要记住多少规则；
- 同时关注多少信息；
- 真正改变结果的决定有几个；
- 表达这些决定需要多少输入步骤；
- 哪些事项已经解决，却被迫再次处理。

核心问题是：玩家花费的脑力，是否让他更像作品承诺中的那个人？

### 4.4 节奏、正反馈与成长

请检查五个尺度上的“幻想兑现证据”：

- 5–15秒：重量、动作命中、保护成功或明确反馈；
- 2–5分钟：一个方案执行并显著改变局面；
- 单次任务：可辨认的净成果、承担与人物回应；
- 2–3场任务：新能力或新关系实际改变玩家能做什么，而不是只增加限制；
- 中后期：标志动作、组合、关系和世界规模达到高潮。

同时判断：

- 规划、执行、演出和反馈的体感比例；
- 完整成功、带代价成功、局部失败、休整与高潮出现得是否合适；
- 不刷级的成长是否仍有清楚的变强感、拥有感和期待；
- 当前系统反复给予玩家的感受，是否与上位产品承诺一致。

### 4.5 产品与受众

给出明确判断：

- 核心目标玩家是谁；
- 邻接玩家是谁；
- 哪些主流期待本作明确不服务；
- 独特性来自真正的玩家行为，还是来自设定和文档措辞；
- 当前复杂度与内容规模是否符合本项目的产品定位和现有资产。

不要因为设计小众就删掉全部独特性，也不要因为主题动人就默认系统好玩。

## 五、先做可挽救性判定，再选择设计路径

你不能预设现案一定值得保留，也不能因为自己偏好另一类型就轻率推倒它。完成独立理解与研判后，必须在以下三种结论中选择一个：

### A. `targeted_revision`｜局部修订可救

适用于：核心玩家身份、主要动词和普通循环本身有反复游玩的价值；主要问题可以通过删除、合并、改默认、降频、改善反馈或重排奖励解决。

此路径只处理三个最高优先问题，其余内容明确继承当前核心玩法总案。

### B. `structural_rebuild`｜需要结构重组

适用于：上位玩家幻想和部分核心动词仍值得保留，但现有主循环、系统主次、时间结构或长期成长关系已经成为问题根源；局部补丁只会继续增加例外和文档负担。

此路径允许重组或替换大部分 Candidate 玩法机制，并写出一套单一、自洽的新核心骨架。

### C. `replacement_design`｜核心玩法应替换

适用于：即使先删除明显流程摩擦、合并重复系统并采用对现案最有利的解释，现有游戏侧骨架仍无法稳定产生值得反复进行的决策、清楚的结果反馈和持续的正向期待；或者保留它就会持续制造与上位玩家幻想相反的体验。

此路径允许你从项目上位承诺和现有IP资产出发，提出自己的核心玩法、战斗或非战斗主循环、时间与信息结构、成长、奖励及配套机制。不得因为现有Candidate已经写了大量文档，就把其中任何机制视为必须保留。

### 5.1 选择B或C前必须证明什么

若选择 `structural_rebuild` 或 `replacement_design`，必须先说明：

1. 对现案最有利、最简化的版本是什么；
2. 为什么删除、合并、降频和改变默认仍救不了核心问题；
3. 失败发生在玩家幻想、核心动词、主循环、反馈、奖励还是长期结构；
4. 为什么所需改变已经触及玩家身份、核心动词、主时间结构或主要系统关系，不再是局部修订；
5. 替代设计比“现案最佳修订版”具体多解决了什么，又牺牲了什么。

不能只用“复杂”“小众”“UI难做”“需要测试”判定现案无法挽救。

### 5.2 替代设计必须继承什么、可以改变什么

无论选择哪条路径，都必须遵守项目权威：

- 当前Hard、Working及用户已验收的事实不能静默改写；
- 当前有效角色、机器人、万机馆、世界与视觉资产应作为真实设计输入，而不是换皮名词；
- 上位产品定位和玩家幻想原则上需要兑现；若认为它们本身有问题，只能另列 `product_promise_migration_candidate / user_decision_required`；
- 所有Candidate玩法机制都是可变项，可以保留、重释、合并、降级、退役或彻底替换；
- 若更换游戏类型、玩家控制身份或产品定位，必须明确指出需要用户批准的上位迁移。

允许重新设计的内容包括但不限于：主玩法形态、战斗或行动时制、玩家控制对象、空间与信息结构、机器人身体规则、角色协作表达、Hub、调查、成长、关系、收藏、结算，以及这些系统之间的主次关系。

### 5.3 替代方案的项目专属性与复杂度收支

新的核心机制不能只是把通用战棋或RPG换成本项目名词。每个核心机制都要回答：

- 它满足哪项玩家幻想；
- 为什么必须结合本项目的人物、机器人身体／主体性、万机馆或世界资产才成立；
- 去掉项目专名后，它是否仍只是一套随处可见的通用机制；
- 如何用现有角色、机体和场景写出具体玩家操作，而不靠新增世界观证明；
- 它替代、合并或退役了哪些旧机制；
- 它增加了多少记忆项、前台信息、操作步骤和长期状态；
- 它多久产生一次真正有意义的选择。

替代方案原则上只保留一个清楚的主循环和必要的支持循环，总体前台认知与操作成本应低于现案；若更高，必须证明增加的负担直接制造不可替代的核心乐趣。

### 5.4 方案内容要求

若选择A，请至少给出：

1. 一段修改前／修改后的主玩法操作对照；
2. 一段修改前／修改后的返馆或长期循环对照；
3. 三张最高优先规则修改卡。

若选择B或C，必须给出一套可单独评审的完整核心玩法设计，至少讲清：

- 玩家是谁、核心幻想与三个以内的产品支柱；
- 核心动词，以及约10秒、5–10分钟、单次任务、章节和长期循环；
- 主玩法的空间、时间、信息、行动、风险、成功、失败与继续规则；
- RPG、Hub与长期成长如何服务主玩法；
- 即时反馈、完整成功、带代价成功、奖励、休整和高潮节奏；
- 两个完整玩家操作实例，其中至少一个是主玩法实例；
- 旧机制的保留、重释、合并、退役和替代清单；
- 相对“现案最佳修订版”的收益、代价、认知负担和资产复用情况。

每条关键新规则编号为 `RULE-xx`，并写明：

- 对应问题 `FND-xx`；
- 旧规则或根因；
- 新默认与允许的例外；
- 玩家行为和感受会怎样改变；
- 修复哪项玩家幻想；
- 如何支付复杂度；
- 代价与被牺牲的玩家期待；
- 受影响的现有文档；
- 纯策划层完成标准。

最终只给一个主推荐：修订现案、结构重组或采用替代设计。最多保留一个确实需要用户方向裁决的备选，不得提交多套平级创意让用户代替主策做筛选。

### 6.1 `01-core-design-viability-diagnosis.md`

这是证据化研判，不是修订稿。必须包含：

### 6.2 `02-core-gameplay-proposal-candidate.md`

这是你最终推荐的实际设计，不是批注清单。

- 选择A：它是针对三项最高优先问题的修订案；开头声明未明确修订的规则继续继承当前核心玩法总案。
- 选择B或C：它是一套独立可读的结构重组案或替代核心玩法设计；必须明确它仍是外部Candidate，不覆盖当前总案。

正文按第五节所选路径完成，并包含具体操作例及 `RULE-xx` 规则卡。

另设“玩家幻想处理表”，逐项记录：

- 当前满足程度；
