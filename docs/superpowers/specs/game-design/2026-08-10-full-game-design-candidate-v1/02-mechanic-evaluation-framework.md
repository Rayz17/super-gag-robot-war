# 机制研究与设计统一评价框架

> Status: `candidate_method / applies_to_all_gameplay_deliverables`

## 一、用途

本框架同时用于三件事：

1. 拆解外部游戏，避免只列作品名和主观感想；
2. 设计本项目机制，避免只生成“导航、预知、经营、收藏”等名词；
3. 评审原型，区分规则完整、代码可跑、玩家理解和真正有趣。

每个机制使用同一张机制卡。字段定义见 [data/mechanic-evaluation-schema.tsv](data/mechanic-evaluation-schema.tsv)。

## 二、机制成立的五层合同

### 2.1 身份合同

- 玩家此刻扮演谁：前线驾驶员、作战室指挥者、馆内负责人、调查者、模型/工程协作者，还是多席位切换者？
- 这个动词为什么属于该角色或机体？
- 如果把角色名字换掉，机制是否仍完全相同？若是，角色化不足。
- 玩家能提案、选择代价或授权什么；哪些身体和决定仍由角色/驾驶员/机魂拥有？

### 2.2 决策合同

- 5-30秒内的核心动词是什么？
- 同一状态下是否至少有两个合理方案，而不是唯一正确按钮？
- 信息是否有来源、时间戳、置信度和盲区？
- 选择消耗行动、注意、时间、能源、权限、关系还是暴露度？
- 敌人、环境和队友怎样反制或拒绝？

### 2.3 反馈合同

- 操作前能预览什么，哪些必须保持不确定？
- 提交时有什么不可逆窗口？
- 执行中通过地图、机体全身动作、声音、通讯、UI和镜头看见什么？
- 成功、部分成功、失败和拒绝能否一眼区分？
- 玩家能否说清“是谁做了什么、为什么发生、代价是什么”？

### 2.4 持续合同

- 结果写回哪些状态：机体伤损、驾驶关系、机魂信任、权限、资源、地点、敌人学习、世界路线？
- Checkpoint、Episode cut、Operation和Mission Clear分别保存/结算什么？
- 失败是否产生可继续的尊严状态，而不只有重开或人物死亡？
- 成长是否增加判断方式、协议、组合和表达，而不是逼玩家刷数值？

### 2.5 生产合同

- 机制能复用多少章、多少地图、多少角色？
- 需要哪些UI、地图、动画、音效、文本、AI和资产？
- 最小灰盒能否在一到两周内回答一个明确问题？
- 如何教程化和无障碍化？
- 哪项真人证据才允许升入正式内容生产？

## 三、本项目专用十项测试

| 测试 | 通过问题 | 常见失败 |
| --- | --- | --- |
| 机器人身体测试 | 选择是否最终变成可读的移动、姿态、碰撞、攻击、保护、变形或损坏？ | 全靠菜单数值和对话解释 |
| 角色身份测试 | 操作是否体现纪存、七海、白鸢、工程组或具体驾驶/机魂的边界？ | 每人一个换皮Buff |
| 非全知测试 | 信息是否带来源、时效、置信度、盲区和欺骗可能？ | 全局视野等于透视答案 |
| 非万能指挥测试 | 玩家能否被权限、距离、机魂拒绝、工程现实或注意力限制？ | 玩家直接控制所有身体 |
| 多解测试 | 标准战术是否至少有两种可行方案和不同代价？ | 单一最优解谜题 |
| 反制测试 | 敌人是否能干扰、诱骗、封锁、抢先、撤退或迫使改计划？ | 敌人只是血条 |
| 故事同义测试 | 游戏胜利是否就是故事冲突的可操作版本？ | gameflow另造任务和装置 |
| 轻练级测试 | 不刷等级能否靠理解、关系、功能装备和新协议成长？ | PP/Credits/数值墙主导 |
| 辅助调剂测试 | 非战棋玩法是否短、轻、可复用并有共同输出？ | 每章一个孤立小游戏 |
| 人类证据测试 | 冷启动玩家是否理解、产生偏好、愿意再玩？ | 作者自测或自动PASS冒充验收 |

## 四、研究样本记录法

每个外部样本至少记录：

- 官方产品页、手册或开发者说明；
- 类型和玩家身份；
- 一分钟、一回合、一局和长线循环；
- 信息呈现、行动经济、失败、成长和内容复用；
- 最值得迁移的一个机制；
- 为什么适合本项目的角色、故事和制作体量；
- 不可照搬的风险；
- 准备通过哪个原型验证。

“像某游戏”不是设计结论。只有被拆成可测试假设，才进入本项目候选池。

## 五、设计评审顺序

1. 先评玩家身份和核心动词。
2. 再评信息、选择、代价、反制和失败。
3. 再评人物/机体边界与故事同义。
4. 再评长期状态、成长、经济和系统互锁。
5. 最后评资产、UI、教程、可访问性和制作成本。
6. 写出最小原型问题，不直接承诺正式实现。
7. 原型通过内部功能检查后，进行真人冷启动试玩。
8. 用户明确裁决后，才进入正式系统、章节、Canon或资产迁移。

## 六、成熟度与状态字段

每项机制同时记录两条轴：

- `authority_status`: `hard | working | candidate | history | user_direction`
- `evidence_level`: `M0 | M1 | M2 | M3 | M4 | M5 | M6`

例如“白鸢没有未来视”可以是 `working + M1 boundary`；“白鸢有限预演按钮”可以是 `candidate + M2`；某次隔离原型可以是 `candidate + M4`；只有目标玩家试玩和用户接受后才是 `candidate_approved_for_migration + M5`。权威高不代表玩法成熟，代码可跑也不代表规则已获权威。

## 七、淘汰规则

机制满足任一项时，优先删除、合并或退回：

- 只能靠专有名词区别，操作与另一机制相同；
- 没有反制、失败或机会成本；
- 需要角色违背Canon权限或常识；
- 只把剧情结论做成点击确认；
- 只服务一个场景且需要独立UI/资产；
- 奖励不进入共同状态或与主玩法无关；
- 迫使玩家重复刷取才能看主线；
- 需要无限回退才能让高复杂度成立；
- 使主角权能掩盖基础战棋无趣；
- 无法提出可证伪的原型问题。
