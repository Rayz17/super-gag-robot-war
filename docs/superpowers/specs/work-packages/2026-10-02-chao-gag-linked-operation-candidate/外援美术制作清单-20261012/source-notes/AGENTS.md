# 项目工作入口

本文件不改变剧情、人物、机体或美术的既有权威。修改这些内容前，仍须按
`chao-gag-canon` 查询当前来源；用户最新明确要求优先。

## 项目游戏制作方法

游戏原型、关卡、机体、交互、演出和资产工作均先读
`docs/superpowers/specs/production/游戏制作方法与工程约定.md`。
使用同目录的`体验批次模板.md`补全或复用当前批次报告，不另建平行进度台账。

这份方法只规定全项目怎样制作、组织工程与判断质量；当前 Demo 的地图、机体、
镜头试验值、代码入口、批次和待办写在对应任务规格及原台账，不反写成通用方法。

- 按“起始局面—实际输入—可见后果—下一决定”组织施工，同时绑定原要求与完整范围。
- 先复用当前能力、效果、空间、命令和事件接口；通用改进须在第二种对象/局面验证，
  不以角色名或地图名打补丁。预测、执行、回放、HUD与演出保持同一结果来源。
- 正常镜头构图先于资产细化；实际制作源、材质、绑定、动作、声音与加载位置相连。
  程序制作和自动检查可用，但不能以文件数、测试数或单帧替代实际质量。
- 每批的主线是一段完整体验。代码/工具工作须对应其中一步或有证据的阻断；
  无关维护保留到原待办，不能抢占主线。美术量实际画面，动作检查连续过程，声音实听。
- 输入响应、性能、无障碍随制作检查；同一主要缺陷两次有效修复未改善时改变方法。
  在原台账的`defect_ledger`记录尝试与方法变更；计划换法不等于已经执行。
- 接续当前会话批次，不替其他会话填写实测、认可或完成状态；不自动发送指令、
  发起外包或要求用户逐批查漏。恢复时读当前台账、本段原规格和上次真实结果。

## 工务城完整整改

仅在进行工务城整改、制作、验证或交付时适用：

1. 先运行 `python3 scripts/gongwu_production_flow.py preflight`，再读它列出的
   `制作流程.json`、`05-施工与验收.md` 和现有 `实施进度-20261010.json`。
2. 范围是全部 52 包及其关联原条目。首关、样板和专关是施工顺序，不能代替完整交付。
3. 沿用主工程 `game-godot` 和现有启动入口。接续已有批次，不重置其他会话的工作。
4. 每批先选一段真实游戏体验，将规则、输入、画面、动作和声音一起落实到主工程。
   当前批次只是局部时，记录局部证据和准确缺口，不把整包标为完成。
5. 资产实际使用参考图；先审源图、结构和正常战棋镜头，再推广到同类资产。
   连续两轮仍有同一主要缺陷，重查资产、构图或制作方法，不继续堆同类细节。
6. 继续使用 `scripts/run_gongwu_runtime_check.py` 做原有脚本检查。
   其成功只证明声明的脚本范围；不能替代原生输入、画面、动作、实听或首玩。
7. 批次证据用 `python3 scripts/gongwu_production_flow.py review <记录.json>` 核对；
   整体交付前必须运行 `python3 scripts/gongwu_production_flow.py delivery`。
   来源、当前文件或证据不匹配时修复对应问题；不得删除要求或改阈值来变绿。
   新评审使用v2格式，绑定项目制作方法和实际体验记录；可用`experience-template`
   输出批次模板。在途旧记录保留历史核对用途，不倒填成新方法验证，最终关单须更新。
   `preflight`同时列出当前`production_focus`与待换法缺陷；这不阻止修复工作。
   `review`检查画面量测、实际评审记录及反复失败的处置，不能仅刷新摘要沿用旧通过。
8. 上述检查只核对来源、范围及证据结构，不会自动判断好玩或批准美术。
   用户认可单独保留；不得自动签署、发送消息或安排外部试玩。
