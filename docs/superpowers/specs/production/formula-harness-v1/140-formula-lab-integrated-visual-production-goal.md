### 0.1 2026-09-26 用户定位：demo 融回公式台的整体制作

**公式台是本项目打磨玩法、游戏机制与表现方式的共同制作平台，也是建立在 Godot 上的游戏专用基础层。** 当前 C02 demo 的成果回到这里，后续各类玩法沿同一条制作链发展。Godot 继续承担底层运行；公式台承担本作的规则、交互、场景组织、演出、状态衔接和内容生产。

本次用户明确要求“精良打磨，把整个游戏不同玩法的呈现和标准都定出来”。执行含义如下：

- **战斗 demo 成为战术公式的制作输入。** 保留读招、未来格瞄准、逐机行动、局部接力、团队编排、精神指令与人物能力的已做能力及试玩教训。先保持可比较的规则与真实结果，再提取共享模块；旧公式的“全队一次提交”不能反向抹掉后续已授权的操作实验。

## 1. 完成后应得到什么

### 1.1 四项相互验证的成果

1. **有实际观看与操作证据的金标研究。** 覆盖§4全部实际采用的参考层；能复述玩家经历了什么、画面和声音怎样反馈、规则如何影响判断，明确视频观察与亲手操作的区别。
2. **本项目统一的体验语言与可执行标准。** 视觉、手感、屏幕层次、菜单操作、教学、对白和反馈共同服务本作气质。每项重要规则均有“具体金标证据→借鉴/舍弃理由→本项目改造→适用场景→验证办法”，不能只有抽象口号或色值。
3. **七个新增章节场景验证包。** 从当前有效的定稿Reader与对应游戏机制解构中，给七公式各选一个有明确主公式的章节场景包；可以含必要的其他公式与衔接。与旧假设场景并存，具备可玩情境、人物动机、玩家行动与后果，并使用足以检验实际表达的Candidate美术。
4. **经过真实体验验证的可复用生产。** 七公式、不同输入与多公式组合都能由有来源的材料生成、编辑、重建，支持新的章节包；成功不仅是流程走通，还要达到研究建立的体验标准。

### 1.2 原公式台范围继续保留

- 轨 A：七公式分别实现玩法、交互、空间、美术、台词、角色存在感、声音与演出的融合；138中的借鉴假设由本次实机研究验证修正，不能把旧推测写成已证标准。
- 轨 B：Reader＋游戏解构＋资产 → 有来源的制作解读 → 可执行缺口 → 补充/必要裁决 → 可编辑配置、场景与状态绑定 → 可玩产物 → 修改后重建。
- Reader或解构不足时，由制作侧提出带来源的Candidate适配方案；不能宣称任意文本都已自动理解正确。
- 普通镜头、坐标、布局、素材裁切和适配由制作侧承担，不让用户填写底层制作字段。
- 每公式至少两个有实质差异的完整输入配置，并有真实操作与结果；每公式至少一个来自本次新增章节包。已有假设包达到标准后可作为另一输入，不要求十四个新增章节包。同题两种打法、单句改写、换色不算第二实质输入。
- 至少两套实质不同的多公式组合，经上述链路生成、编辑、重建并真实玩通；体现章节包中的因果衔接，不把无关场景拼成菜单巡回。支持范围内换输入不改公式代码。
- 已登记预设都要有验证或明确capability_gap；TAC_T0–T11等继续是能力面，单机共同回合不冒充多机协同。缺口有后续实现或必要裁决，不因记账而永久排除困难能力。
- 复用四件套：`formula-input-contracts.tsv`、`formula-asset-specs.tsv`、`formula-runtime-capability.tsv`、`formula-scene-types.tsv`。研究与体验文件为其制作依据，不另造平行管理框架。

### 1.3 研究应解决的问题，不预先冒充体验标准

研究要回答：玩家如何进入情境；看哪里、选谁、做什么；怎样理解规则、风险与取舍；确认、撤销、切层怎样自然；结果如何被身体、空间、角色与声画表达；什么使人满足并愿意继续。

这些是研究问题。必须从具体观察中形成可比较的表达方案，再通过本项目切片验证。不能先写“清楚、自然、有回报”六条通用检查，然后宣布已有标准。固定派遣与线性对白不强造分支；需要判断的玩法不能变成照提示逐项确认。

整体样例要体现原始游戏吸引力：玩家主动布置形成战术强解或高光，演出兑现力量并回到仍成立的战场；发现或生活选择带来人物、空间或下一次玩法的变化。人物不只有解释、拒绝、签收职能；不要求每段同时承担燃、爽、笑、痛。

### 6.3 第三阶段：选定七个章节场景验证包

建立`artifacts/formulas/experience-foundation-v1/chapter-slices.md`，给叙事、战术、调查、探索、结算、世界路线、Hub各选一个主验证包。七包可以来自同章不同场景，也可含多个公式；同一物理包不能重复计成七个新增包。每包写清：

- Reader版本与具体段落、机制解构出处、人物/机体及有效身份源；
- 进入时的处境、人物动机、玩家目标、可作判断、操作过程和退出后的真实后果；
- 主公式、必要衔接、要验证的统一语言条目与对应金标片段；
- 既有资产与按§5.4新增的验证资源，哪些裁切/镜头/动作属于制作适配；
- 成功、失败、取消或未开始中哪些适用于本情节；可独立启动的前置状态和结束边界。

选材与普通制作解读由主对话负责，不把七个包的策划交给用户。改动正式情节、核心机制或身份时才裁决。确实没有合适定稿场景的公式，给出具体来源缺口与最小Candidate适配方案；继续其他包，不能把假设场景悄悄算作已完成的章节包。

保留原假设包作为规则实验和回归。新增七包作为另一组可选择的章节体验入口，明确来源和Candidate身份；普通游玩界面使用简明场景名与操作语言，不展示制作审计字段。

### 6.4 第四阶段：制作切片并据统一语言评估、修复

先选最能验证共同语言、且资源和情节来源完整的代表包打通，再扩展七包；代表包通过不外推到其他包。必要时以相同局面作少量表达对照，比较金标观察、本项目改造和实际效果。不能把临时资产缺陷误判成玩法失败，也不能因它是Candidate就豁免身份、动作、可读性或反馈。

此时再独立评估旧Demo与新增切片：以已建立的具体语言条目为基准，覆盖进入、判断/操作、后果和跨公式返回。复用仍对应当前版本的已有实录；改版、缺证和问题处补实际操作。制作侧先完成缺陷检查，再组织实际不熟悉该段的人短试玩；观察其理解和行为，不能由熟练代理冒充首玩者，也不要求玩家先读设计文档或签大表。

评估与修复归入`artifacts/formulas/experience-foundation-v1/experience-review.md`，每条有包/版本、操作、可见现象、参考与语言条目、玩家影响、原因确定性、修复及复测。区分已观察、仅代码推断和待证。先修妨碍判断/操作/真实因果的问题，再修节奏、角色、声画与回报；每次完成一个从进入到结果的体验改善。

A的困惑与工程表达、事实卡键盘焦点、F的可解性等是已有疑问，不是研究前就定好的全部结论。不能以“多写四句教学”“只差签字”替代这轮工作，也不因新增章节包而丢弃已完成且仍有效的底座。

### 6.5 第五阶段：复用、组合与最终交付

所有共享改进回到输入合同、消费者和生产链。七个新增章节包都能由来源输入生成、编辑、重建；每公式另一份实质输入也达到相应标准。至少两套不同多公式组合完成真实操作，前段选择确实影响后段，Full/Skip、取消、重试保持真实因果。

沿用四件套更新能力面；TAC_T0–T11等逐项核实实现/验证/缺口，不为过门只测最简单档，也不把复杂玩法拆成互不相干的小演示。受真实重大裁决约束的项单独列出，不阻塞无关制作。

交付四份有证据的研究/设计/选材/评估文件、七个新增章节包及所需Candidate资产、保留并复用的假设包、每公式两输入与两套组合证据、可编辑输入和重建入口、四件套与准确范围的用户体验验收。上述文件路径为计划产物；未产生前不能算交付，也不为形式先创建空PASS文件。

## 7. 质量门

以下是通用质量底线；具体体验标准必须由§6的实机研究、项目取舍和切片验证形成，不能只凭本节判定体验成立。

- **事实与输入**：身份/来源正确；读写与状态因果有证据；摘要前不写世界，Skip 不改变结局。
- **真实游玩**：正常键鼠可操作，错误/取消/重试清楚；自动驱动不能偷设成功、瞬移、改时间来凑图。
- **空间与接触**：相机/地面/脚点/单位朝向一致，双方与接触对象可识别，起势→命中→余波→返回连续。
- **声画与角色**：统一规格与身份，合法动作、真实透明边缘、可读 UI/台词，音效与命中同步；不是只有呼吸漂浮。
- **复用与重建**：真实输入变化进入可玩产物，缺口可执行，来源可追溯；不要求用户手填全部底层适配。
- **验收分级**：机器通过≠实际画面通过≠用户喜欢≠Canon/Runtime 晋升。所有未验收项保持明确状态。
- 仅在冻结输入和跨任务交接保留必要哈希；不每帧哈希、不反复全项目重审、不以流程复杂度代替质量。

**140完成须同时满足：** 实际研究证据覆盖所借参考层；统一语言有来源、有本项目取舍且经过切片验证；七个新增包来自有效定稿章节并配有必要Candidate美术；七公式两实质输入与两套组合、生成/编辑/重建均有实际证据；体验满足据研究形成的具体标准与上述质量要求；适用的用户验收完成。仅完成研究文档、通用检查表、工程测试或签名不能替代其中任一项。未达到目标的动作、声画、内容和能力仍是开发工作，范围取舍需明确裁决。

`formula-desk test/swap/freeze` 仍按原合同使用。137 的四门和旧手感模板检查的是其明确覆盖的范围；`freeze` 放行不自动等于本目标完成，一个档位的签收不外推到整公式、所有输入或整体视觉。先给可评体验，再记录准确范围的验收，不以凑齐签名收尾。

### 8.1 模型分工与额度纪律

- **用户最新裁决：不固定 Sol，也不把复杂工作永久绑定 Astra。** 主对话负责制作决策、接口与验收，可按任务难度、工具/模态、风险和模型实际表现，为 subagent 选择任何当前接口支持的模型，并保留最终整合责任。
- 以保证质量前提下的**总 token/额度消耗最小**为选型目标，包含上下文、推理、工具输出、返工与复审；不能只按模型名称、单次速度或单价判断，也不降低既有验收标准。
- 简单、边界清楚、可直接验证的查找、机械修改、小范围修复、现成测试与证据整理，在能力适配且接口可调用时，**尽量优先 `gpt-5.3-codex-spark`**。不要求全部任务先试 Spark；复杂状态因果、跨模块设计、身份/空间审图等可直接选胜任模型。
- 以当前 **subagent 接口**实际模型与 reasoning 支持为准，显式指定所选模型/档位；主任务模型列表或账号可选项不等于 subagent 一定可调用。Spark 不支持时选合适替代并简短说明，不循环调用，也不擅自新建用户任务来绕过限制。
- 短上下文通常 `fork_turns=none`，只交必要文件/背景/证据；一般 1–2 个有用并行任务，写清所有权、输入、交付和停止点。不整段历史 fork，不为用 Agent 而拆任务；主对话一次即可做完的小改动可直接完成。
- 用定向测试和实际结果检查交付；一次明确纠正后仍在同类问题上失败，或发现任务超出所选模型能力，及时换模型/重拆任务/主对话接管，不无限低能力重试，也不让高能力模型重复重做全部普通工作。
- 定向读取与风险比例验证；普通修复不要重跑所有公式/Canon 全套，只有迁移相应权威才跑相关治理门。
- 每完成可见增量更新短交接：产物、证据、未通过、下一刀。140 只更新目标/裁决，历史日志归证据目录，避免再次膨胀。
- 换模型属于已授权的常规分工，不必逐次申请；升级时简短说明原因。新增付费服务、购额或改变用户计费设置仍需另行授权。

事实边界：OpenAI Docs 将 Spark 定位为快速、能力较低且有独立用量限制的模型；这不保证它必然更省总 token，也不保证当前 subagent 支持。见[官方说明](https://learn.chatgpt.com/docs/agent-configuration/speed#codex-spark)。以上是动态选型策略，不是固定模型能力排行榜。
