## 1. 完成后应得到什么

交付 **Godot 可复用游戏框架与内容制作能力，以及能证明“值得玩、玩得懂、结果可信”的完整候选体验**。第一次进入的人能理解自己正在做什么；需要判断的地方有可理解的取舍；动作、人物和环境把结果演出来；换一份实质不同的输入仍然成立。

公式台不绑定正式章节，但样例必须有足够的任务情境、人物动机和可感知回报。允许用既有中性 Lab 人物和 Candidate 输入完成这一证明；不以“这里只是测试台”解释空洞，也不把正式 C01/C04 内容制作或全剧长线系统实现新增为本目标前置条件。

### 1.1 轨 A / B 的共同终态

- 轨 A：七公式分别达到 138 §2.3 的玩法、交互、空间、美术、台词、角色存在感、声音与演出融合要求。
- 轨 B：Reader＋游戏解构＋资产 → 有来源的制作解读 → 可执行缺口 → 补充/必要裁决 → 可编辑配置、场景与状态绑定 → 可玩产物 → 修改后重建。
- Reader 或玩法解构不足时，系统提出带来源的 Candidate 适配方案；不能宣称任意文本已经自动理解正确。
- 普通镜头、坐标、布局、素材裁切与适配由制作侧完成；不把每个底层制作字段都交用户填写。
- 每公式至少两个有实质差异的完整输入配置，并有真实操作与结果。同一 T3 的两种打法不等于两个不同关卡输入。
- 至少两套实质不同的多公式组合，经上述链路生成/编辑/重建；在所支持能力内，不改公式代码即可换输入。
- 已登记预设都要有验证或明确 capability_gap；TAC_T0–T11 等是应检查的能力面，不能只测最简单一个就宣布完成。
- capability_gap 是后续工作与扩展依据，不是永久排除困难能力、缩小目标的借口。
- 现有四件套继续复用：`formula-input-contracts.tsv`、`formula-asset-specs.tsv`、`formula-runtime-capability.tsv`、`formula-scene-types.tsv`；不另造一套管理框架。

### 1.2 玩家体验的共同完成标准

每个公式在其承担的任务内，必须用实际体验回答下面的问题。固定派遣、线性对白不强造分支；需要取舍的玩法不能用一路确认替代判断。

| 玩家问题 | 制作要求与验收证据 |
| --- | --- |
| 我是谁，眼前发生了什么，为什么值得做？ | 场景、人物、任务与目标相互对应。开场让玩家有行动理由；不能靠仓外文档、长篇系统讲解或反复弹帮助才能开玩。 |
| 我现在能做什么，选中了谁，怎样返回？ | 目标、可操作对象、焦点、合法/非法原因与下一步反馈清楚；键鼠各自承诺支持的路径完整。提示随当前动作变化，不要求记住内部术语或连续按键次数。 |
| 我作出了什么判断？ | 观察改变理解，方案存在可说明的区别，规则公开且能验证。可达成的挑战必须证明至少一条成功路线；失败能解释并指导下一次尝试。预设为不可胜的剧情样例须有明确输入来源，不能事后用“设计如此”解释未通关。 |
| 我的行动造成了什么？ | 实体、状态、角色回应和后续承接一致；可见动作与真实接触相符。玩家能说明一个关键结果的原因，成功、中止、未开始和失败各自成立。 |
| 我得到什么回报，为什么想继续？ | 在样例范围内兑现解题的满足、机战力量感、发现、人物回应、空间变化或新办法。允许爽快成功、安静日常和适量幽默，不让每种公式都变成审批与代价结账。 |
| 这些段落是否像同一款游戏？ | 镜头、身体尺度、操作语言、对白与声音协调；公式切换承接同一件事和同一世界状态。一次任务只前台化需要的玩法，避免七个菜单串联和重复确认。 |

“不看设计文档能开始并完成一段”“能说清自己作出的关键判断及其后果”“知道下一次可尝试什么”是体验证据；不以答题考试、统一分数或每段强塞选择作为新玩法。首玩理解必须由实际不熟悉该段的人验证；代理熟练操作与既有用户负反馈分别保留，不冒充新的首玩通过。

整套样例还要证明原始游戏吸引力：至少一条战术体验中，玩家通过主动布置形成可辨识的强解或高光，演出兑现力量与接触，回到仍成立的战场；至少一条非战术组合中，发现或生活选择带来人物回应、空间或后续办法的可见变化。人物不能只有解释、拒绝和签收的职能。不同公式各有节奏，不要求每段同时承担燃、爽、笑与伤感，也不以自动胜利的过场替玩家制造高光。

### 1.3 生产能力的体验证明

每公式至少两份实质不同的输入、至少两套实质不同的多公式组合，均须达到对应体验标准并有真实操作与结果。实质差异体现在题面、空间、关系、约束、选择或后果；改一句对白、换颜色或同题换打法，只能证明相应字段可改，不计第二内容输入。

链路保持 Reader＋游戏解构＋资产 → 有来源的制作解读 → 缺口及 Candidate 适配 → 配置/场景/状态 → 可玩体验 → 编辑后重建。体验修复要回到该链路：引导、焦点、镜头、对白和反馈若依赖新输入，明确字段、默认适配和缺项诊断；不能只给某包硬编码补丁，也不让用户承担普通坐标与裁切工作。

### 4.1 金标必须进入制作与验收

上述是分层借鉴与品质参照，不是只列游戏名，也不是承诺整部商业游戏的体量。每个公式开工/验收时都要说明：**参考中的具体一屏/一段操作→本项目吸收什么→为何改造→实际试玩表现与剩余差距**。做到功能清单不等于做到金标体验；颜色/斜框/像素色值相似也不等于可读、自然、有冲击力。

- 来源入口：[138 §3–9 案例](138-formula-lab-case-survey.md)、[融合取舍表](formula-lab-fusion.tsv)、[视频与时间戳账](formula-lab-video-ledger.tsv)、截图目录 `artifacts/formulas/case-survey/screenshots/`。只读相关行/案例，不重载庞大的历史实现日志。
- 至少用该功能的“操作前／关键动作或切换／结果返回”实际游戏帧或连续实录，与已核验参考对照。静态截图只能证明该屏，不能证明操作链、声音或节奏。
- 138 当前证据仍缺机战 Y 指令菜单本体、XCOM 2 编队卡 AAR、Banner Saga 行军提交、Obra Dinn 盖章动画的对应专帧；不能把理事会屏/开场地图或仓内简陋复刻冒充这些证据。涉及精确复刻/验收时先补相关来源，未补保留限制；不是要求每轮重看整部实况。
- 商业游戏只借设计与表达，不搬其资产/音乐/商标；Dialogue Manager、Popochiu 是实现参考，裂湾/Desk/LocationSceneRuntime 是工程底座，三者都不冒充商业金标。

## 6. 执行顺序：先评估体验，再集中修复并证明可复用

### 6.1 第一阶段：独立体验评估

从当前可启动入口和最新隔离变体开始，先明确玩家实际会打开哪一版。覆盖七公式、各自第二输入及至少两条现有跨公式操作链；已有实录足够证明的步骤直接复用，只对改版、缺证或存在问题的步骤补实际操作。不能只看成功路径、菜单截图或 readback。

以 §1.2 六个玩家问题审视体验，先记录看到的现象，再查实现原因。把“基本看不懂需要干什么”与“只是在测载荷，没有内容”作为待验证的两类问题：前者可能是目标/操作不清，后者可能是判断、动机、反馈或回报不足；不预设多写几句教学就能同时解决。

评估必须同时使用：

- 本项目实际的进入／关键选择或动作／后果返回；
- §4 对应金标的一段具体操作及借鉴层，按缺口补证，不重看整部实况；
- 原规则合同与状态结果，核对“玩家看见的”是否与真实发生的一致；
- 既有用户反馈，以及后续实际首玩者的简短观察。制作侧先自行排除明确缺陷，向用户提供可操作的短段，询问他理解了什么、想做什么、何处卡住，不要求先读术语或签整张表。

旧 OG 实玩与 [04 研发假设](../../game-design/2026-08-10-full-game-design-candidate-v1/research/2026-08-27-playable-reference-study/04-design-transfer-and-rd-hypotheses.md)用于检验意图、顺序、提交、反馈与层次；沿用“观察→解释→最小试验→通过/失败”的方法。它们补充既有七公式金标，不据此整套迁入 OG 指令、数值或成长结构。

只建立一份主评估 `artifacts/formulas/production-lab-v1/qa/experience-review-20260918/experience-review.md`，包含七公式/组合的覆盖表和按影响排序的问题清单。每条记录：包与版本、具体操作、玩家可见现象、截图/片段、影响、原因判断及其确定性、建议修复、如何验证、是否真需用户决策。明确区分已观察的问题、仅代码推断、证据不足。该路径是计划产物，未生成前不得声称评估完成。

优先级按影响决定：阻止理解/操作/可解性/真实因果的先修；削弱判断、回报、角色或连续体验的随后成组修；细小润色后置。不是按最容易变绿的测试、单一公式或最便宜的画面改动排序。完成这次评估后进入实施，不再反复扩写同类规划材料。

### 6.2 第二阶段：每次修好一个完整体验问题

主对话从评估中选择最有影响且可自主执行的一组问题，写清玩家修前与修后的差别，直接实施、定向测试、实际试玩并与参考对照。每轮走通从问题出现到结果返回的完整路径，避免只改一个标签后宣布整段通过。

首轮候选检查点：A 的任务理解与判断价值、事实卡键盘焦点/滚动与回源、F 的成功路线及失败解释、当前默认入口与较新变体是否脱节。这是已知线索，不预先定为所有公式的唯一问题；最终排序由评估证据决定。

玩法、空间、人物、对白、声音与动作共同修整：该由场景与表演说明的，不长期用结果文字顶替；美术不可读、缺动作或声画脱节仍记为开发工作。受身份/姿态许可约束的部分准备具体比较材料再求裁决，已授权环境及普通呈现工作继续推进。不能长期停在灰盒，也不能让一项美术裁决阻止无关体验修复。

### 6.3 第三阶段：不同输入和连续任务都成立

每项共享修复验证受影响的另一份实质输入，保持生产输入/消费者/产物对应，必要时更新原四件套。至少两套不同多公式组合完成生成、编辑、重建和真实操作；检查前段选择是否改变后段可见行为，后果是否在场景里承接，取消/重试/跳过是否保持承诺。

TAC_T0–T11 等已登记能力逐项给出当前实现、验证和可执行缺口。capability_gap 可让机器检查诚实报告，不能使所需能力永久免做；暂缓或移出目标必须有用户明确裁决。同一实验室可复用扩展，不把高档位拆成互不相干的小演示。

### 6.4 第四阶段：整体验收与交付

先完成制作侧审查、必要回归、金标对照和实际操作，再给用户短而明确的可试玩入口。报告已达到的体验、剩余问题和需要判断的具体差别；用户反馈“不懂、无聊、不自然”继续回到对应体验问题，不能归咎于未看文档或未签字。

最终交付：可启动的七公式与两套以上组合、各公式两份实质输入、可编辑输入与重建命令、四件套、主体验评估及修复复测证据。常规运行不展示制作内部术语、审计字段或签收任务；这些留在制作侧。

每轮只报告：玩家改善了什么、哪份输入可复用、实际看到了什么、剩下什么。用户判断品味、重大方向与最终验收；主对话负责需求拆解、制作方案和实施，不把规划工作反向交回用户。

## 7. 质量门

- **事实与输入**：身份/来源正确；读写与状态因果有证据；摘要前不写世界，Skip 不改变结局。
- **真实游玩**：正常键鼠可操作，错误/取消/重试清楚；自动驱动不能偷设成功、瞬移、改时间来凑图。
- **空间与接触**：相机/地面/脚点/单位朝向一致，双方与接触对象可识别，起势→命中→余波→返回连续。
- **声画与角色**：统一规格与身份，合法动作、真实透明边缘、可读 UI/台词，音效与命中同步；不是只有呼吸漂浮。
- **复用与重建**：真实输入变化进入可玩产物，缺口可执行，来源可追溯；不要求用户手填全部底层适配。
- **验收分级**：机器通过≠实际画面通过≠用户喜欢≠Canon/Runtime 晋升。所有未验收项保持明确状态。
- 仅在冻结输入和跨任务交接保留必要哈希；不每帧哈希、不反复全项目重审、不以流程复杂度代替质量。

**140 完成须同时满足：** §1 的体验与两类复用要求、§4 七公式矩阵与对应参考证据、§6 的实际组合和交付、上述质量要求，以及适用的用户验收。体验评估中的阻断问题已关闭，其他未达目标项不能靠改名为“长程美术”或“用户侧”移出范围；范围取舍需明确裁决。

`formula-desk test/swap/freeze` 仍按原合同使用。137 的四门和旧手感模板检查的是其明确覆盖的范围；`freeze` 放行不自动等于本目标完成，一个档位的签收不外推到整公式、所有输入或整体视觉。先给可评体验，再记录准确范围的验收，不以凑齐签名收尾。

## 8. 自主执行与需暂停事项

常规修错、测试、既有界面/镜头/配置打磨、独立候选窗口与采集可自主进行；不要反复问“是否可以打开”。

### 8.1 模型分工与额度纪律

- **用户最新裁决：不固定 Sol，也不把复杂工作永久绑定 Astra。** 主对话负责制作决策、接口与验收，可按任务难度、工具/模态、风险和模型实际表现，为 subagent 选择任何当前接口支持的模型，并保留最终整合责任。
- 以保证质量前提下的**总 token/额度消耗最小**为选型目标，包含上下文、推理、工具输出、返工与复审；不能只按模型名称、单次速度或单价判断，也不降低既有验收标准。
- 简单、边界清楚、可直接验证的查找、机械修改、小范围修复、现成测试与证据整理，在能力适配且接口可调用时，**尽量优先 `gpt-5.3-codex-spark`**。不要求全部任务先试 Spark；复杂状态因果、跨模块设计、身份/空间审图等可直接选胜任模型。
- 以当前 **subagent 接口**实际模型与 reasoning 支持为准，显式指定所选模型/档位；主任务模型列表或账号可选项不等于 subagent 一定可调用。Spark 不支持时选合适替代并简短说明，不循环调用，也不擅自新建用户任务来绕过限制。
- 短上下文通常 `fork_turns=none`，只交必要文件/背景/证据；一般 1–2 个有用并行任务，写清所有权、输入、交付和停止点。不整段历史 fork，不为用 Agent 而拆任务；主对话一次即可做完的小改动可直接完成。
- 用定向测试和实际结果检查交付；一次明确纠正后仍在同类问题上失败，或发现任务超出所选模型能力，及时换模型/重拆任务/主对话接管，不无限低能力重试，也不让高能力模型重复重做全部普通工作。
- 定向读取与风险比例验证；普通修复不要重跑所有公式/Canon 全套，只有迁移相应权威才跑相关治理门。
- 每完成可见增量更新短交接：产物、证据、未通过、下一刀。140 只更新目标/裁决，历史日志归证据目录，避免再次膨胀。
- 换模型属于已授权的常规分工，不必逐次申请；升级时简短说明原因。新增付费服务、购额或改变用户计费设置仍需另行授权。

事实边界：OpenAI Docs 将 Spark 定位为快速、能力较低且有独立用量限制的模型；这不保证它必然更省总 token，也不保证当前 subagent 支持。见[官方说明](https://learn.chatgpt.com/docs/agent-configuration/speed#codex-spark)。以上是动态选型策略，不是固定模型能力排行榜。
