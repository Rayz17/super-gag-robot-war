# 《超GAG机器人大战》剧情 Reader 与游戏解构分层规则 v2

> Status: `working_delivery_separation`; 创作顺序由[2026-09-05现行方法](./2026-09-05-chao-gag-author-first-writing-method-v1.md)更新。本文仍规定三层产物边界，不再要求先用三板生成故事。
> Date: 2026-08-07  
> Supersedes: `2026-07-07-chao-gag-episode-production-layer-split-v1.md` 中“在同一 Reader 内混排可读层与制作层”的推荐结构。旧文档仍可作为六类制作段落的字段参考。

## 一、为什么要改

此前 Episode Reader 同时承担了四种互相冲突的任务：

1. 让普通读者连续经历一段故事；
2. 说明玩家此时操作什么、目标是什么；
3. 记录关卡变量、触发条件、单位和状态；
4. 补充世界机制与已公开情报。

结果是人物刚开口，正文便切进任务界面；机器人刚行动，叙述便解释接口、数值、阶段和冷却。作者为了让所有字段成立，不断临场发明场景名词和微小动作，故事的欲望、冲突、情绪与大画面反而被压扁。

从本规则开始，这四种任务不再由同一份正文承担。

## 二、三份独立产物

### A. 纯剧情 Reader

唯一目的：回答“这段故事本身是否好看、好懂、有人物和机器人动画的力量”。

它可以写：

- 人物行动、对白、关系和情绪；
- 玩家能够看见的地点与大画面；
- 战斗为什么发生、双方争什么；
- 战斗中的关键转折、必杀动作和人物选择；
- 战后结果及下一话悬念。

它不写：

- `玩家`、`UI`、菜单、可操作名单、地图格、回合、冷却、数值和变量名；
- 胜利条件、失败条件、隐藏条件和支援教学；
- 制作资产、镜头成本、立绘需求和触发器；
- 用于证明设计合理的承重公式、接口链、权限链和设备操作全过程；
- 话末百科、机制注释或作者后台真相。

战斗在剧情 Reader 中只写成一场戏：目标清楚，动作有画面，转折来自人物和机体，胜负改变故事。具体怎么玩留给游戏解构。

### B. 游戏流程解构

唯一目的：把已经成立的剧情转换成玩家经历和制作接口。

它按实际游玩顺序拆分：

- ADV；
- 地图移动、探索或副玩法；
- SRPG 战斗；
- 战中通讯和演出；
- 战后关系事件；
- 结算、变量与下一话交接。

这里才允许出现：

- 玩家目标、失败条件和可选目标；
- 地图、单位、阶段、触发条件和变量；
- UI 提示、教学、支援选择和分支；
- 演出载体、资产需求和制作预算；
- Clear State 与状态账回写。

游戏解构不得给剧情补动机。若一个目标只能在此文件解释，剧情 Reader 不成立，应退回故事层。

### C. 可公开情报

唯一目的：解释玩家在本话已经看见、但正文不适合长篇说明的背景或表层机制。

规则：

- 情报页只能总结已经由剧情或操作展示过的事实；
- 可以解释名词、历史、机体规格和局部技术原理；
- 不能推进剧情、替人物作选择或补上遗漏的因果；
- 没有真正需要解释的内容可以不生成；
- 一张卡只回答一个问题，优先使用常用词。

## 三、生产顺序

```text
有效前情、人物模型与未来职责
-> 主笔选择故事
-> 简洁章纲与早期玩法概念相互校准
-> 必要因果、尺度核对与难点场面试写
-> 纯剧情 Reader
-> 普通读者冷读与人物声线审查
-> 故事暂定通过
-> 游戏流程解构
-> 可制作性与机战体验审查
-> 可公开情报
-> 三层一致性检查
-> 用户创作验收
```

正式Story Chain未迁移前，其阶段顺序继续用于合法整合与封存；Candidate探索不覆盖封存文件，也不因先写样稿自动获得正式PASS。详细三板、拓扑和L4.5用于验证选定故事，不能提前规定全部动作答案。早期玩法概念与详细游戏解构是两种粒度，后者仍不混入纯剧情。

### 3.1 Episode不等于关卡

生产时显式区分七种对象：Story beat/Scene、Episode、Battle Incident/Operation、Encounter/Play Segment、Battle Phase、Checkpoint/Save Resume、Mission Clear。它们允许多对多映射。

- Episode只决定叙事何处切话，可以插标题、回顾和存档。
- Operation记录世界中尚未解决的同一场危机或行动。
- Encounter是玩家的一段连续操作，可换地图但不能默默重置世界状态。
- Phase只改变同一Encounter内的目标、增援、Boss形态或地图状态。
- Checkpoint允许退出和继续，不代表治疗、奖励结算或敌人刷新。
- Mission Clear只在Operation的主要冲突真正结束时出现。

每章在完整章纲前生成`Cxx-剧情游玩拓扑与状态桥接.tsv`。每个边界记录敌人、友军伤势、装备、地图破坏、平民风险、当前目标和时间的`IncidentState`输入/输出。详细规则见`2026-08-08-chao-gag-story-play-operation-topology-contract-v1.md`。

导演板、物理板和战斗预案仍可在后台提供硬边界，但纯剧情主笔只接收其结论：谁在场、什么不能发生、冲突为何无简便解。不得把板上的术语、阶段和动作链直接交给主笔照写。

## 四、纯剧情 Reader 的最低门槛

每一场先用白话回答：

1. 谁想得到什么；
2. 谁或什么阻止；
3. 为什么现在必须处理；
4. 采取了什么容易看懂的办法；
5. 场面结束后什么变了。

并通过以下检查：

- 陌生读者不看设定表也能复述本话；
- 删除所有游戏术语后，故事仍完整；
- 角色不是为了交代机制才说话；
- 建筑和机体只描写足以形成画面及因果的部分；
- 同一段不同时解释空间、权限、技术、玩法和主题；
- 常识能解决的事不另造名词；
- 重要动作以大画面和结果为主，小机构只在决定胜负时出现；
- 章前已存在的重要人物必须用一句自然前情完成再介绍；
- 人物不会突然不知道自己上一章亲历或确认过的事情。

## 五、游戏解构的最低门槛

- 每个可玩段都能指出对应的剧情场面；
- 关卡目标是剧情冲突的可操作版本，不是额外任务；
- 战斗中复杂机制不反向污染剧情对白；
- 画面和交互可以代替说明的内容不写成长篇旁白；
- 变量只记录制作需要，不伪装成人物语言；
- 若制作成本过高，先改变玩法承载，不要求剧情用更多技术解释自救。
- 每个Episode边界必须说明是`episode_cut`、`phase_transition`、`checkpoint`、`mission_clear`、`time_skip`还是`location_change`；不得默认结算。
- 户外SRPG默认允许镜头滚动，楼房、街区、道路和可破坏建筑属于棋盘本体；固定小图仅用于确实封闭的室内空间。

## 六、当前 C03-C04 迁移规则

- 用户已于 2026-08-08 明确接受 C03 四话纯剧情 Reader。正式单话源位于 `V35.9/rebuild/reader/episodes/C03/`，正式章节入口为 `V35.9/rebuild/reader/C03-章节连续阅读稿.md`。
- C03 纯剧情 Reader 是 C04 唯一可直接继承的故事前情；同轮制作的《游戏流程解构》和《可公开情报》仍留在 `story-runtime/effect-tests/`，只作 Candidate 制作接口，不自动成为角色记忆、剧情事实或后章正文输入。
- C03 的旧混合 Reader、旧同章草稿和失效审查继续作为 History 诊断样本，不得与正式纯剧情源拼接。
- C04 必须从已验收 C03 的章末人物、机体、去向和天空铸环来讯重新完成 L4；旧 C04/C05 只允许按项打捞发动机、高光和已识别问题，不能直接刷新哈希复活。
- C04 及后章继续执行固定次序：完整章纲与后台可行性边界 -> 逐话纯剧情 Reader -> 冷读/因果/人类声线 -> 独立游戏流程解构 -> 按需公开情报 -> 三层一致性 -> 用户创作验收。

## 七、验收方式

用户应按以下顺序阅读：

1. 只读纯剧情 Reader，判断是否想继续、是否清楚、人物是否像人；
2. 再读游戏流程解构，判断是否好玩、能否制作、有没有把故事转成操作；
3. 最后按需阅读公开情报，判断是否补足而非补锅。

任何内部规则检查、字段完整、Canon 对齐和审稿 PASS 都不能替代第一步。

## 八、已验收章节的回溯迁移

当新方法要回溯处理已获得用户验收的章节时，不得直接覆盖 Current Reader，也不得因为新文件内部 PASS 就自动提升。

正确顺序是：

```text
锁定已验收的剧情事实与章末状态
-> 建立并行 Candidate 目录
-> 重写纯剧情单话源文件
-> 机械合成候选章节 Reader
-> 纯剧情冷读
-> 独立派生游戏流程与可公开情报
-> 三层一致性与跨章连读
-> 用户决定保留 Current、局部吸收或整体替换
```

回溯重写的目标不是换句式，而是恢复三种不同的创作职责：

- 纯剧情层重新决定场面、人物选择、情绪和机器人动作，不复制旧 Reader 的解释段；
- 游戏流程层只对已成立的故事做可玩化，不得为了关卡而新造一条剧情因果；
- 情报层负责解释玩家已看见的机制，不能把正文本该说清的动机藏到百科里。

候选章节只允许由明确排序的单话源机械合成。当前工具为：

```bash
python3 scripts/assemble_pure_story_candidate.py \
  --chapter Cxx \
  --title '章节名' \
  --output '<candidate-reader.md>' \
  --episode '<episode-1.md>' \
  --episode '<episode-2.md>'
```

工具必须记录单话哈希，拒绝将公开情报或 SRPG 字段合回纯剧情。在用户确认替换前，它不修改 story-chain manifest、Current Canon Pack 或生产看板的当前章节状态。

## 九、C01-C02 回溯样板的当前边界

- C01、C02 原 Current Reader 仍然是已验收的正式前情。
- `story-runtime/effect-tests/C01-story-gameplay-separation-2026-08-07/` 与 `C02-story-gameplay-separation-2026-08-07/` 是并行 Candidate，用来评估新方法能否在不丢已验收事实的前提下提高故事可读性。
- 用户若确认替换，再从 C01E01 开始使原 story-chain 下游失效，回建 Current Reader、状态账、章间交接与 C03 前情。
- 用户若只接受局部改进，必须将具体场面迁移回单话源，不直接手改机械合成的章节 Reader。

## 十、三层权威不得互相冒充

- **剧情事实权威**：只取已验收的纯剧情单话源、机械章节 Reader、章末状态和用户回执。
- **游戏制作权威**：只取从相应纯剧情稿派生并单独审查的游戏流程文件；它可以规定玩法和变量，不能反向补写人物动机。
- **公开说明权威**：只取玩家已见事实的解释卡；它不能成为读懂剧情的必读前提。
- 后章主笔默认只读取剧情事实权威。只有在设计玩法或核对表层机制时，才按问题查询另外两层。
- 同一事件若三层表述冲突，先判断冲突属于故事、可玩化还是说明；退回对应上游修正，不用合订稿折中。
